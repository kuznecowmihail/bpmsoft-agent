# bpmsoft-agent

ИИ-агент для разработки BPMSoft-проектов: пишет файлы пакетов, а при включённых настройках сам обновляет и компилирует стенд, читает БД и смотрит интерфейс CRM. Описание и принципы — `README.md`, бэклог — `BACKLOG.md`, сценарии ручной проверки — `docs/test-runs/`.

## Где что лежит
- `packages/agent-runtime/knowledge/*.md` — база знаний агента о metadata BPMSoft: файлы «фактов» (`<тип>.md`) и «рецептов» (`<тип>-edit.md`). Общая механика — `metadata-editing.md`, таблица «что подтверждено записью» — `knowledge-status.md`.
- `packages/agent-runtime/src/provider/systemPrompt.ts` — системный промпт агента и индекс файлов знаний. Каждый новый файл знаний нужно добавить в этот индекс.
- `packages/agent-runtime/claude-export/` — ядро правил `AGENTS.md` и скиллы для Claude Code и Cursor, которые приложение устанавливает в стенд (кнопка в «Настройки»): ядро — в `AGENTS.md` стенда, `CLAUDE.md` стенда подключает его строкой `@AGENTS.md`, скиллы — в `.claude/skills` (Cursor читает их оттуда же). Тексты экспорта пишем нейтрально к инструменту. Меняешь порядок работы или правила в `systemPrompt.ts` — проверь и `claude-export/`.
- Агент работает в корне приложения BPMSoft: рабочая область — `BPMSoft.Configuration/Pkg`; только для чтения — `conf/content`, `BPMSoft.Configuration/Autogenerated`, `Resources`, XML-документация `BPMSoft.*.xml`. Пути к стендам в репозитории не храним.

## Карта кода
npm workspaces, порядок сборки: `metadata-core` → `agent-runtime` → `desktop` / `evals`. Пакеты подключаются друг к другу через `dist/` (`main: dist/index.js`): после правки `agent-runtime` или `metadata-core` пересобери их (`npm run build -w @bpmsoft-agent/<пакет>`), иначе desktop и evals видят старый код. Тесты — vitest в каждом пакете: `npm test -w @bpmsoft-agent/<пакет>`, тест по имени — `npx vitest run <файл>` в папке пакета. Desktop: `npm run dev -w @bpmsoft-agent/desktop`, проверка UI — скилл `run-desktop`.

`packages/agent-runtime/src/`:
- `provider/anthropicProvider.ts` — Claude Agent SDK `query()`. Инструменты приложения — in-process MCP-серверы `crm_db`, `crm`, `app` (имена `mcp__app__<инструмент>`); изоляция от `~/.claude` разработчика (`settingSources: []`, `skills: []`); хук `PreToolUse` вызывает песочницу.
- `provider/cursorProvider.ts` — Cursor SDK: встроенные инструменты Cursor выключены, файлы и команды идут через `tools/localTools.ts`, инструменты приложения — `customTools`; правила песочницы — текстом в первом сообщении.
- `provider/systemPrompt.ts` — промпт и индекс знаний; разделы про инструменты включаются флагами `dbQuery`, `crmActions`, `crmBrowser`, `crmRequest`, `gitMr`, `tracker` (выставляются в `anthropicProvider.ts` по набору инструментов). `messageMapper.ts` — сообщения SDK → `AgentEvent`; `claudeModels.ts` — список моделей.
- `safety/sandboxGuard.ts` — доступ инструментов к путям (чтение — папка приложения и знания, запись — `Pkg`, секреты запрещены) и списки имён инструментов приложения (`*_TOOL_NAMES`, `*_TOOL_PATTERN`); `safety/shellSandbox.ts` — песочница ОС для shell.
- `db/` — `crm_db_query` (только SELECT/WITH, `sqlGuard.ts`); `crm/` — сессия CRM, `crm_update_from_fs`, `crm_compile`, `crm_request` (OData/DataService), журналы, счётчик петли исправлений `fixLoop.ts`; `lint/` — `pkg_lint`; `git/` — `git_branch_status`, `git_switch_branch`, `git_create_mr`; `tracker/` — `jira_get_issue`, `jira_add_comment`, `confluence_get_page`; `tools/` — тип `AppTool` и zod-схемы, `localTools.ts`, `gitBash.ts`, уборка staging-папок SDK.
- `mcp/` — MCP-сервер `bpmsoft` для Claude Code и Cursor стенда; `claudeExport/` — установка в стенд `AGENTS.md`, скиллов, знаний, MCP и разрешений (`MCP_PERMISSIONS` в `standIntegration.ts`). `lint/pkgLintMain.ts` и `mcp/mcpMain.ts` бандлятся esbuild в `dist/claude-export/` (`pkg-lint.js`, `bpmsoft-mcp.js`).

`apps/desktop/src/` (Electron, electron-vite, React):
- `main/index.ts` — окно и все `ipcMain.handle` (каналы `agent:*`, `chat:*`, `settings:*`, `crm:*`, `db:*`, `jira:*`, `confluence:*`, `crmBrowser:*`, `claudeSkills:*`, `project:*`, `env:*`); `preload/` — мост IPC; `shared/types.ts` — общие типы main и renderer.
- `main/agentSession.ts` — ход агента: собирает инструменты по настройкам (`appTools`), выбирает провайдера, карточки разрешений, «Стоп», продолжение сессии; ключи и пароли — через `secureStore.ts` (safeStorage: Keychain / DPAPI).
- `main/crmBrowser.ts` — встроенный браузер CRM и инструменты `crm_browser_*`; `chatLog.ts`, `chatIndex.ts`, `chatReplay.ts`, `chatOpen.ts` — логи и история чатов; `appSettings.ts` — настройки (подключения по проектам — `projectConnections`); `fileDesignMode.ts`, `projectValidation.ts`, `environmentCheck.ts` — проверки стенда и машины.
- `renderer/src/` — `App.tsx`, `components/` (все настройки — `SettingsMenu.tsx`), `chatFormat.ts` (разбор `<choices>` и форматирование ответа).

Остальное:
- `packages/metadata-core/src/layout/workspaceLayout.ts` — структура папок приложения BPMSoft.
- `packages/evals/src/` — `cli.ts`, `runner.ts` (диалог и ответы агенту), `checks.ts` (проверки результата), `evalPackage.ts` (тестовый пакет); кейсы — `packages/evals/cases/NN-<тема>.json`, фикстуры — `packages/evals/fixtures/`.
- `scripts/fetch-platform-packages.mjs` — SDK под другие платформы для `dist:mac` / `dist:win`; `scripts/crm-probe.mjs` — прототип вызовов API CRM. Конфиг сборки — `apps/desktop/electron-builder.yml`, результат — `apps/desktop/release/`.
- `docs/superpowers/specs/` и `plans/` — описания и планы крупных возможностей; `BACKLOG.md` — разделы «Выполнено», «В работе», «Не реализовано».
- Данные приложения на macOS: логи — `~/Library/Logs/bpmsoft-agent/` (`chats/`, `knowledge-notes.md`, `environment.json`), настройки — `~/Library/Application Support/@bpmsoft-agent/desktop/settings.json`; на Windows логи — в `<userData>/logs`.

Новый инструмент агента: `AppTool` в `agent-runtime` → подключить в `appTools` в `agentSession.ts` → имя в списки `sandboxGuard.ts` → флаг и раздел в `systemPrompt.ts` → если нужен в экспорте, в `mcp/bpmsoftMcpServer.ts` и `MCP_PERMISSIONS` → тесты в `packages/agent-runtime/test/`.

## Как мы работаем с BPMSoft
- Все изменения схем — только через файлы в `Pkg`. После правки пользователь нажимает в CRM «Обновить из файловой системы» и проверяет результат. Действия и скриншоты в Designer делает пользователь по запросу.
- Тестовые схемы создаём в отдельном тестовом пакете, с тестовым префиксом в имени; после проверки удаляем.
- Ресурсы (`resource.<culture>.xml`) — всегда в двух языках: `ru-RU` и `en-US`.
- При каждом создании или изменении схемы — актуальный `ModifiedOnUtc` в `descriptor.json` (`date +%s000`), а не выдуманная дата.
- Удаление схемы: папки `Schemas/<Имя>/` и `Resources/<Имя>.<Категория>/`. Перед удалением проверь по всему `Pkg`, не ссылаются ли на схему другие (по UId и имени), и предупреди пользователя, если ссылки есть.

## Как пополнять знания
- Не изобретай metadata. Факт, помеченный ✅, используй напрямую; для 🧪-рецептов и UId конкретного проекта делай узкий точечный поиск по файлам.
- Опровергнутую гипотезу помечай явно (что предполагали и что опровергло), а не удаляй молча.
- Как только рецепт подтверждён реальной записью в CRM, переведи его в ✅ в `<тип>-edit.md` и обнови таблицу в `knowledge-status.md`.
- Новый тип схемы — пара файлов `<тип>.md` + `<тип>-edit.md` и строка в индексе `systemPrompt.ts`.
- Знания в экспорте для Claude Code и Cursor: при установке скиллов папка `knowledge` копируется в стенд целиком, но агент находит файл только по ссылке в `claude-export/AGENTS.md` или скилле. Новый файл знаний (в том числе после деления) — сразу и в индекс `systemPrompt.ts`, и в подходящий скилл `claude-export/skills/` (таблица `bpm-develop`, список `bpm-explain`, скилл темы); новые правила работы из `systemPrompt.ts` — в `claude-export/AGENTS.md`. Тест `claudeExportTexts.test.ts` проверяет, что каждый файл знаний упомянут в экспорте.
- Размер файла знаний — до 40 КБ; жёсткий предел 50 КБ и наличие файла в индексе проверяет тест `knowledgeFiles.test.ts`. Перед дописыванием проверь `wc -c`: если файл выйдет за 40 КБ, сначала раздели его по разделам `##` на `<тип>-<тема>.md` / `<тип>-<тема>-edit.md` (на месте раздела — строка-ссылка), новый файл — в индекс `systemPrompt.ts` и в скиллы `claude-export/`.

## Наблюдения агента → знания
- Как идёт разработка: пользователь тестирует агента в приложении на своём стенде; в конце задачи агент пишет блок «Наблюдения для базы знаний» (лог чата и `~/Library/Logs/bpmsoft-agent/knowledge-notes.md`). По просьбе «проверь наблюдения» сверяем каждое с логом и файлами стенда и переносим в знания только подтверждённое.
- Репозиторий публичный, знания обезличены: в записях нет названия проекта и стенда, путей, имён пакетов, схем, колонок и процессов проекта. В примерах — нейтральные имена (`<Объект>`, `<Пакет>`, `Test…`).
- Подтверждение пишем без указания, на чём: «✅ подтверждено записью в CRM (<дата>)», «✅ подтверждено на реальных схемах проекта», «🧪 не проверено». UId платформы указываем, UId схем и записей проекта — нет.
- Перед коммитом проверь поиском, что в файлах репозитория нет имён проекта.

## Эвалы (`packages/evals`)
- После изменений, которые меняют поведение агента (`systemPrompt.ts`, файлы знаний, инструменты `agent-runtime`, провайдеры, смена модели), предложи пользователю прогнать эвалы: после правки — кейсы по затронутой теме (`--case`), перед сборкой для пользователей — полный прогон. Правки интерфейса приложения, настроек и упаковки эвалов не требуют.
- Новая возможность агента или ошибка агента, найденная в ручной проверке, — предложи новый кейс в `packages/evals/cases/`: задача, которой ещё нет на стенде (предпроверка не должна проходить), ответы раннера по порядку и проверки результата.
- Прогон запускает пользователь: стенд общий, прогон стоит денег. После прогона разбери `packages/evals/results/<runId>` и поправь кейс (ответы, проверки) или агента.
- Кейсы обезличены, как знания: имена только из плейсхолдеров (`{{entity}}`, `{{package}}`, `{{prefix}}`…), значения стенда — в `local.json` и `.env`, они не коммитятся.

## Технические правила
- Правки файлов делает субагент `haiku-common-agent` (skill `claude-token-economy`); основная сессия читает, планирует и после каждой правки сама перечитывает изменённые файлы.
- Приложение работает на macOS и Windows (Linux — только как среда разработки). Любой код пиши кроссплатформенно: пути через `path.join`, без `/` в строках; никаких `$HOME`, `~`, `/tmp` и обратных кавычек оболочки в коде; внешние программы — через `spawn`/`execFile` без `shell: true`; бинарники ищи по платформе и расширению (`.exe`). Если поведение неизбежно разное (песочница, Keychain/DPAPI, bash), пиши ветку по `process.platform` и покажи в ответе, что будет на второй ОС.
- Код и знания должны переживать файлы с CRLF и BOM: сравнение и замену текста делай устойчиво к переводам строк, а при записи сохраняй исходные.
- Весь промпт в `systemPrompt.ts` — один template-литерал: не вставляй в него обратные кавычки. После правки — `npm run build` в `packages/agent-runtime`.
- Shell — zsh: `echo` превращает `\n` внутри строк в перевод строки. Код передавай через `printf '%s\n'` или пайп, а не через `echo`.
