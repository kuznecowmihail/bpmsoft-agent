# Задачи для проверки — прогон 16 (задача из Jira, ветка и MR)

Проверяем цепочку «задача из Jira → агент → ветка и MR» в приложении на реальных Jira, Confluence и GitLab: загрузку задачи, проверку ветки на старте, ветку и MR после проверки, комментарий в Jira и допуш в открытый MR. Описание — `docs/superpowers/specs/2026-10-29-jira-mr-chain-design.md`.

## Перед прогоном
- Собери и перезапусти приложение: `npm run build -w @bpmsoft-agent/agent-runtime`, затем `npm run dev -w @bpmsoft-agent/desktop` (или собранное приложение).
- В настройках заданы Jira и Confluence (адрес, токен, для Cloud — email), CRM и Claude.
- Стенд — тестовый, работаем в пакете `<Пакет>`. Тестовые схемы — только с префиксом `Test…`, после проверки удаляем.
- `Pkg` (или пакет) — git-репозиторий с origin в тестовом проекте GitLab, у разработчика есть права на push. Целевая ветка MR существует на origin.
- В Jira заведена тестовая задача `<KEY>` с описанием и критериями приёмки небольшой доработки в `<Пакет>`; в описании — ссылка на страницу Confluence.
- После прогона закрой тестовые MR, удали тестовые ветки на origin и тестовые схемы.

## 1. Подключение
**Проверяет:** проверку подключения и бейджи в шапке.
**Как проверить:**
- в настройках «Проверить подключение» для Jira и Confluence показывает имя пользователя;
- бейджи Jira и Confluence в шапке зелёные;
- с неверным токеном — понятная причина (401/403), токена в тексте ошибки нет; верни правильный токен.

## 2. «Взять задачу из Jira»
**Проверяет:** загрузку задачи кодом и то, что агент не переспрашивает то, что в ней есть.
**Как проверить:**
- нажми «Взять задачу из Jira», введи ключ `<KEY>`, затем повтори со ссылкой на задачу;
- новый чат начинается сообщением с ключом и названием задачи, строкой «Тип: … · Статус: …», описанием, критериями приёмки и комментариями;
- агент не вызывает `jira_get_issue` повторно;
- вопросы агента — только о том, чего нет в задаче; запиши каждый вопрос и есть ли ответ на него в задаче;
- несуществующий ключ — причина ошибки; текст задачи можно вставить в чат вручную, и агент работает по нему.

## 3. Confluence в задаче
**Проверяет:** загрузку связанных страниц.
**Как проверить:**
- в сообщении задачи есть текст страницы Confluence из описания;
- со ссылкой на страницу, к которой нет доступа, — строка «не загружена: причина», остальная задача загружена.

## 4. Ветка на старте
**Проверяет:** `git_branch_status` и переключение ветки.
**Как проверить:**
- перед задачей встань на чужую ветку с коммитами, которых нет в целевой;
- после выбора пакета, до вопросов по требованиям, агент показывает текущую ветку и чужие коммиты и спрашивает «В какой ветке работать?» с кандидатами (ветка с ключом задачи, целевая, недавние ветки origin);
- «Переключись в <ветка>» — карточка подтверждения `git_switch_branch`; после переключения агент предлагает обновить CRM;
- с незакоммиченными правками в репозитории переключение не выполняется, агент показывает список файлов.

## 5. План
**Проверяет:** строку о ветке и MR в плане.
**Как проверить:**
- в плане есть строка «Ветка: от <текущая>, MR в <целевая>, репозиториев N».

## 6. Ветка и MR
**Проверяет:** `git_create_mr`: состав коммита, push-опции, описание MR.
**Как проверить:**
- до MR положи в `Pkg` посторонний незакоммиченный файл вне задачи;
- после проверки на стенде агент спрашивает «Создать ветку и MR?»; без ответа MR не создаёт;
- карточка подтверждения показывает по каждому репозиторию файлы, имя ветки `<KEY>-<кратко>`, текущую и целевую ветки, чужие коммиты (если есть), заголовок и текст MR;
- в GitLab появился MR в целевую ветку: заголовок «<KEY> <название>», описание — из плана (AC, CC, DoD, итог pkg-lint и проверки);
- в коммите только файлы задачи с их ресурсами; посторонний файл остался незакоммиченным в рабочей копии;
- агент приводит ссылку на MR и говорит, что рабочая копия осталась на новой ветке.

## 7. Комментарий в Jira
**Проверяет:** `jira_add_comment` с подтверждением.
**Как проверить:**
- после MR агент спрашивает «Добавить комментарий в Jira?»;
- после подтверждения в задаче появился комментарий со ссылкой на MR.

## 8. Допуш в открытый MR
**Проверяет:** доработку в ветке открытого MR.
**Как проверить:**
- в том же чате попроси небольшую правку по задаче;
- после проверки агент спрашивает «Допушить в MR?»;
- новый коммит появился в ветке открытого MR; новой ветки и второго MR нет.

## 9. Репозиторий на пакет
**Проверяет:** несколько MR в одной задаче.
**Как проверить:**
- возьми задачу, которая меняет два пакета, у каждого свой git-репозиторий;
- в плане — «будет 2 MR»;
- создано два MR с одинаковым именем ветки; в отчёте агента и в комментарии Jira — обе ссылки;
- запиши, есть ли в каждом MR ссылка на второй.

## 10. Сбои
**Проверяет:** поведение при ошибке push и без git.
**Как проверить:**
- отключи сеть (или забери права на push) и попроси создать MR: локальная ветка и коммит есть, агент называет причину; после восстановления повторный `git_create_mr` только отправляет ветку, второго коммита нет;
- на стенде без git агент говорит, что MR не создать, и не пытается делать ветку и коммит командами git.

## Итог
- Для каждой задачи отметь результат и то, что видно в интерфейсе.
- Отдельно запиши, совпадает ли поведение с описанием в спеке; расхождения — в бэклог или в спеку.
