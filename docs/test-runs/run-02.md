# Задачи для проверки агента — прогон 2

Цель — проверить всё, что добавлено в знания и приложение после первого прогона (27 задач): чек-лист и скрипт проверки процесса, исправленные рецепты процессов, шаблоны наборов данных для проекта без образцов, новые клиентские и серверные рецепты, правило «ошибку исправляй без нового плана» и вопросы кнопками.

## Общие правила
- **Перед прогоном** перезапусти приложение (новый промпт и повтор запросов Cursor работают только после перезапуска).
- **Стенд.** Основной — стенд B без своих пакетов. `{PKG}` — новый пакет из задачи 1, `{P}` — префикс `Tst2`. На стенде A (если повторяешь): `{PKG}` = `ProjectMain`, `{P}` = `PrjTst2`, задачу 1 начинай со второго абзаца (справочник и раздел в существующем пакете).
- **Новая задача — новый чат.** Внутри задачи ответы, «делай» и сообщения об ошибках — в тот же чат.
- **Провайдер.** Задачи с процессами (4–8) прогони на обоих: сначала Cursor, затем Claude в новом пакете или с другим префиксом. Остальные — на любом, отметь какой.
- **После задачи** — «Обновить из файловой системы», при необходимости компиляция и Ctrl+F5; ошибки — в журналах `[app]/Logs/<дата>/`.
- Задача 9 зависит от задачи 4, задача 10 — от всех.

## Что смотреть в каждом прогоне
1. **Вопросы кнопками.** Вопросы и подтверждение плана пришли блоком с кнопками, а не «1 а 2 б». Ответ кнопками агент понял правильно.
2. **Порядок.** Пакет → вопросы → план → «Делай» → запись. После «Делай» лишних вопросов нет.
3. **Скрипт проверки процесса.** В логе после записи процесса есть запуск `scripts/check-process.js`, строки «ОШИБКА» исправлены до ответа, «ВНИМАНИЕ» упомянуты в ответе.
4. **Число кругов «ошибка → правка».** Сколько раз пришлось писать агенту об ошибке. В первом прогоне — 9 на 8 задач с процессами. Цель — 0–2 на весь прогон.
5. **Знания вместо догадок.** Агент берёт ✅-рецепты и шаблоны (`templates/process`, `templates/data`), а не изобретает; 🧪 честно помечает в рисках.
6. **Наблюдения для базы знаний** в конце задачи — без повторов того, что уже ✅.

В нём: справочник "Тип обращения" ({P}TicketType) — Вопрос, Жалоба, Благодарность / Question, Complaint, Thanks, виден в разделе "Справочники"; объект "Обращение" ({P}Ticket): Тема (строка, обязательная), Тип (справочник), Срочное (логическое), Ответственный (контакт, по умолчанию текущий), Срок (дата и время); раздел "Обращения" с иконкой в рабочих местах "Общее" и "Продажи"».
**Проверяет:** новый пакет — агент спрашивает зависимость и предлагает ProductCore, не Custom; наборы из `templates/data/` (Lookup, записи справочника, SysModuleEntity, SysModule, SysModuleEdit, SysModuleInWorkplace, SysImage); Id рабочих мест агент просит у тебя SQL-запросом и сверяет имя; раздел в двух рабочих местах — две строки в одном наборе.
**Как проверить:** пакет установился; справочник в «Справочниках» на двух языках; раздел с иконкой в обоих рабочих местах; карточка открывается.

## 2. Автономер, мини-карточка и пункт «Действий» по условию — M
**Зависит от:** 1.
**Формулировка для агента:** «У обращения: Номер заполняется автоматически по маске "ОБР-00001" и на карточке, и на мини-карточке быстрого добавления (Тема, Тип, Срок); поле "Срок" обязательно, если обращение срочное; в меню "Действия" пункт "Снять срочность" виден только у срочного обращения и сразу исчезает после выбора — и в отдельной карточке, и при открытии из реестра».
**Проверяет:** `setIncrementCode` и настройки `CodeMask`/`LastNumber` с `IsForceUpdate: false`; у мини-карточки нет `setIncrementCode` — агент вызывает сервис сам; правило `REQUIRED` по флажку; пункт «Действий» через `Visible` + `bindTo` с признаком в карточке и в разделе (не через `getActions` с проверкой поля).
**Как проверить:** номера идут подряд с обеих карточек; обновление пакета не сбрасывает счётчик; пункт появляется и исчезает без перезагрузки в обоих режимах.

## 3. Несколько событий объекта и слушатель — M

Отдельным слушателем: при смене Типа в историю (новый объект {P}TicketHistory с деталью на карточке только для просмотра, новые сверху) пишется старый и новый тип».

**Как проверить:** вкладка «События» — каждый старт и скрипт внутри своей рамки; все три сценария и история; компиляция без ошибок.

## 4. Процесс с CRUD, фильтрами и проверкой «запись найдена» — L
**Зависит от:** 1.
**Формулировка для агента:** «Процесс {P}ProcTicketCheck с входом "Тема обращения": находит обращение по теме; если не найдено — завершается с текстом итога "Не найдено"; если найдено и оно срочное — ставит Срок = сейчас + 1 день; иначе удаляет у ответственного его задачи старше 14 дней в любом статусе, кроме "Выполнена"; в конце формула собирает текст итога в выходной параметр».
**Проверяет:** чек-лист и `check-process.js`; проверка «найдено» по `ResultCount` в режиме Count (не в режиме «первая запись»); ссылка на параметр в `dataSourceFilters` объектом; `comparisonType` 5 (меньше) и 4 (не равно); подписи колонок у «Читать данные» в обоих языках; формула заголовка экземпляра; целые координаты.
**Как проверить:** три запуска — несуществующая тема, срочное, обычное с старыми задачами; дизайнер открывает все элементы; «Обновить из файловой системы» без ошибок.

## 5. Сценарий, метод процесса и запуск из REST — M
**Зависит от:** 4.
**Формулировка для агента:** «В процессе из задачи 4 вынеси сборку текста итога в метод процесса, который вызывается из задания-сценария; добавь REST-метод {P}TicketService.Check(тема), который запускает процесс и возвращает его итог; добавь в раздел "Обращения" кнопку "Проверить", которая вызывает этот метод для выбранного обращения и показывает итог».
**Проверяет:** сценарий не обращается к элементам по имени — значения через параметры процесса и `Get<T>`; `Execute<string>(процесс, выходной параметр, входы)`; у процесса есть простой старт; метод сервиса для `ServiceHelper.callService` — `POST` с ответом `{<Метод>Result}`.
**Как проверить:** кнопка показывает тот же итог, что запуск процесса; компиляция без ошибок; `Request.log` — POST со статусом 200.

## 6. Сигналы, задача и привязка процесса — M
**Зависит от:** 1.
**Формулировка для агента:** «Когда обращение становится срочным, ответственному ставится задача "Срочное обращение <Тема>" через элемент "Выполнить задачу" со сроком 4 часа, процесс ждёт её выполнения и затем пишет комментарий в историю; экземпляр привязан к обращению. Кроме того, процесс бросает сигнал {P}TicketUrgent, а отдельный процесс по этому сигналу пишет в журнал строку с Id обращения».
**Проверяет:** стартовый сигнал объекта с фильтром «логическое = да»; шаблон «Выполнить задачу» (`activity-task.json`, на проекте без образцов ещё 🧪); «Связать объект с процессом»; произвольный сигнал не передаёт данные — агент должен сам предложить передать Id иначе (подпроцесс или запуск с параметром, у вызываемого — простой старт), а не обещать Id через сигнал.
**Как проверить:** задача, ожидание, комментарий после выполнения; в журнале — реальный Id; экземпляр на вкладке процессов обращения.

## 8. Своё действие процесса и проверка процессом-скриптом — M
**Зависит от:** 1.
**Формулировка для агента:** «Сделай действие процесса "Часы до срока" (вход — Id обращения, выход HoursLeft — число рабочих часов до срока без выходных) и процесс "Проверка сроков" по таймеру каждый будний день в 10:00 и вручную: для каждого незакрытого обращения со сроком считает часы этим действием и, если их меньше 8, ставит "Срочное"».

## 9. Ошибка после сдачи — исправление без нового плана — S
**Зависит от:** 4.
**Подготовка (делаешь сам, не агент):** в `metadata.json` процесса из задачи 4 поменяй у одной связи `CI11` на дробное значение (например `…;199.5`) и нажми «Обновить из файловой системы» — получишь ошибку.
**Формулировка для агента (в новом чате):** «После обновления из файловой системы ошибка в процессе {P}ProcTicketCheck: The input string '' was not in a correct format».
**Проверяет:** агент читает журнал, находит причину, исправляет сразу без нового плана (объём задачи не меняется) и запускает `check-process.js`.
**Как проверить:** в чате нет «Подтверждаете план?»; обновление без ошибок; в логе — запуск скрипта после правки.

## 10. Полная уборка — L

**Формулировка для агента:** «Удали всё, что создано в задачах 1–9, включая пакет {P}Package: схемы, ресурсы, данные, SQL-скрипты, регистрацию, процессы, действие. Перед удалением проверь ссылки и покажи, что останется в БД; данные в БД удаляй SQL».
**Проверяет:** удаление с проверкой ссылок; в Cursor — удаление командой `rm` внутри Pkg после согласия (встроенный инструмент удаления не работает); SQL для данных и регистрации; выключение процесса с таймером.
**Как проверить:** «Обновить из файловой системы» без ошибок; раздела, справочника и процессов нет; в `SysSchema` нет `{P}%`.
