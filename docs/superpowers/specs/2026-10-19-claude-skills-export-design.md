# Экспорт скиллов Claude Code в проект стенда — дизайн

Дата: 19.10.2026

## Зачем

Разработчики и аналитики работают со стендом BPMSoft не только через приложение bpmsoft-agent, но и в Claude Code, открытом в корне стенда. Сейчас там нет ни правил работы, ни базы знаний агента — Claude Code изобретает metadata и не знает, где логи и что можно править. Нужно, чтобы те же знания и порядок работы, что у агента приложения, были доступны в Claude Code: приложение по кнопке устанавливает в корень стенда папку `.claude/` со скиллами, пользователь архивирует её и раздаёт коллегам.

С чем приходят в Claude Code:
1. **Сделать задачу** — создать или изменить схемы в `Pkg`.
2. **Уточнить текущий функционал** — объяснить, как устроено сейчас, без правок. Для аналитиков ответ — языком функционала («при сохранении заявки проверяется…»), а не именами схем и UId.
3. **Разобрать ошибку и починить** — стенд не запускается (причина в `[app]/Logs`), ошибка в консоли браузера (пользователь присылает текст или скриншот), ошибка компиляции или обновления из файловой системы.

## Цели

- Кнопка в приложении записывает в `<корень стенда>/.claude/` набор скиллов и `CLAUDE.md`, собранные из текущих знаний и правил агента.
- Повторное нажатие обновляет установленное; приложение показывает статус: не установлены / установлены (версия) / есть обновление.
- Папка самодостаточна: её можно заархивировать и передать — без ссылок на репозиторий, приложение и абсолютные пути; работает на macOS и Windows (нужен только `node` для скриптов проверки).

## Не цели

- Инструменты приложения в Claude Code не переносим: БД, «Обновить из файловой системы», компиляцию, браузер CRM. Claude Code просит пользователя: даёт готовый SQL и ждёт результат; просит обновить, скомпилировать и проверить в CRM.
- Синхронизация у коллег — нет; обновление = новая установка и новый архив.
- Отдельный CLI-генератор — не сейчас (логика пишется так, чтобы его можно было добавить).
- Правка `.cursorrules` и других файлов стенда вне `.claude/` (кроме случая с `CLAUDE.md` ниже) — нет.

## Анти-цели (провал, даже если «работает»)

- Установка затирает чужое: `settings.local.json`, скиллы пользователя, его собственный `CLAUDE.md`.
- Копия знаний в стенде расходится с репозиторием без способа это заметить.
- В раздаваемой папке есть что-то из личного окружения (пути, ключи, адрес CRM, имена из настроек приложения).
- Скиллы ссылаются на инструменты, которых в Claude Code нет (`pkg_lint`, `crm_db_query`, `crm_browser_*`, блоки `<choices>`), без замены.

## Решено с пользователем

- БД — Claude Code просит пользователя выполнить SQL.
- Знания — копируются в `.claude/` (не симлинк, не ссылка на репо).
- Скиллы — три верхних (разработка, разбор функционала, разбор ошибок) и подскиллы по типам схем.
- Раздача — пользователь сам архивирует `.claude/` и отправляет коллегам.
- Генерация — из приложения, кнопкой в меню «Настройки», отдельным блоком «Claude Code».
- Перезапись — только файлы, которые создало приложение.

## Устройство

### Что получается в стенде

```
<стенд>/
  CLAUDE.md                      ← общее ядро (см. ниже); только если CLAUDE.md нет или он наш
  .claude/
    settings.local.json          ← пользователя, не трогаем
    skills/
      bpm-develop/SKILL.md       ← «сделай задачу»
      bpm-explain/SKILL.md       ← «как сейчас работает»
      bpm-troubleshoot/SKILL.md  ← «стенд не стартует / ошибка в консоли / ошибка компиляции»
      bpm-entity/SKILL.md        ← подскиллы по типам схем
      bpm-client-schemas/SKILL.md
      bpm-process/SKILL.md
      bpm-user-task/SKILL.md
      bpm-source-code/SKILL.md
      bpm-data/SKILL.md
      bpm-sql-script/SKILL.md
      bpm-registration/SKILL.md
      bpm-knowledge/             ← копия packages/agent-runtime/knowledge как есть
        *.md, scripts/, templates/
        scripts/pkg-lint.js      ← автономная сборка pkg_lint (см. ниже)
      .bpmsoft-agent.json        ← манифест установки (.claude/skills/.bpmsoft-agent.json)
```

Все файлы знаний лежат плоско в одном `bpm-knowledge/`, а не разложены по подскиллам: знания ссылаются друг на друга по имени файла (`metadata-editing.md`, `templates/README.md`), раскладка сломала бы ссылки. Подскиллы — короткие `SKILL.md`: когда срабатывать, какие файлы `../bpm-knowledge/` читать и в каком порядке, какой скрипт проверки запускать после записи.

### Общее ядро — `CLAUDE.md` в корне стенда

Выжимка постоянных правил из `systemPrompt.ts`, которые нужны в любом скилле:
- карта папок: `BPMSoft.Configuration/Pkg` — единственное место правок; только чтение — `Autogenerated`, `Resources`, `conf/content`, `ResourcesCore` (если есть на стенде — декомпилированный .NET), `BPMSoft.*.xml`; `Logs/<ГГГГ-ММ-ДД>/` — журналы (UTC);
- главное правило metadata (✅ используй, 🧪 и UId проекта — точечный поиск), правило для C#;
- ресурсы ru-RU и en-US, `ModifiedOnUtc` — реальное время, префикс и стиль соседних схем;
- секреты не читать (`ConnectionStrings.config`, ключи, сертификаты);
- git — только чтение и откат своих правок по согласованию;
- БД, обновление, компиляция, проверка в CRM — делает пользователь по просьбе Claude;
- блок «Наблюдения для базы знаний» в конце задачи, если узнал новое (как в промпте; приложение его не собирает — пользователь переносит вручную);
- список скиллов и когда какой.

Причина, почему ядро в `CLAUDE.md`, а не в скилле: эти правила должны действовать всегда, а скилл загружается только при срабатывании.

### Верхние скиллы

- **bpm-develop** — порядок из промпта: пакет → требования (вопросы через встроенный инструмент вопросов Claude Code вместо `<choices>`) → исследование (подскилл по типу схемы) → план с AC/CC/DoD и «Не делаем» → стоп до подтверждения → запись → перечитать → `node .claude/skills/bpm-knowledge/scripts/pkg-lint.js` → git status → итог с шагами проверки для пользователя. Исключение «исправление только что сделанного» — как в промпте.
- **bpm-explain** — без пакета, плана и правок. Сначала знания, затем Pkg/Autogenerated/conf. Ответ языком функционала; имена схем и файлов — в конце отдельным списком «где это в коде». Если нужны данные из БД — предложить SQL пользователю.
- **bpm-troubleshoot** — три входа:
  - стенд не стартует / ошибка обновления или компиляции: последняя папка `Logs/<дата>/` → `Error.log`, `PackagesSynchronization.log`, `Common.log` (и `BusinessProcess.log`, `Scheduler.log` по ситуации), читать с конца, сопоставлять по времени UTC; найти схему-виновника в Pkg;
  - ошибка консоли браузера (текст или скриншот от пользователя): по стеку найти клиентскую схему (Pkg, затем `conf/content`, `Resources`), собрать иерархию скриптом `hierarchy.js`;
  - ошибка в работе процесса или серверной логики: `BusinessProcess.log`, `Error.log`, затем схема.
  Далее — причина, исправление по правилам bpm-develop (своя только что сделанная правка — сразу; иначе — план и стоп), шаги проверки для пользователя.

### Подскиллы

По одному на тип: entity, client-schemas, process, user-task, source-code, data, sql-script, registration. Источник содержимого — строки индекса знаний в `systemPrompt.ts` (что в файле фактов, что в рецептах, обязательные шаги вроде скрипта иерархии и проверок). `browser-check.md`, `metadata-editing.md`, `metadata-codes.md`, `platform-api.md` подскиллов не получают: на них ссылаются верхние скиллы и подскиллы.

### Проверка после записи — автономный `pkg-lint.js`

В приложении `pkg_lint` делает больше, чем `check-entity.js`/`check-process.js`: проверяет JSON, ресурсы в двух языках, SQL-скрипты, скобки в C#. В Claude Code нужна та же проверка, поэтому из `packages/agent-runtime/src/lint` собирается один автономный JS-файл (без зависимостей, только `node`), который кладётся в `bpm-knowledge/scripts/pkg-lint.js`. Сборка — часть обычного `npm run build` в `packages/agent-runtime`, чтобы кнопка работала и в dev-режиме. Вход — явные пути схем или пакета (основной режим: Claude передаёт папки схем, которые менял), либо «изменённые по git status», если Pkg — git-репозиторий. Формат вывода — как у `pkg_lint` (ОШИБКА / ВНИМАНИЕ).

Запасные пути описываются в `CLAUDE.md` ядра: нет git — список изменённых схем Claude ведёт сам и передаёт пути в `pkg-lint.js`, шаг git status пропускается; нет `node` — Claude сообщает пользователю, что автоматическая проверка недоступна, и перечитывает файлы сам по чек-листам из знаний.

### Источник текстов скиллов в репозитории

Тексты `CLAUDE.md` и `SKILL.md` — отдельные файлы в `packages/agent-runtime/claude-export/` (markdown, обезличенные, как знания). Это не генерация из строки промпта: промпт завязан на инструменты приложения, дословная копия была бы неверной. Чтобы не разойтись — правило в `CLAUDE.md` репозитория: меняешь порядок работы или правила в `systemPrompt.ts` — проверь `claude-export/`. Знания копируются как есть.

### Логика установки — `agent-runtime`

Функция вроде `installClaudeSkills(appRoot, { knowledgeDir, exportDir, appVersion })` и `claudeSkillsStatus(appRoot)`:
- пишет `bpm-*` в `.claude/skills/`, включая `bpm-knowledge/`; всё, что удаляется или перезаписывается, определяется только манифестом — посторонние файлы, в том числе положенные пользователем внутрь `bpm-*` и `bpm-knowledge/`, не трогаются (никакого удаления папки целиком);
- `CLAUDE.md` в корне: нет — пишет; есть и содержит метку приложения (например, первая строка `<!-- bpmsoft-agent: generated -->`) — перезаписывает; есть без метки — не трогает и возвращает «конфликт», UI спрашивает пользователя: «Записать ядро отдельно и подключить» (рекомендуемый: ядро — в `.claude/bpmsoft-agent.md`, файл в манифесте; в чужой `CLAUDE.md` один раз дописывается строка-импорт `@.claude/bpmsoft-agent.md`, если такой строки ещё нет — это единственная правка чужого файла, и только с согласия) / «Заменить мой CLAUDE.md» / «Отмена». Выбор запоминается в манифесте, при обновлении не спрашивается повторно;
- манифест `.claude/skills/.bpmsoft-agent.json`: версия приложения, дата установки, общий хэш устанавливаемого содержимого (считается по источнику — тому, что приложение собирается записать) и список записанных файлов с хэшем каждого; удалённые из новой версии файлы, которые есть в старом манифесте, удаляются; файлы не из манифеста не трогаются;
- файлы из манифеста, которые пользователь изменил на диске (хэш на диске не совпадает с хэшем в манифесте), перед перезаписью показываются списком, и установка ждёт подтверждения;
- статус: нет манифеста → «не установлены»; общий хэш манифеста совпадает с хэшем текущего источника → «установлены (<дата установки>, версия приложения)»; не совпадает — даже при той же версии приложения → «есть обновление»;
- запись с сохранением переводов строк не требуется (файлы наши), пути — через `path.join`.

### UI

В меню «Настройки» новый блок «Claude Code»: строка статуса и кнопка «Установить скиллы в проект» / «Обновить скиллы». Без открытого проекта — кнопка неактивна с подсказкой «Откройте проект». После установки — заметка «Готово: <путь>/.claude. Чтобы передать коллегам, заархивируйте папку .claude и CLAUDE.md». IPC — по образцу существующих `settings:*` / `db:*` в `apps/desktop/src/main/index.ts`. Упаковка приложения должна включать `claude-export/` так же, как `knowledge/`.

## Ограничения

- Кроссплатформенность по правилам репозитория: `path.join`, без `shell: true`, CRLF/BOM в знаниях не ломаются (копируются байт-в-байт).
- Обезличенность: тексты в `claude-export/` и собранная папка не содержат имён проекта, путей и данных стенда.
- В раздаваемой папке нет ничего из настроек приложения (адрес CRM, пользователь, ключи).
- Тест в `agent-runtime` проверяет источник `claude-export/`: нет абсолютных путей (`/Users/`, `C:\`, `~/`), нет имён инструментов приложения (`pkg_lint` как инструмент, `crm_db_query`, `crm_update_from_fs`, `crm_compile`, `crm_browser_`, `<choices>`). Знания копируются как есть: в них имя `pkg_lint` встречается, ядро `CLAUDE.md` объясняет его замену на `pkg-lint.js`. Имена проекта в репозитории не хранятся, их проверяют вручную перед коммитом, как для знаний.

## Оставлено на усмотрение исполнителя

- Точные тексты `SKILL.md` (description каждого скилла стоит прогнать через skill-creator / writing-skills на типичных запросах: «добавь колонку», «почему не стартует стенд», «как работает согласование»).
- Чем собирать `pkg-lint.js` (esbuild или tsc + ручная обвязка) и как он получает список изменённых файлов без git.
- Вёрстка блока в настройках.
- Тесты: установка в пустую папку, повторная установка, чужой `CLAUDE.md`, удаление файла из новой версии.
