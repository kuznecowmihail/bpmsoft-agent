# История чатов в desktop-приложении — проект решения

Дата: 2026-10-19 · Статус: черновик на согласование

## Зачем

Пользователь работает с агентом над задачей, случайно перезапускает приложение (или оно падает) — и вся переписка пропадает: агент начинает с нуля, хотя на половине пути уже многое выяснено и сделано. Нужно, чтобы после перезапуска можно было открыть прерванный чат и продолжить с того же места: агент помнит весь прежний диалог (свои вопросы, ответы пользователя, что правил и что запускал), а пользователь видит прежнюю ленту сообщений.

Образец — боковая панель чатов в современных агентах (Claude, Cursor, ChatGPT): список слева, клик открывает чат, можно писать дальше.

## Цели

- Панель слева со списком чатов **текущего стенда** (открытого проекта, папки `Pkg`), новые сверху.
- Открытие чата из списка: восстанавливается лента сообщений, а следующее сообщение продолжает тот же диалог с полным контекстом агента.
- У каждого чата в списке видно, на каком провайдере он идёт (Claude или Cursor).
- При открытии чата приложение само переключается на провайдера и модель этого чата.
- Кнопка «Новый чат» над списком; текущий чат при этом остаётся в списке.

## Не цели (сейчас)

- Поиск по чатам, переименование, удаление, закрепление.
- Чаты других стендов в панели.
- Продолжение чата на другом провайдере или другом стенде.
- «Начать новый чат со сводкой старого», когда сессия провайдера потеряна.
- Восстановление прерванного посреди работы хода (агент работал в момент перезапуска). Основной сценарий — агент закончил ход и ждал сообщения пользователя.

## Анти-цели (провал, даже если «работает»)

- Открытый старый чат выглядит восстановленным, но агент на самом деле начинает с нуля (контекст не подхватился) и пользователь этого не видит.
- Сообщение в старом чате случайно уходит в новую сессию или в чужой чат.
- Открытие старого чата меняет файлы в `Pkg` или что-то запускает на стенде.
- Панель тормозит или ломается из-за большого числа/размера логов.

## Что есть сейчас (исходные данные)

- Логи чатов: `apps/desktop/src/main/chatLog.ts`. Папка логов — `resolveChatLogDir()` в `apps/desktop/src/main/index.ts`: на macOS `~/Library/Logs/bpmsoft-agent`, на других ОС `<userData>/logs`. На каждый чат — пара файлов `chats/<YYYY-MM-DD>/<HH-MM-SS>.jsonl` и `.md`.
- Записи `.jsonl` (по одной на строку, поле `kind`): `chat_start` (`projectPath`, `readRoot`), `user_message` (`text` — текст пользователя без служебной пометки о «Стоп», `provider`, `model`, `resume`, флаги инструментов), `agent_event` (`event` — тот же `AgentEvent`, что получает интерфейс; в `system_init` и `result` есть `sessionId`), `permission_request`/`permission_response`, `db_query`, `crm_action`, `crm_browser`, `stop_request`, `stop_timeout`, `error`, `turn_end` (`sessionId`, `stopped`).
- Ограничения лога: строки длиннее 20 000 символов обрезаны, base64 картинок заменён пометкой (`truncateDeep`). Для показа ленты это годится, для восстановления контекста модели — нет.
- Продолжение диалога уже есть внутри одного запуска: `agentSession.ts` хранит `currentSessionId`, `currentSessionProject`, `currentSessionProvider`, `currentChatStartedAt`, `lastTurnStopped` и передаёт `resume: currentSessionId` в оба провайдера (Claude Agent SDK — `resume`, Cursor SDK — `Agent.resume(agentId)`). Сброс — `resetAgentSession()` («Новый чат», смена провайдера, смена проекта).
- `currentChatStartedAt` влияет на поведение агента: от него считаются «свои» изменённые схемы и проверка `pkg_lint` (`chatSince`).
- Интерфейс: `apps/desktop/src/renderer/src/App.tsx` строит ленту из `AgentEvent` через `mapAgentEventToEntry` (`chatFormat.ts`); сообщения пользователя добавляются в ленту самим `App` при отправке.
- Стенд выбирается на стартовом экране (список недавних проектов); «текущий стенд» = открытый проект (`projectPath`).

## Решение

### 1. Контекст агента берётся из сессии провайдера, а не из лога

При открытии чата приложение восстанавливает в `agentSession.ts` состояние сессии этого чата: `sessionId` (последний известный из `system_init`/`result`/`turn_end`), проект, провайдер, `currentChatStartedAt` = время `chat_start` чата, `lastTurnStopped` = был ли последний ход остановлен. Следующее сообщение уходит с `resume: sessionId` — модель получает настоящую историю провайдера (с вызовами инструментов и их результатами).

Лог используется только для показа ленты в интерфейсе.

### 2. Индекс чатов

Список чатов не собирается каждый раз разбором всех логов. Приложение ведёт небольшой индекс (файл в папке данных приложения, рядом с `settings.json`), по записи на чат:

- id чата (стабильный, например путь лога относительно папки логов);
- стенд (`projectPath`);
- провайдер и модель (последние использованные);
- `sessionId` провайдера (последний известный);
- название — начало первого сообщения пользователя (одна строка, обрезанная);
- время создания и время последнего сообщения;
- путь к `.jsonl`.

Индекс обновляется в тех же местах, где пишется лог: создание чата, первое сообщение (название), получение `sessionId`, конец хода. Чтение ленты — из `.jsonl` по пути из индекса.

Существующие логи (до появления функции): при первом запуске после обновления индекс один раз дозаполняется сканированием `chats/**/*.jsonl` — берутся `chat_start`, первый `user_message`, последний `sessionId`. Решение исполнителя: делать ли это (рекомендуется — сразу появится история).

### 3. Продолжение записи в тот же лог

Открытый старый чат продолжает писать в свой же `.jsonl`/`.md`, а не создаёт новую пару файлов. Сейчас `startChatLogIfNeeded` всегда создаёт новый файл, а `endChatLog` сбрасывает текущий — нужен способ «переоткрыть» существующий лог.

### 4. Панель слева

- Только чаты текущего стенда, сортировка по времени последнего сообщения, новые сверху.
- Элемент списка: название, дата/время, значок провайдера (Claude / Cursor).
- Сверху — кнопка «Новый чат» (сейчас она в шапке; перенести или продублировать — решение исполнителя).
- Текущий открытый чат подсвечен. Новый чат появляется в списке после первого отправленного сообщения.
- Пока агент работает (`isRunning`), переключать чаты и создавать новый нельзя (как сейчас с «Новым чатом» и сменой провайдера).
- Панель можно свернуть (решение исполнителя; по умолчанию открыта).
- При запуске приложения и открытии стенда открывается пустой новый чат (как сейчас); прерванный чат — первый в списке.

### 5. Открытие чата из списка

1. Main-процесс читает `.jsonl` и отдаёт в интерфейс последовательность для ленты: сообщения пользователя (из `user_message.text`) и события агента (из `agent_event.event`) в исходном порядке. Интерфейс строит ленту теми же функциями, что и в живом чате (`mapAgentEventToEntry`). Запросы разрешений из прошлого показываются как уже решённые или не показываются — без активных кнопок.
2. Если провайдер или модель чата отличаются от текущих настроек — приложение переключает настройки на провайдера и модель чата. Важно: сейчас `settings:setProvider` вызывает `resetAgentSession()`, поэтому переключение настроек должно произойти до восстановления состояния сессии, либо восстановление должно идти отдельным путём без сброса.
   - Если у провайдера чата нет ключа — настройки **не** переключаются (иначе сломаются и новые чаты), чат открывается только для чтения (раздел 6).
   - Если модели чата больше нет в списке моделей провайдера — переключается только провайдер, модель остаётся текущей выбранной для этого провайдера; в ленте — короткая пометка об этом.
3. Восстанавливается состояние сессии (раздел 1) и переоткрывается лог (раздел 3).
4. Пользователь пишет сообщение — оно уходит с `resume`.

### 6. Когда продолжить нельзя

Продолжение невозможно, если:

- в логе нет `sessionId` (ход оборвался до `system_init`);
- провайдер чата недоступен (нет ключа);
- провайдер не нашёл сессию при `resume` (сессия удалена/истекла).

Первые два случая видны заранее: чат открывается только для чтения — лента видна, поле ввода заменено пометкой «Этот чат нельзя продолжить: <причина>. Начните новый чат». Третий выясняется только при отправке: ошибка провайдера показывается в ленте как обычная ошибка хода, с той же подсказкой начать новый чат.

Где хранятся сессии провайдеров:

- Claude Agent SDK — в `~/.claude/projects/<cwd>/<sessionId>.jsonl` (на Windows — `%USERPROFILE%\.claude\...`); живут, пока пользователь их не удалит.
- Cursor SDK (локальный агент, `Agent.resume`) — **не проверено**, где и сколько хранится состояние агента и переживает ли оно перезапуск приложения. Проверить первым шагом реализации.
- Защита от «тихой подмены» (анти-цель 1): если `resume` вернул агента/сессию с другим id, чем запрошенный (провайдер молча начал новую сессию), — считать контекст потерянным: показать в ленте ошибку «контекст чата не восстановлен, начните новый чат» и не продолжать в этом чате. Если для Cursor такую подмену обнаружить нельзя или сессия не переживает перезапуск — Cursor-чаты из прошлых запусков приложения открываются только для чтения, и это честно показано в интерфейсе.

### 7. Оборванный ход (защита на будущее)

Если последний ход чата не закончился (`user_message` без `turn_end`, или `turn_end` со `stopped: true`) — при продолжении первое сообщение получает служебную пометку, как сейчас после «Стоп» (`STOPPED_TURN_NOTE`, через `lastTurnStopped`). Для оборванного перезапуском хода текст пометки другой: «предыдущий ход прервался (перезапуск приложения); перед продолжением проверь, что успел сделать». Не основной сценарий, но дёшево.

## Ограничения

- Кроссплатформенность (CLAUDE.md): пути только через `path.join`, без `~`/`$HOME`; папка логов разная на macOS и Windows (см. `resolveChatLogDir`). Значок провайдера и панель — без зависимостей от ОС.
- Логи пишет само приложение (без CRLF/BOM), но чтение `.jsonl` должно пропускать битые/недописанные строки (последняя строка могла оборваться при падении).
- Большие логи (сотни КБ – единицы МБ): чтение ленты не должно блокировать интерфейс; список строится только из индекса.
- Папка логов — пользовательская, её могут почистить. Если `.jsonl` из индекса пропал — запись убирается из списка (или помечается), приложение не падает.
- Ничего из открытия чата не трогает стенд: никаких вызовов агента, CRM, БД до явного сообщения пользователя.
- Эвалы не нужны (меняется приложение, не поведение агента), кроме случая, если меняется текст служебной пометки — она уходит в промпт.

## Решения пользователя

- Главный сценарий — продолжить работу после случайного перезапуска; агент в тот момент ждал сообщения.
- В панели — только чаты текущего стенда.
- При открытии чата провайдер и модель переключаются на те, что были в чате.
- У чата в списке подсвечен провайдер.

## Решения автора документа (можно оспорить)

- Отдельный индекс чатов вместо сканирования логов при каждом показе.
- Контекст модели — через `resume` провайдера, лог — только для ленты.
- Старый чат дописывает свой же лог.
- При запуске открывается новый пустой чат, а не последний.
- Чат без `sessionId` или без ключа провайдера — только для чтения; настройки провайдера при этом не переключаются.
- Модели чата больше нет — переключается только провайдер.
- Подмена сессии при `resume` (другой id) — контекст считается потерянным; если для Cursor это не обнаружить — его чаты из прошлых запусков только для чтения.
- Отложено: поиск, переименование, удаление, сводка в новый чат.

## Оставлено исполнителю

- Формат и имя файла индекса, стабильный id чата.
- Дозаполнение индекса из старых логов.
- Размещение кнопки «Новый чат» и сворачивание панели.
- Как показывать в восстановленной ленте прошлые запросы разрешений и запросы к БД/CRM.
- Новые IPC-каналы и разбиение кода по модулям (`chatLog.ts`, `agentSession.ts`, новый модуль индекса).
- Тесты: разбор `.jsonl` в ленту (включая битую последнюю строку), обновление индекса, восстановление состояния сессии — по образцу `apps/desktop/test/chatLog.test.ts`.
