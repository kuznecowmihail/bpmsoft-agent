# Цепочка «задача из Jira → агент → ветка и MR»

Дата: 2026-10-29. Статус: этапы 1–4 реализованы. Проверка на реальных системах — сценарий `docs/test-runs/run-16.md`; 🧪 — REST v2 Jira и Confluence на нашем экземпляре и ссылки между MR.

## Зачем

Сейчас разработчик пересказывает задачу агенту своими словами, а после проверки на стенде сам делает ветку, коммит и MR. Обе ручные части убираем кодом, порядок работы агента между ними не меняем:

1. **Вход.** Задача из Jira (описание, комментарии, ссылки, связанные страницы Confluence) попадает в контекст кодом, а не пересказом. Это вход шага «Требования»: если данных не хватает, агент всё равно спрашивает.
2. **Существующая цепочка** без изменений: пакет → требования → исследование → план и стоп → реализация → pkg_lint → проверка на стенде.
3. **Выход.** Ветка с ключом задачи, коммит только файлов задачи, push и MR — кодом, после подтверждения пользователя. Ссылки на MR — комментарием в задачу Jira.

Вне этой версии: чтение замечаний ревью из GitLab и правки по ним, режим без человека (headless-запуск по задаче).

## Решения

| Вопрос | Решение |
|---|---|
| Где работает | desktop-приложение и экспорт для Claude Code и Cursor; логика одна, в `agent-runtime` |
| Инструменты | в `agent-runtime`; desktop регистрирует их в провайдерах, экспорт — в MCP-сервере `bpmsoft`. Появляются, только если заданы настройки (как `crm_*`) |
| Внешние MCP Jira / Confluence / GitLab | не нужны. В экспорте не запрещены: если инструментов Jira в `bpmsoft` нет, скилл разрешает пользоваться подключённым у пользователя сервером |
| Кто создаёт MR | агент вызывает инструмент, приложение (или разрешения Claude Code / Cursor) просит подтверждение |
| Когда ветка | в конце, от текущего HEAD; в коммит — только файлы задачи, чужие незакоммиченные правки остаются в рабочей копии |
| Git или GitLab | по ответу сервера на push, а не по адресу remote (см. «Ветка и MR») |
| Токен GitLab | для создания MR не нужен: push с push-опциями под git-учёткой разработчика |
| Jira Cloud или Server/DC | оба: задан email — Basic с API-токеном (Cloud), нет — Bearer с personal access token (Server/DC) |
| Git обязателен? | нет. Без git цепочка работает до MR; `git_create_mr` прямо говорит, что MR не создать. pkg-lint без git ищет изменения по времени файлов |

## Настройки

Настройки Jira и Confluence в desktop общие для всех проектов (`StoredSettings`), токены — в secureStore; в экспорте — блоки `jira` и `confluence` в `.claude/bpmsoft-agent.local.json`, их пишет установка скиллов, как `crm` и `db`:

- `jira`: `url`, `email` (необязательно), токен; `acceptanceField` — id поля критериев приёмки (`customfield_…`, необязательно).
- `confluence`: `url` (у Cloud — с `/wiki`), `email`, токен. Если не задан, а Jira — Cloud того же сайта, берём учётку Jira.
- `git.targetBranch` — целевая ветка MR (`develop`, `release/…`, ветка спринта). Пусто — основная ветка remote (`git symbolic-ref refs/remotes/origin/HEAD`). Из Jira (спринт, fixVersion) ветку не выводим: соответствие у каждого проекта своё.

Токены в desktop — в `secureStore` (Electron `safeStorage`), в экспорте — только в файле доступов, который читает MCP-сервер. В настройках — кнопка «Проверить подключение» для Jira и Confluence.

## Инструменты

| Имя | Что делает | Подтверждение |
|---|---|---|
| `jira_get_issue(key)` | Markdown: ключ, тип, статус, заголовок, описание, поле критериев приёмки, метки, fixVersion, комментарии (автор, дата, текст), связанные задачи, вложения (имена), удалённые ссылки. Ссылки на страницы Confluence того же сайта — до 3 страниц текстом, каждая до 20 000 символов; не загрузилась — строка «не загружена: причина» | нет |
| `confluence_get_page(urlOrId)` | текст страницы (storage-формат → Markdown-подобный текст), заголовок, ссылка; до 40 000 символов | нет |
| `git_branch_status(key?)` | по каждому репозиторию из `findPkgGitRepos`: текущая ветка, целевая, сколько коммитов в текущей нет в целевой (список до 10) и на сколько она отстаёт; кандидаты на переключение. Перед этим `git fetch` с таймаутом; не прошёл — пометка «по данным последнего fetch» | нет |
| `git_switch_branch(repo, branch)` | переключает один репозиторий: локальная ветка — `git switch <ветка>`, только на remote — `git switch -c <ветка> --track origin/<ветка>`. Есть незакоммиченные правки в этом репозитории — не переключает, возвращает их список | да |
| `git_create_mr({ issueKey, title, paths, description })` | ветка, коммит, push, MR по каждому затронутому репозиторию (см. ниже) | да, карточка |
| `jira_add_comment(key, text)` | комментарий в задачу | да |

Jira — REST API v2 (`/rest/api/2/issue/{key}`, `/remotelink`, `/comment`): тот же путь у Cloud и Server/DC, описание приходит wiki-разметкой, а не ADF. Confluence — `/rest/api/content/{id}?expand=body.storage,version`. Оба пути 🧪 — проверить на этапе 0.

Все HTTP-запросы — с таймаутом (30 с), все вызовы git — через `execFile` без оболочки, с `GIT_TERMINAL_PROMPT=0` и таймаутом (fetch и push — 120 с), чтобы git не ждал ввода пароля.

## Вход: задача из Jira

- Desktop: кнопка «Взять задачу» → поле ключа (`PRJ-123` или ссылка) → код вызывает `jira_get_issue` и `git_branch_status` и начинает новый чат с сообщением «Задача из Jira» + оба результата. Ошибка загрузки — показываем причину (сеть, 401/403, нет задачи); пользователь может вставить текст задачи сам.
- Экспорт: пользователь пишет «возьми задачу PRJ-123», скилл `bpm-develop` вызывает те же два инструмента.
- Промпт (`systemPrompt.ts` и `claude-export`): если в начале чата задача из Jira — шаги 1–4 идут по ней, ключ запоминается; требования, которые в задаче не однозначны, всё равно спрашиваются.

## Проверка ветки

На старте задачи и повторно перед MR.

**На старте.** Если текущая ветка не целевая или в ней есть коммиты, которых нет в целевой, агент до вопросов по требованиям показывает это и останавливается блоком выбора:

- «Переключись в <кандидат>» — по варианту на кандидата, не больше трёх;
- «Работать от текущей»;
- «Переключусь сам».

Кандидаты считает `git_branch_status`, по порядку: ветки с ключом задачи в имени (локальные и на remote) → целевая ветка → недавно обновлённые ветки remote (`git for-each-ref --sort=-committerdate refs/remotes`), всего до 3. Рекомендуемый вариант: ветка с ключом задачи, если есть, иначе целевая.

На «Переключись»: `git_switch_branch` с подтверждением. После переключения файлы `Pkg` на стенде другие — агент предлагает «Обновить из файловой системы» и компиляцию существующим блоком выбора «Обновить CRM сейчас?». Незакоммиченные правки мешают — переключение не делается, агент показывает список файлов и предлагает «Переключусь сам».

**В плане** (шаг 4) — строка «Ветка: от `<текущая>`, MR в `<целевая>`, репозиториев N (`<список>`)»; при нескольких репозиториях — «будет N MR».

**Перед MR** — снова `git_branch_status`: пользователь мог переключиться по ходу работы. Расхождение попадает в карточку подтверждения.

## Ветка и MR: `git_create_mr`

Вход: `issueKey`, `title` (кратко, по-русски можно), `paths` — папки схем задачи (desktop: изменённые в чате схемы; экспорт: список, который агент ведёт по ходу задачи, как для pkg-lint без git), `description` — из плана шага 4: AC / CC / DoD, решения без вопроса, риски, результат pkg_lint и проверки на стенде.

1. `findPkgGitRepos(Pkg)` → изменённые файлы каждого репозитория; берём только лежащие внутри `paths` (папка схемы `Schemas/<Имя>` тянет за собой `Resources/<Имя>.*` того же пакета). Пакеты из `paths` вне git — в отчёт: «MR для них не создан, нет git».
2. Ничего не осталось — ошибка без побочных действий.
3. Карточка подтверждения: по каждому репозиторию — файлы, ветка `<KEY>-<кратко латиницей>`, текущая и целевая ветки, «в MR попадут ещё N коммитов, которых нет в целевой: <список>» (если есть), заголовок и текст MR.
4. По каждому репозиторию: `git switch -c <ветка>` от текущего HEAD (ветка уже есть и указывает на наш коммит — пропускаем шаги 4–5, повтор после сбоя push); `git add -- <файлы>`; `git commit -m "<KEY> <title>" -m "<description>"`.
5. `git push -u origin <ветка> -o merge_request.create -o merge_request.target=<целевая> -o "merge_request.title=<KEY> <title>"`. Push-опции не могут содержать перевод строки, поэтому полный текст MR идёт в тело коммита (🧪 этап 0: берёт ли его GitLab в описание MR, созданного push-опциями; если нет — необязательный токен GitLab и `PUT /projects/:id/merge_requests/:iid` для описания).
6. Ответ сервера:
   - есть ссылка на MR (`/-/merge_requests/<n>`) — MR создан;
   - git отказал до отправки: сервер не поддерживает push-опции — повторяем обычный `git push -u origin <ветка>`; ссылка на создание PR/MR из вывода сервера, если есть, — в отчёт: «ветка отправлена, MR создай вручную»;
   - иначе — «ветка отправлена, MR не создан» + вывод сервера.
7. Несколько MR — в отчёт и в комментарий Jira все ссылки; в каждый MR — ссылки на остальные (🧪 тем же способом, что описание).
8. Агент предлагает `jira_add_comment` со ссылками на MR (с подтверждением).
9. Доработка после MR: текущая ветка уже содержит ключ задачи — новая ветка не создаётся, коммит и push идут в неё, открытый MR получает коммит. Описание открытого MR инструмент не меняет.

После MR рабочая копия остаётся на новой ветке — это сказано в отчёте.

## Ошибки и недоступность

Каждый узел падает отдельно и не ломает цепочку.

| Где | Что видит пользователь | Что дальше |
|---|---|---|
| Jira при старте | причина: сеть, таймаут, 401/403, задачи нет | вставить текст задачи вручную; цепочка работает без Jira |
| Confluence | задача загружена, у страницы пометка «не загружена: причина» | агент спрашивает недостающее |
| `git fetch` | «сравнение по данным последнего fetch» | работа идёт |
| git не установлен | `git_*` возвращают «git не найден» | цепочка до MR; MR — вручную |
| Push (сеть, права, нет учётки) | локальные ветка и коммит есть, push не прошёл: причина | повторный `git_create_mr` находит ветку с коммитом и только отправляет |
| `jira_add_comment` | ссылки на MR уже в ответе агента, комментарий не добавлен | повторить вызов |
| Незакоммиченные правки при переключении | список файлов | «Переключусь сам» |

## Тесты

- `pkgGitRepos` (есть): расклады «репо = Pkg», «репо на пакет», смешанный, без git.
- Git-модуль на временных репозиториях с bare-remote (`file://`): `git_branch_status` (впереди, позади, кандидаты по ключу), `git_switch_branch` (локальная, только на remote, отказ при грязной копии), `git_create_mr`:
  - в коммит попадают только файлы из `paths` и их ресурсы;
  - повтор после сбоя push не создаёт второй коммит;
  - bare-remote с `receive.advertisePushOptions=true` получает опции (hook `pre-receive` пишет `GIT_PUSH_OPTION_*` в файл);
  - без этой настройки — повтор обычным push и отчёт «MR не создан».
- Jira и Confluence — на подменённом `fetch` (как `FetchLike` в `crmSession`): Basic против Bearer, разбор задачи v2, ссылки Confluence в описании, 401/404/таймаут → текст ошибки без токена.
- `claudeExportTexts.test.ts`: новые инструменты упомянуты в экспорте.
- Эвал: кейс «задача из Jira» с подменённым ответом Jira в раннере — агент задаёт вопросы только о том, чего нет в задаче; MR в эвале не создаётся.
