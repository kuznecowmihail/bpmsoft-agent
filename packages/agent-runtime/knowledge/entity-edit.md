# Объекты (EntitySchemaManager) — рецепты создания/редактирования

Общая механика diff-формата, штампов-полей и ресурсов — см. `metadata-editing.md`. Здесь — только рецепты, специфичные для объектов. Подробности значений полей — см. `entity.md`.

**Не забывай про 2 обязательных правила из `metadata-editing.md`: (1) обе локали `ru-RU`+`en-US` для ресурсов, (2) актуальный `ModifiedOnUtc` при каждом изменении `descriptor.json`.**

## ✅ Подтверждено экспериментом: добавить простую колонку (без lookup)
1. В `Schemas/<Объект>/metadata.json` добавить перед завершающим `~ MetaData.Schema.D2 [...]`:
```
+ MetaData.Schema.D2 {
  "UId": "<новый GUID>",
  "A2": "<ИмяКолонки>",
  "A3": "<UId объекта>",
  "A4": "<UId объекта>",
  "A5": "<любой существующий A5 из этого же файла>",
  "S2": "<GUID типа данных, см. таблицу в entity.md>"
}
```
2. Дописать `<новый GUID>` в конец списка `~ MetaData.Schema.D2 [...]`.
3. (Опционально, но рекомендуется) В `Resources/<Объект>.Entity/resource.ru-RU.xml` добавить `<Item Name="Columns.<ИмяКолонки>.Caption" Value="<Подпись>" />`.
4. Открыть объект в Designer и проверить, что колонка отображается без ошибок.

**Подтверждено на практике**: колонка `ManualWrite` (простой текст) успешно создана этим способом на тестовом объекте `TestEntity`, включая подпись — см. `entity.md`.

## ✅ Удалить объект (схему) целиком

**Подтверждено пользователем**: весь workflow разработки идёт через файловую систему — правики файлов, затем в самой BPMSoft-CRM нажимается кнопка "Обновить из файловой системы" (Update from file system), которая подхватывает изменения из `Pkg`.

**Для удаления схемы целиком достаточно:**

1. Удалить рекурсивно две папки:
   - `Pkg/<Пакет>/Schemas/<ИмяСхемы>/` (сама схема)
   - `Pkg/<Пакет>/Resources/<ИмяСхемы>.<Категория>/` (ресурсы, где категория — `.Entity` для объектов, `.Process` для процессов, `.ClientUnit` для клиентских юнитов, `.SourceCode` для исходного кода и т.д.)

2. Открыть BPMSoft-CRM и нажать "Обновить из файловой системы" (Update from file system)

3. Схема пропадает из runtime и больше недоступна в системе

**✅ Подтверждено массово 05.10.2026**: за одно «Обновить из файловой системы» удалены 25 схем разных типов — объект `TestProcEntity`, 23 процесса, действие процесса `TestUserTask`, преднастроенная страница `TestPreconfPage` — и SQL-скрипт; окно «Изменения» показало их со статусом «Удалено», компиляция без ошибок. Проверка без скриншотов — `[app]/Logs/<ГГГГ-ММ-ДД>/PackagesSynchronization.log`: по каждой удалённой схеме строка `Schema '<Имя>' not found in <ManagerName>` (это признак удаления, а не ошибка). Что стало с таблицей объекта и данными в БД — не проверялось.

**ПЕРЕД удалением проверить зависимости — ОБЯЗАТЕЛЬНЫЙ ШАГ БЕЗОПАСНОСТИ** (добавлено по прямому указанию пользователя как защита от случайной поломки связанных схем/данных)

4. **ОБЯЗАТЕЛЬНО проверь, не ссылаются ли на удаляемую схему другие схемы проекта**, иначе можно случайно сломать зависимые объекты/процессы/данные. Алгоритм проверки:

   1. Возьми `UId` удаляемой схемы (из её `descriptor.json` → `Descriptor.UId`) и её `Name`.
   
   2. Проверь ПО ВСЕМУ дереву `Pkg/**` (через `grep -r`), встречается ли этот `UId` в файлах ДРУГИХ схем — в частности:
      - `descriptor.json` → `Parent.UId` (кто-то наследует эту схему)
      - `metadata.json` поля `S4`/`ReferenceSchemaUId`/`FC2`/`EntitySchemaUId` (кто-то ссылается на неё как на lookup-цель или объект-триггер процесса)
      - `DependsOn` в `descriptor.json` других схем
   
   3. Также проверь встречается ли `Name` схемы как `Parent.Name`/`referenceSchemaName` в других файлах (менее надёжно, чем UId, но дополнительный сигнал).
   
   4. Если находятся совпадения (кроме самой удаляемой схемы) — **ОБЯЗАТЕЛЬНО предупреди пользователя ПЕРЕД удалением**: покажи, какие конкретно схемы ссылаются на удаляемую и как именно (lookup-колонка, наследование, триггер процесса и т.д.), и явно спроси подтверждение, действительно ли удалять — не удаляй молча.
   
   5. Если совпадений не найдено — можно удалять без дополнительного предупреждения (кроме обычного подтверждения самого действия удаления).

**Важно**: этот рецепт работает для ЛЮБОГО типа схемы (Entity, Process, ClientUnit, etc.), не только для объектов. Это подтверждено как правильный и универсальный способ удаления (не гипотеза).
