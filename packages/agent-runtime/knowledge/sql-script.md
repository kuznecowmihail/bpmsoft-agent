# SQL-скрипт пакета (SqlScript) — подтверждённая модель metadata

## ✅ ПОДТВЕРЖДЕНО: структура и формат descriptor.json и .sql-файла для SqlScript-схем

Собрано на сотнях реальных SQL-скриптов проекта и подтверждено перечислениями платформы BPMSoft (`DBEngineType`, `SysPackageSqlScriptInstallType`). Структура одна из самых простых среди всех типов схем.

## Общее

- `descriptor.json` → **ключевое отличие: корневой ключ называется `"SqlScript"`, А НЕ `"Descriptor"`** (единственный тип схем с таким исключением).
- Папка схемы содержит ТОЛЬКО 2 файла: `descriptor.json` + `<Name>.sql` (сырой SQL-текст). **НЕТ `properties.json`, НЕТ `metadata.json`, НЕТ отдельного `resources.json` с локализацией** — подтверждено сканированием всех 306 примеров проекта (ни у одного из них нет папки Resources с xml-ресурсами).
- Это самый простой тип схемы на платформе: минимум информации в descriptor, ничего в metadata, ничего в ресурсах.
- Тип схемы определяется её расположением в папке `SqlScripts/` пакета, а не полем в `descriptor.json`.

## `descriptor.json` — поля

**Структура (помни про ключ `SqlScript`, а не `Descriptor`):**

```json
{
  "SqlScript": {
    "UId": "5e89f02a-e17e-fa38-7161-f79f86dcffe8",
    "Name": "AdminUnitFeatureState_U_EnableThemeSwitcher",
    "DBEngineType": 2,
    "InstallType": 1,
    "ModifiedOnUtc": "\/Date(1781528034000)\/",
    "DependsOn": []
  }
}
```

**Поля:**

- `UId` — уникальный идентификатор SQL-скрипта (GUID).
- `Name` — техническое имя скрипта (совпадает с именем папки `SqlScripts/<Name>/`), никогда не должно содержать пробелы, только латиница/цифры/подчёркивание.
- `DBEngineType` — **ПОЛНОСТЬЮ ПОДТВЕРЖДЕНО** (enum платформы `BPMSoft.Common.DBEngineType`):
  - `0` = `MSSql` (Microsoft SQL Server)
  - `1` = `Oracle` (Oracle Database)
  - `2` = `PostgreSql` (PostgreSQL) — **самый частый случай на PostgreSQL-стендах**
  
  В большинстве проектов используется PostgreSql (`2`); `0` встречается редко (5 файлов — вероятно старые MSSql-скрипты, оставленные для совместимости).

- `InstallType` — **ПОЛНОСТЬЮ ПОДТВЕРЖДЕНО** (enum платформы `BPMSoft.Core.Packages.SysPackageSqlScriptInstallType`):
  - `0` = `BeforePackage` — выполняется ДО установки пакета (редко, встречается в менее 1% случаев)
  - `1` = `AfterPackage` — выполняется ПОСЛЕ установки пакета (самый частый случай, ~80%)
  - `2` = `AfterSchemaData` — выполняется после установки данных схемы пакета (~8%)
  - `3` = `UninstallApp` — выполняется при удалении приложения/пакета (редко, встретился только 1 раз)
  
  Распределение по частоте подтверждает: большинство SQL-скриптов пакета — это обычные пост-установочные миграции, фиксы данных, настройки после развёртывания пакета.

- `ModifiedOnUtc` — **ОБЯЗАТЕЛЬНО**: текущий момент времени в формате `"\/Date(<миллисекунды_с_эпохи_Unix>)\/"` (совпадает со временем создания/последней правки). Получить можно через `date +%s000` в shell. Никогда не использовать захардкоженные значения — это приводит к десинхронизации истории в системе.

- `DependsOn` — массив зависимостей от других SQL-скриптов (обычно пустой `[]` в подтверждённых примерах). Позволяет задать порядок выполнения скриптов друг относительно друга внутри одной стадии `InstallType`, но на примерах с непустым значением подтверждение не получено.

**ОТЛИЧИЕ от других типов схем: НЕТ полей `Caption`, НЕТ `ManagerName` — они не нужны для SQL-скриптов.**

## `.sql`-файл

Содержит сырой SQL-текст, выполняется как есть движком БД, указанным в `DBEngineType`.

**Особенности:**

- Файл содержит ТОЛЬКО SQL-команды (SELECT, UPDATE, INSERT, DELETE, CREATE, DROP, ALTER и т.д.), БЕЗ JSON-обёртки.
- Может быть однострочным или многострочным.
- Для PostgreSql (`DBEngineType: 2`) может содержать PL/pgSQL-блоки:
  ```sql
  DO $$ 
  BEGIN
    -- Ваш код на PL/pgSQL
    UPDATE table SET col = value WHERE condition;
  END;
  $$ LANGUAGE plpgsql;
  ```
- Для других движков (MSSql, Oracle) — соответствующий SQL-диалект.
- Пример реального содержимого (PostgreSql):
  ```sql
  UPDATE "AdminUnitFeatureState"
  SET "FeatureState" = 1
  WHERE "FeatureId" = (
      SELECT "Id" from "Feature" WHERE "Code" = 'EnableThemeSwitcher'
  )
  ```
- Скрипт выполняется в контексте БД пакета, имеет доступ ко всем таблицам и может создавать новые таблицы/индексы/функции/триггеры.

## Ресурсы

**✅ ЭТОТ ТИП СХЕМЫ НЕ ИМЕЕТ РЕСУРСОВ/ЛОКАЛИЗАЦИИ ВООБЩЕ.**

Подтверждено:
1. Сканированием всех SQL-скриптов реального проекта — ни у одного из них нет папки `Resources/<Name>.SqlScript/` или подобной структуры.
2. Логикой платформы — SQL-скрипт — это техническое, не локализуемое содержимое (как индексы, функции БД и т.д.). Не имеет `Caption`, нет пользовательского интерфейса, нет необходимости в многоязычности.
3. Структурой `descriptor.json` — отсутствие поля `Caption` или ссылок на ресурсы.

Значит, при создании или редактировании SQL-скрипта **НЕ НУЖНО создавать файлы `resource.ru-RU.xml` и `resource.en-US.xml`** — это ОТЛИЧИЕ от всех остальных типов схем (Entity, Process, SourceCode, ClientUnit).

## Не проверено пока

- Точный формат/назначение непустого `DependsOn` — единичный пример с непустым значением не встретился; неясно, задаёт ли это строгий порядок выполнения или просто логическую зависимость.
- Может ли одна папка `SqlScripts/<Name>/` содержать несколько `.sql`-файлов (вместо одного) — на примерах встречается только одна пара (descriptor + .sql на имя папки).
- Поведение скриптов с `InstallType: 0` (BeforePackage) — очень редко встречаются, точный механизм не подтверждён на примерах.

## ✅ Подтверждено записью 05.10.2026: когда выполняется скрипт
Новый скрипт с `InstallType: 1` выполняется при первом «Обновить из файловой системы»; повторно — только если изменён `ModifiedOnUtc` в `descriptor.json`. Обновления без изменений скрипт не запускают. Рецепт — `sql-script-edit.md`.
