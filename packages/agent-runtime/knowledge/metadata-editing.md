# Общая механика редактирования metadata.json (все типы схем)

## Статус подтверждения
Этот файл описывает механику формата, общую для схем на платформе BPMSoft. **ВАЖНО: не ВСЕ типы схем используют построчный diff-журнал.** Существует два основных формата хранения `metadata.json`:
- **Формат A (diff-журнал)**: используется Entity, большинством Process, ClientUnitSchema — каждое изменение записывается как отдельная строка с префиксом операции (`=`/`+`/`~`/`-`).
- **Формат B (плоский JSON-снимок)**: используется SourceCodeSchemaManager (см. `source-code.md`), некоторыми ProcessSchemaManager примерами, ClientUnitSchema примерами — весь файл это один JSON-объект `{"MetaData": {"Schema": {...}}}` без построчных операций.

**Как определить, какой формат используется**: откройте начало файла `metadata.json`. Если файл начинается с `{` и содержит структуру `{"MetaData": {"Schema": {...}}}` — это Формат B (плоский JSON). Если состоит из строк вида `= MetaData.Schema...`, `+ MetaData.Schema...`, `~ MetaData.Schema [...]` — это Формат A (diff-журнал). **Перед редактированием ЛЮБОЙ схемы сначала определи, с каким форматом имеешь дело**.

Подтверждено на `EntitySchemaManager` (см. `entity.md`/`entity-edit.md`) прямым экспериментом ЗАПИСИ; у `ClientUnitSchemaManager` (см. `client-schemas.md`) и у `ProcessSchemaManager` формат Формата A идентичен по всем прочитанным примерам, но ручная ЗАПИСЬ там ещё не тестировалась. SourceCodeSchemaManager использует Формат B (см. `source-code.md`). Статус см. в таблице ниже и в соответствующих `-edit.md` файлах.

**✅ Формат B: `BL1` — первым полем каждого элемента** (05.10.2026, процесс `TestProcSrcCall`): элемент процесса, у которого `BL1` стоял после `A3`/`A4`/`A5`, не загрузился — «Обновить из файловой системы» показало у схемы «Добавлено/Ошибка: Value cannot be null. (Parameter 'key')», в `PackagesSynchronization.log` стек `FlowSchema.CreateFlowElement(String bpmnElementName)`. После перестановки (`BL1`, `UId`, `A2`, `A3`, `A4`, `A5`, затем остальные — как в реальных файлах) схема загрузилась и выполнилась. Платформа определяет тип элемента по `BL1` только если это первое поле объекта. Порядок остальных ключей держи как в реальных файлах; при генерации node-скриптом собирай объект в этом порядке, а не через `Object.assign({общие поля}, элемент)`.

## Формат diff-журнала (Формат A)
**Применяется только к схемам, использующим diff-журнал (EntitySchemaManager, большинство ProcessSchemaManager, ClientUnitSchemaManager). Для SourceCodeSchemaManager и других схем, использующих Формат B (плоский JSON), эти правила не применяются — см. соответствующие файлы (`source-code.md` и т.д.).**

- `=` — установить значение (или «без изменений относительно родителя/шаблона»).
- `+` — добавить новую запись/поле.
- `~` — заменить ЦЕЛИКОМ список (обычно массив UId дочерних записей) — этот список должен содержать ВСЕ актуальные UId после правки.
- `-` — удалить поле/запись.
- **Правило «последняя запись побеждает»**: в одном файле путь может встречаться НЕСКОЛЬКО раз (это не пакетные слои, а последовательные сохранения) — действующее значение определяется ПОСЛЕДНИМ по порядку в файле (сверху вниз), а не первым найденным совпадением. **Это правило относится ТОЛЬКО к Формату A (diff-журнал); Формат B (плоский JSON) не имеет этого механизма вообще**.

- ⚠️ **Многострочный блок** `+ <путь> {` закрывается строкой, где `}` стоит в начале строки, без отступа. ❌ Закрывающая `}` с отступом: блок молча не применяется — объект загружается без этих колонок и отображаемого значения, раздел падает (подтверждено в CRM, 09.10.2026). Проверка объекта — `scripts/check-entity.js` (`entity-edit.md`).

## Как добавить новую запись в массив (колонка/индекс/маппинг/элемент и т.д.)
1. Добавить `+ MetaData.Schema.<Путь> { ...новый объект... }` — обычно в конце соответствующей секции, перед завершающим `~`-списком этого же пути.
2. Найти завершающий `~ MetaData.Schema.<ТотЖеПуть> [...]` список этого же массива и ДОПИСАТЬ новый UId в конец.
3. Если такого `~ [...]` списка в файле ещё нет вообще (например массив был пустым) — Designer сам создаёт список при первом добавленном элементе (подтверждено на `D2`/`D6`); для РУЧНОЙ записи в изначально пустой массив это не проверено — безопаснее сначала протестировать на некритичной тестовой схеме.

## Обязательные поля-«штампы» на КАЖДОЙ записи
- `UId` — свежий, уникальный GUID (генерировать заново, никогда не переиспользовать существующие).
- `A2` — читаемое имя (Код) записи.
- `A3`/`A4` — UId схемы-владельца (той схемы, в которую входит запись) — ОБА поля равны `MetaData.Schema.UId` этой схемы, не UId самой записи.
- `A5` — UId «группы ревизии» — подтверждено сканированием (см. `entity.md`/`client-schemas.md`): группирует записи, изменённые в одном движении; НЕ обязан быть уникальным для новой записи — безопасно переиспользовать любой уже встречающийся в этом же файле `A5` (например тот, что стоит у соседних недавно добавленных записей).
- `B6` (только на уровне СХЕМЫ целиком, не отдельной записи) — UId ПАКЕТА, которому принадлежит схема — обязательно должен совпадать с `Pkg/<Пакет>/descriptor.json.UId`.
- `B8` (на уровне схемы) — версия BPMSoft — совпадает с `properties.json.CreatedInVersion`; для ручной правки безопасно оставить текущее значение как есть, не менять.
- `ModifiedOnUtc` (на уровне СХЕМЫ в `descriptor.json`) — **ОБЯЗАТЕЛЬНО** должно обновляться при любом создании новой схемы или изменении существующей на РЕАЛЬНЫЙ текущий момент времени в формате `"\/Date(<миллисекунды_с_эпохи_Unix>)\/"`. Получить актуальный timestamp можно через `date +%s000` в shell (миллисекунды с 01.01.1970 UTC). Никогда не использовать захардкоженные/произвольные даты — это приводит к десинхронизации истории изменений. Была ошибка при первом создании `TestCounterLookup`, где использовалась захардкоженная дата — правило добавлено по замечанию пользователя.
- Обновить `ModifiedOnUtc` в существующем `descriptor.json` — одной командой, без пересборки файла (BOM, отступы и остальные поля не меняются): `perl -pi -e 's/("ModifiedOnUtc": "\\\/Date\()\d+/${1}'"$(date +%s000)"'/' <папка схемы>/descriptor.json`. Не собирай `descriptor.json` через `JSON.stringify` с подстановкой строки `\/Date(…)\/` — получается двойной обратный слеш. После любой правки перечитай `descriptor.json` целиком: правка инструментом редактирования уже обрезала файл и теряла `DependsOn`.
- ⚠️ **Кириллица и perl** (✅ подтверждено в файле, 13.10.2026): `perl -CSD -pi -e` с русским текстом в коде (`-e` или подставленная переменная оболочки) кодирует его в UTF-8 второй раз — в `resource.ru-RU.xml` появляются кракозябры. Русский текст вставляй инструментом правки или через `node -e` с `fs.readFileSync(p, "utf8")` / `fs.writeFileSync(p, t, "utf8")`. 🧪 Вариант `perl -CSD -Mutf8` не проверялся.
- ⚠️ **Посторонние папки в Pkg ломают обновление** (✅ подтверждено логом PackagesSynchronization, 14.10.2026): любая папка не-схемы внутри `Pkg/<Пакет>/Schemas` или папки схемы (например скрытая служебная папка редактора или среды) останавливает «Обновить из файловой системы» с `InvalidDescriptorInFileSystemException: Название объекта "<имя>" некорректное`. Если обновление упало с этой ошибкой — найди и удали лишнюю папку, а сам ничего, кроме файлов схем и ресурсов, в пакете не создавай.
- BOM: `descriptor.json`, `metadata.json` и ресурсы часто начинаются с BOM (UTF-8). Читая их в node, убери `\uFEFF` перед `JSON.parse`, иначе разбор падает. BOM необязателен — в пакетах из Designer встречаются файлы и с ним, и без (у `descriptor.json` схем и SQL-скриптов тоже); при правке сохраняй как было и не переписывай файл ради BOM.

## Ресурсы (`resource.<culture>.xml`)
- Для КАЖДОГО культурного файла (`resource.ru-RU.xml`, `resource.en-US.xml`, ...) — добавить `<Item Name="<Путь>.Caption" Value="<Текст>" />` (или `LocalizableStrings.<Ключ>.Value` — см. по типу схемы) внутрь `<Items>`.
- Подтверждено экспериментом (`entity.md`): достаточно добавить ОДНУ культуру (например только `ru-RU`) — Designer не требует присутствия перевода во всех остальных культурных файлах, просто показывает пустое значение там, где перевода нет, без ошибки.
- **ВАЖНО (правило качества агента)**: при СОЗДАНИИ или РЕДАКТИРОВАНИИ любой подписи/локализуемой строки — агент ОБЯЗАТЕЛЬНО должен создавать/обновлять ОБА культурных файла минимум `resource.ru-RU.xml` И `resource.en-US.xml` (не только одну культуру), даже если технически Designer второе не требует. Это стандарт качества при работе с локализацией, независимо от типа схемы (Entity/Process/ClientUnit).
- Точный вид ключа зависит от типа схемы: `Columns.<Имя>.Caption` (объекты), `LocalizableStrings.<Ключ>.Value` (клиентские схемы), `BaseElements.<Имя>.Caption` (процессы верхнего уровня) / `EventsProcessSchema.BaseElements.<Имя>.Caption` (процесс событий внутри объекта) — см. конкретные `-edit.md` файлы.

## ✅ Как проверить «Обновить из файловой системы» и откатить боевую схему
- Лог обновления — `[app]/Logs/<ГГГГ-ММ-ДД>/PackagesSynchronization.log`: этапы загрузки пакетов; для изменённых ресурсов — `Deleted/Changed/Added - <N> <culture> resource values for schema '<Имя>'`; для удалённых схем — `Schema '<Имя>' not found in <ManagerName>`.
- После обновления окно «Изменения» показывает схемы пакета со статусом «Изменено» или «Удалено». «Изменено» бывает и при смене одного `ModifiedOnUtc`.
- Если `Pkg` стенда — git-репозиторий, правку боевой схемы откатывай так: `git diff -- <файлы схемы>` (убедись, что отличаются только твои правки), `git checkout -- <файлы>`, затем свежий `ModifiedOnUtc` в `descriptor.json`. Проверено 05.10.2026 на `ContactPageV2`.
- Резервные копии не храни в `/tmp`: macOS очищает его, копии от 30.09 пропали к 05.10. Архив перед удалением — в постоянную папку. Агенту в приложении запись вне `Pkg` запрещена: откат — через git `Pkg`; если `Pkg` не под git — копию делает пользователь.

## Данные из БД CRM (инструмент crm_db_query)
- Если пользователь включил в приложении доступ к БД, у агента есть инструмент crm_db_query: один запрос `SELECT` или `WITH`, транзакция только для чтения, до 200 строк, колонки с паролями, хешами, токенами и ключами недоступны (запрос с ними отклоняется), составные значения (строка целиком, json) скрываются — перечисляй нужные колонки явно. Без инструмента — попроси пользователя выполнить запрос и прислать результат.
- Для чего: Id записей, которых нет в `Pkg` (рабочие места `SysWorkplace`, записи базовых справочников, разделы залоченных пакетов в `SysModule` / `SysModuleEntity`), текущие значения системных настроек (`SysSettings` + `SysSettingsValue`), проверка после «Обновить из файловой системы» (записи данных пакета появились, SQL-скрипт выполнился).
- Имена таблиц и колонок в PostgreSQL — в двойных кавычках, как в схеме объекта: `"SysModule"."Code"`; справочная колонка в таблице — с суффиксом `Id` (`"SysWorkplaceId"`).
- Менять данные запросом нельзя — только файлами `Pkg` (данные пакета, SQL-скрипты пакета). Id записей проекта из БД в знания не пиши.
- Объект или раздел из задачи сначала ищи в пакетах проекта, потом в БД: рядом бывает одноимённый базовый раздел (в `SysModule` у него другой `Code`). Сверяй `Code` с регистрацией в пакете; базовый предлагай, только если в проекте подходящего нет.
- Названия базовых записей платформы в основной таблице могут быть на английском (`High`, `Call`, `To do`) — это культура, в которой запись создана; перевод — в `Sys<Объект>Lcz`. Ищи на обоих языках и показывай пользователю найденный Id вместе с названием.
- Рабочее место и его разделы: `SysModuleInWorkplace` (`SysWorkplaceId`, `SysModuleId`, `Position`) + `SysWorkplace` (`Name`) + `SysModule` (`Code`, `Caption`).
- Значение системной настройки: `SysSettings` (`Code`) + `SysSettingsValue` (`SysSettingsId`; значение — в `TextValue` / `IntegerValue` / `FloatValue` / `BooleanValue` и других колонках по типу).
- Выключен ли процесс: строка в `SysProcessDisabled`, где `SysSchemaId` = `SysSchema.Id` процесса (поиск по `SysSchema.Name`).
- Выполнился ли SQL-скрипт пакета: `SysPackageSqlScript` (`Name`, `NeedInstall`, `ModifiedOn`); 🧪 у уже выполненного скрипта `NeedInstall = false`.
- 🧪 Metadata схем в БД (по запросам к БД на другом стенде, не сверено со своим): отдельных таблиц колонок схем нет (`SysEntitySchemaColumn`, `SysSchemaColumn`, `SysDataValueType` — «отношение не существует»). Полная metadata схемы — в `"VwSysSchemaInfo"."MetaData"` (bytea, текст diff-журнала): читать `convert_from("MetaData", 'UTF8')`, фильтр по `"Name"` и `"ManagerName"` (`EntitySchemaManager`); `left()` к bytea неприменим. Нужно, когда в файлах нет ни папки схемы в `Pkg`, ни класса в `Autogenerated`.
- ✅ Колонки в PostgreSQL (подтверждено запросом к БД, 20.10.2026): колонки типа «Логическое», строковые (`character varying`, `text`) и целые создаются `NOT NULL` с умолчаниями `false`, `''` и `0` — даже если в схеме нет обязательности (`E2`) и значения по умолчанию; `NULL` допускают только справочные (`uuid`) колонки. В SQL-скриптах и запросах пустую строку проверяй как `= ''`, а не `IS NULL`; при `INSERT` не передавай `NULL` в такие колонки.
- ✅ Проверено в CRM (12.10.2026): рабочие места и привязки разделов, Id записей базовых справочников, значения системных настроек, выключение процесса, проверка созданных записей после «Обновить из файловой системы».

## Как узнать identity и колонки ЗАБЛОКИРОВАННЫХ (Autogenerated) схем, у которых нет своей папки в Pkg
- ✅ GUID типов данных (`DataTypeValueUId` в `descriptor.json` наборов данных) — в `[app]/Resources/ui/BPMSoft/core/enums/sysenums.js`; (подтверждено в CRM 08.10.2026: наборы с этими типами загрузились). UId колонок системных таблиц (`Lookup`, `SysModule`, `SysDetail`, `SysImage`, `SysSettings`…) — в `Autogenerated/Src/<Таблица>Schema.*.cs`.
Базовые объекты BPMSoft (Contact, Lead, BaseLookup и т.д.) генерируются автоматически, не имеют собственной папки в `Pkg` и раньше считались недоступными для чтения из файловой системы дампа проекта. Однако существует два надёжных источника для узнавания их `RealUId` (стабильного идентификатора) и определений колонок (вместе с `UId` и типом).

**Источник 1: `[app]/conf/content/<Имя>.js`** — JavaScript-объект с определением колонок схемы. Пример реального файла `Contact.js`:
```js
BirthDate: {
    uId: "3f08db69-6d2f-4b1c-87a4-acddc6c3b9d6",
    name: "BirthDate",
    caption: resources.localizableStrings.BirthDateCaption,
    dataValueType: BPMSoft.DataValueType.DATE,
    usageType: 0,
    isInherited: false,
    isValueCloneable: true
},
```

**Источник 2: `[app]/BPMSoft.Configuration/Autogenerated/Src/<Имя>Schema.<Пакет>.cs`** — C#-класс схемы. Содержит:
- `RealUId` — **стабильный UId САМОЙ схемы-объекта**, используется везде в проекте как значение `S4`/`ReferenceSchemaUId`/`FC2`/`EntitySchemaUId` при ссылке на эту схему из других мест.
- `ParentSchemaUId` — UId родительской схемы.
- ✅ **У замещённого объекта два `RealUId`** (06.10.2026, `ActivityPriority`): `ActivityPrioritySchema.Base.cs` — `b934f48c-5dea-49b9-bde3-697cb4be5d8b`, `ActivityPrioritySchema.<Пакет>.cs` — свой UId (UId схемы-замещения). Для ссылок (`S4`, `ReferenceSchemaUId`) бери `RealUId` базового слоя — так ссылаются и существующие колонки (`Activity.Priority`); lookup-колонка `TestTicket.TestPriority` с базовым UId работает.
- В методах `Create<Колонка>Column()` — `UId` колонки и (для lookup) `ReferenceSchemaUId` (реальный UId цели).
- ⚠️ 🧪 Классов схем `<Имя>Schema.<Пакет>.cs` в `Autogenerated/Src` может не быть (по логам другого стенда: нет ни одного `AccountSchema.*`/`ContactSchema.*`, при этом классы объектов `<Имя>.<Пакет>.cs`, например `Account.Base.cs`, есть). Тогда колонки бери из Источника 1 (`[app]/conf/content/<Имя>.js`), `UId` схемы — из `"SysSchema"` в БД (`"Name"`, `"ManagerName" = 'EntitySchemaManager'`, базовая схема — `"ExtendParent" = false`), остальное — из `"VwSysSchemaInfo"."MetaData"` (раздел «Данные из БД CRM»).

**Перекрёстные подтверждения (реальные файлы проекта, дополнительное доказательство):**

1. **Lead.QualifiedContact ↔ Contact.RealUId**:
   - `LeadSchema.Lead.cs`: колонка `QualifiedContact` имеет `UId = "ad490d58-054a-4d85-9246-dd8466eb3983"`, `ReferenceSchemaUId = new Guid("16be3651-8fe2-4159-8dd0-a803d4683dd3")`.
   - `ContactSchema.Base.cs`: `RealUId = new Guid("16be3651-8fe2-4159-8dd0-a803d4683dd3")` — **точное совпадение**.

2. **Справочник-наследник: descriptor.Parent ↔ BaseLookup.RealUId**:
   - `Pkg/<Пакет>/Schemas/<Справочник>/descriptor.json` → `Descriptor.Parent.UId = "11ab4bcb-9b23-4b6d-9c86-520fae925d75"`, `Parent.Name = "BaseLookup"`.
   - `BaseLookupSchema.Base.cs`: `RealUId = new Guid("11ab4bcb-9b23-4b6d-9c86-520fae925d75")` — **точное совпадение**. Это закрывает вопрос про Parent schema UId для Entity: на самом деле для Entity-схем (как и для клиентских схем) identity родителя хранится в `descriptor.json` → `Descriptor.Parent.UId`/`Parent.Name`, а НЕ в metadata.json.

3. **LeadPageV2 canonical-Parent-UId ↔ новая карточка-наследник**:
   - `Pkg/<Пакет>/Schemas/LeadPageV2/descriptor.json` (override с `ExtendParent: true`) имеет свой `Descriptor.UId`, `Parent.UId = "ddf8941f-92f3-4b10-9f59-faab18c12f46"` (Parent.Name = "LeadPageV2").
   - `Pkg/<Пакет>/Schemas/<НоваяКарточка>/descriptor.json` (новая схема, наследующая LeadPageV2 под новым именем) имеет `Parent.UId = "ddf8941f-92f3-4b10-9f59-faab18c12f46"` — **точное совпадение**. Значит, при создании новой клиентской схемы, наследующей override-схему, каноническим Parent-UId является `Parent.UId` ИЗ ФАЙЛА override-схемы, а не собственный `Descriptor.UId` этого override.

**Главный вывод**: поле `RealUId` C#-класса схемы = тот же самый идентификатор, что записывается в других местах проекта как `S4`/`ReferenceSchemaUId`/`FC2`/`EntitySchemaUId`/`descriptor.json.Parent.UId` — **единый стабильный идентификатор схемы на уровне всего проекта, независимо от того, есть у схемы своя папка в Pkg или нет**. Это позволяет использовать Autogenerated C#-классы как достоверный источник UId даже для базовых систем объектов, не имеющих видимого представления в Pkg.

## ✅ Как расшифровать неизвестное поле metadata: сверка с Autogenerated C#
Для залоченных и уже скомпилированных схем `Autogenerated/Src/<Имя>Schema.<Пакет>.cs` содержит те же данные, что `metadata.json`, но с человеческими именами свойств (`RequirementType`, `IsIndexed`, `DefValue`, `IsUnique`…). Метод: собрать по всем схемам проекта пары «элемент в `metadata.json` по UId ↔ тот же элемент в C#» и посчитать, какое свойство C# присутствует ровно тогда, когда присутствует поле. Совпадение 100% на сотнях примеров — надёжная расшифровка без экспериментов в Designer. Числовые значения enum смотреть в XML-документации `[app]/BPMSoft.*.xml` (`platform-api.md`). Так расшифрованы все поля `E*` колонок (см. `entity.md`).

## Расширение — новые типы схем
Этот же формат `metadata.json` встречается и у других менеджеров схем:

### ✅ SourceCodeSchemaManager (исходный код)
**Создано**: файлы `source-code.md` (факты) + `source-code-edit.md` (рецепты).
- Используется для именованного C#-кода, компилируемого в `Autogenerated` (обработчики событий, веб-сервисы и т.д.).
- **Формат B (плоский JSON-снимок)**, а не diff-журнал — см. `source-code.md`.
- Нет наследования (`Parent` отсутствует в `descriptor.json`), реальный C#-код содержится в `.cs`-файле.

### ✅ Data (данные пакета)
**Создано**: файлы `data.md` (факты) + `data-edit.md` (рецепты).
- Используется для строк данных справочников/лукапов, переносимых между стендами при установке пакета.
- Хранит конкретные ЗНАЧЕНИЯ строк таблицы БД (не структуру схемы), зафиксированные в файлах пакета.
- **Локализация через подпапку `Localization/data.<culture>.json`** внутри папки Data-схемы (отдельный механизм, не через `Resources/` XML-файлы как у Entity/Process).
- **`InstallType`** — управляет поведением при установке: `0` = Install (каждая установка, частый), `1` = FirstInstall (первая установка, редкий), `2` = Update (обновление версии, редкий). Это **другой enum** от SQL-скриптов (3 значения вместо 4).

### ✅ SqlScript (SQL-скрипт пакета)
**Создано**: файлы `sql-script.md` (факты) + `sql-script-edit.md` (рецепты).
- Используется для SQL-скриптов миграций и инициализации БД при установке пакета.
- **Самый простой тип схемы**: ТОЛЬКО 2 файла (`descriptor.json` + `.sql`), БЕЗ `metadata.json`, БЕЗ `properties.json`, БЕЗ ресурсов/локализации вообще.
- **Ключевое отличие**: корневой ключ в `descriptor.json` называется `"SqlScript"` (а не `"Descriptor"`).
- Содержит сырой SQL-текст (PostgreSql/MSSql/Oracle по `DBEngineType`), выполняется при установке пакета согласно `InstallType` (BeforePackage/AfterPackage/AfterSchemaData/UninstallApp).

### ✅ ServiceSchemaManager (веб-сервис)
**Создано**: файлы `web-service.md` (факты) + `web-service-edit.md` (рецепты).
- Описание внешнего REST-сервиса для элемента процесса «Вызвать веб-сервис»: URI, методы, параметры запроса и ответа.
- **Формат B (плоский JSON)**, три файла (`descriptor.json`, `metadata.json`, `properties.json`) и ресурсы `Resources/<Имя>.Service/`; `.cs` нет.

### Ещё не описанные типы
- `DcmSchemaManager` (10 схем) — кейсы со стадиями (DCM).
- Папки пакета `Files` и `Assemblies`; `descriptor.json` самого пакета (зависимости).
- Преднастроенная страница и своё действие процесса уже описаны: `process-edit.md`, `user-task.md` + `user-task-edit.md`.

При добавлении нового типа схемы в будущем — создавай пару файлов `<topic>.md` (подтверждённые факты) + `<topic>-edit.md` (рецепты создания/редактирования) по этому же образцу, и ссылайся на этот файл (`metadata-editing.md`) для общей механики вместо повторения её содержимого. Особое внимание: убедись, используется ли новый тип diff-журнал (Формат A) или плоский JSON (Формат B), и явно отметь это в файле `<topic>.md`.
