# Кейсы (DcmSchemaManager) — факты

Кейс (DCM) — схема процесса особого вида: стадии записи одного объекта (раздела) и шаги на стадиях. Стадия записи — значение справочной колонки объекта («колонка стадии»); на карточке раздела кейс показан панелью стадий и блоком «Следующие шаги». Рецепты файлами — `dcm-edit.md`, шаблон шага «Выполнить задачу» — `templates/dcm/case-activity-task.json`. Общая механика процессов (параметры `BP2`, маппинги `BK15`, `BK37`, журнал процессов) — `processes.md`.

Отметки: ✅ подтверждено записью в CRM (25.10.2026, стенд .NET 8) или ✅ на реальных схемах проекта; 🧪 не проверено; ❌ опровергнуто.

## ✅ Где лежит и как открыть
- Схема с `"ManagerName": "DcmSchemaManager"`: `Schemas/<Имя>/` (`descriptor.json`, `metadata.json`, `properties.json`) и `Resources/<Имя>.Dcm/resource.<culture>.xml`; `.cs` нет. Кейсы проекта: grep `"DcmSchemaManager"` в `Pkg/*/Schemas/*/descriptor.json` (✅ на реальных схемах проекта).
- Платформенные кейсы (`LeadCase`, `OpportunityCase`, `CaseCase`, `ProblemCase`, `OmniChatCase`) есть только в БД (`SysSchema`), в `Pkg` их нет; шагов на стадиях у них нет.
- Дизайнер кейсов: `<CRM>/Nui/ViewModule.html?vm=DcmDesigner#case/<UId схемы>` (.NET 8). Адрес `/0/Nui/ViewModule.aspx?vm=DcmDesigner#case/<UId>` на .NET 8 перенаправляет без `?vm=` и открывает пустую страницу; на .NET Framework 🧪.
- Дизайнер сохраняет кейс в БД и сразу в файлы пакета (`Schemas/<Имя>/`, `Resources/<Имя>.Dcm/`); при этом убирает `DependsOn` из `descriptor.json` и ставит в `properties.json` свой `CreatedInVersion`.
- Кейс работает после «Обновить из файловой системы», компиляция не нужна.

- ✅ Свойства кейса в БД (подтверждено запросом к БД, 28.10.2026, 15 кейсов): таблица `"SysSchemaProperty"` (`"SysSchemaId"` = `"SysSchema"."Id"` кейса, `"Name"`, `"Value"`) — `EntitySchemaUId`, `StageColumnUId`, `Enabled`, `IsActiveVersion`, `Version`, `IsTracing`, `CreatedInVersion`. Условие запуска (`Filters`) и стадии — только в metadata: `convert_from("MetaData", 'UTF8')` из `"VwSysSchemaInfo"`; это текст diff-журнала, а не JSON, поэтому `::json` падает (`invalid input syntax for type json`) — ищи `position`/`regexp_matches` по `"Filters"`, `"StageRecordId"`.

## ✅ Как работает экземпляр кейса
- Запуск — системный стартовый сигнал «запись добавлена» по объекту `EntitySchemaUId` с фильтром `Filters` кейса: новая запись объекта, подходящая под условие, получает экземпляр кейса. Запуск для записей, созданных раньше кейса, 🧪.
- Выбор кейса: среди кейсов объекта берутся активные (`Enabled`) актуальные версии (`IsActiveVersion`), для записи — тот, чьи `Filters` ей подходят. Проверено: при условии «Категория = <значение>» запись с этим значением получила экземпляр, с другим — нет.
- Экземпляр — процесс: `SysProcessData`, `SysProcessLog` (имя = заголовок кейса), в `SysProcessElementLog` — стадии (`Type` `BPMSoft.Core.DcmProcess.DcmSchemaStage`) и шаги (`BPMSoft.Core.DcmProcess.DcmSchemaElement`). Подписка экземпляра на запись — строка `SysEntityCommonPrcEl` (`RecordId` записи, `RecordChangeType` 2, `ChangedColumns` = `["<UId колонки стадии>"]`).
- Смена стадии — смена значения колонки стадии у записи: кликом по стадии на карточке, `UpdateQuery` DataService или `Entity.Save()`. Экземпляр переходит на стадию, у которой `StageRecordId` = новое значение, и запускает её шаги (задача создаётся при входе в стадию).
- Автопереход: у стадии `TransitionType` 1 — после выполнения обязательных шагов (`RequiredType` 1), 2 — после всех шагов 🧪. Платформа сама меняет колонку стадии на следующую по порядку в `Stages` стадию из `StageConnections`. Проверено: выполнение обязательной задачи перевело запись на следующую стадию (не на альтернативную).
- Если на стадии нет шагов, экземпляр завершается (статус Completed) после перехода на неё; панель стадий на карточке продолжает работать по значению колонки.
- После новой версии кейса новые записи получают актуальную версию, уже запущенные экземпляры продолжают работать на своей.
- Задача шага связывается с записью кейса, только если у параметра связи шага задано значение (`dcm-edit.md`, «Шаг «Выполнить задачу» на стадии»); иначе задача создаётся без ссылки на запись.

## ✅ Связь с объектом, разделом и справочником стадий
- `EntitySchemaUId` — UId объекта, `StageColumnUId` — UId справочной колонки стадии; оба в `metadata.json` и в `properties.json`, значения одинаковые.
- Справочник стадий — справочник, на который ссылается колонка стадии. Стадия кейса указывает на свою запись справочника (`StageRecordId` = `Id` записи); одна запись — одна стадия, дизайнер не даёт выбрать занятую запись. Подписи стадий — свои, в ресурсах кейса.
- `SysDcmSettings` — настройка кейсов раздела, одна на регистрацию объекта раздела: `SysModuleEntityId` (`Id` записи `SysModuleEntity` объекта), `StageColumnUId`, `Filters`, `DefaultSchemaUId`.
  - `Filters` = `[{"columnUId":"<UId колонки>"}]` — колонка, по которой дизайнер строит «Условие запуска кейса» (настройка раздела «По какой колонке настраивать условие запуска кейса»). При `[{"columnUId":null}]` дизайнер пишет «Для раздела не задана настройка…» и условие не редактирует. Сервер запускает кейс по `Filters` самого кейса независимо от этой настройки.
  - `DefaultSchemaUId` — кейс по умолчанию (в проекте `null`, у платформенных разделов — UId платформенного кейса); роль 🧪.
- `SysDcmSchemaInSettings` — связь кейса с настройкой раздела: `SysDcmSettingsId`, `SysDcmSchemaUId` = UId схемы кейса. Каждая версия кейса — своя строка (дизайнер при сохранении новой версии добавляет её сам).
- Панель стадий на карточке появилась у раздела с `SysDcmSettings` (карточка открыта из раздела) и активным кейсом объекта. Без `SysDcmSettings` 🧪: по клиентскому коду панель не строится. Дизайнер без строки `SysDcmSchemaInSettings` для кейса 🧪: ожидается сообщение о ненайденной настройке, в опыте дизайнер с кешем браузера открылся.
- На панели стадий кликабельны только стадии, в которые есть переход из текущей по `StageConnections` (класс `stage-enabled`). Проверено: из первой стадии доступна только связанная с ней вторая.
- `SysDcmUserTask` — типы шагов в меню «Добавить шаг» дизайнера (`SchemaUId` действия процесса, `Position`): «Выполнить задачу» (`b5c726f2-af5b-4381-bac6-913074144308`), «Визирование» (`51179e03-650d-4492-862d-9943005c26b4`), «Открыть страницу редактирования» (`b0d3ad9f-7a27-46a3-9483-ed70c26872ae`), «Отправить email» (`184dbb27-ce13-4d37-8dff-c2ff1df9cf19`), «Изменить права доступа» (`0ebbb23c-f6db-45eb-ad13-a1445b7ef081`); плюс «Подпроцесс».
- `SysModuleDcmSettings` — таблица с теми же колонками, на стенде пустая; не используй.
- ✅ На реальных схемах проекта: настройки переносят наборами данных `Data/SysDcmSettings_<…>` и `Data/SysDcmSchemaInSettings_<…>` в пакете кейса; для платформенного раздела набор `SysDcmSettings` повторяет `Id` платформенной настройки и меняет её колонки (`IsForceUpdate: true`).

Стадия (`BL1` `BPMSoft.Core.DcmProcess.DcmSchemaStage`): `UId`, `A2` (`Stage<N>`), `A3`/`A4` = UId кейса, `A5` = UId пакета, `ParentStageUId` — у альтернативной стадии (ветка от стадии, на панели — отдельной стадией, например «Отменена» от «В работе»), `Color` (`#RRGGBB`), `StageRecordId`, `Elements` (шаги), `IsSuccessful` (по умолчанию `true`, пишется только `false` — неуспешная завершающая стадия), `TransitionType` (0 — вручную, 1 — после обязательных шагов, 2 — после всех), `UsePermissions` и `Permissions` (права на переход в стадию, строка UId через запятую) 🧪.

Шаг (`BL1` `BPMSoft.Core.DcmProcess.DcmSchemaElement`): `UId`, `A2` (`DcmElement<N>`), `A3`/`A4` = UId кейса, `A5` = UId пакета, `IL2` = UId стадии, `RequiredType` (0 — необязательный, 1 — обязательный; пишется всегда), `Conditions` — переход на стадию по результату шага (JSON-массив с `nextStageId`) 🧪, `ProcessFlowElement` — обычный элемент процесса. Значение «поле записи кейса» в параметре шага — макрос `[#ColumnValue.{<UId объекта кейса>}.{<UId колонки>}#]` с `GS1` 3; `Id` записи — колонка `ae0e45ca-c495-4fe7-a39d-3ab7278e1617`.

Ресурсы `Resources/<Имя>.Dcm/`: `Caption`, `NotificationCaption.Caption`, `NotificationCaption.DisplayValue`, `Stages.<Стадия>.Caption`, `Stages.<Стадия>.Elements.<Шаг>.Caption`, `Stages.<Стадия>.Elements.<Шаг>.ProcessFlowElement.Parameters.<Параметр>.Caption` / `.Value` / `.DisplayValue`.

## ✅ Версии, замещение, «Активен», удаление
- Правка файлов кейса с тем же `UId` меняет кейс на месте («Изменено» в окне обновления).
- «Сохранить новую версию» в дизайнере создаёт новую схему в пакете: имя `<Имя прежней версии><Пакет><N>`, свой `UId`; в `descriptor.json` — `"Parent": {"UId": "<UId прежней>", "Name": "<Имя прежней>"}`; в metadata — `BK8` = UId прежней, `IJ9` = номер; UId стадий и шагов те же, `A3`/`A4` — новый UId. У прежней версии — `IJ7: false` и `"IsActiveVersion": "False"`. Дизайнер спрашивает «Установить текущую версию актуальной?».
- Строку `SysDcmSchemaInSettings` новой версии дизайнер пишет в БД вместе с привязкой данных `SysDcmSchemaInSettings_<Id>` только в БД, без папки в `Pkg`; следующее «Обновить из файловой системы» удаляет эту привязку (строка в таблице остаётся). На другом стенде у такой версии связи не будет — добавь строку в свой набор.
- Замещений кейсов нет: все 10 кейсов проекта и 5 платформенных — самостоятельные схемы (`ExtendParent` false). Менять платформенный кейс — новой версией в своём пакете 🧪.
- «Активен» — `Enabled` корневой (первой) версии, действует на все версии. ❌ Опровергнуто как способ выключения: `"Enabled": "False"` в `properties.json` корневой версии после обновления и перезапуска не выключил кейс, дизайнер показывал «Активен». Выключай чекбоксом «Активен» в дизайнере 🧪.
- Удаление схемы версии через «Обновить из файловой системы» убирает её запущенные экземпляры из `SysProcessData` и `SysEntityCommonPrcEl` и её строку `SysDcmSchemaInSettings`; журнал `SysProcessLog` остаётся со статусом Running.
