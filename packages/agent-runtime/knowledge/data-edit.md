# Данные пакета (Data) — рецепты создания/редактирования

Общая механика ресурсов и локализации — см. `metadata-editing.md`. **Важное уточнение**: Data не использует ресурсные XML-файлы в `Resources/` папке (как Entity/Process/ClientUnitSchema) — вместо этого локализация хранится через подпапку `Localization/` прямо ВНУТРИ папки Data-схемы, и это **ДРУГОЙ, ОТДЕЛЬНЫЙ механизм** от `resource.xml`.

**Не забывай про обязательное правило из `metadata-editing.md`: `ModifiedOnUtc` в `descriptor.json` должно обновляться при любом создании новой схемы на РЕАЛЬНЫЙ текущий момент времени в формате `"\/Date(<миллисекунды>)\/"` (получить можно через `date +%s000`).**

## ✅ Создать новый набор данных с нуля — общий рецепт

Подтверждено записью 05.10.2026 на справочнике, системной настройке и таблице с колонками-справочниками, числом, логическим и датой (`TestDataEntity_D4`, факты — `data.md`).

### Шаг 1: Создать папку набора данных

```
Pkg/<Пакет>/Data/<Имя>/
```

### Шаг 2: Создать `descriptor.json`

```json
{
  "Descriptor": {
    "UId": "<новый GUID для самого набора данных>",
    "Name": "<Имя>",
    "ModifiedOnUtc": "\/Date(<текущее_время_миллисекунды>)\/",
    "InstallType": 0,
    "Schema": {
      "UId": "<UId целевого объекта (Entity-схемы), в которую загружаются данные>",
      "Name": "<Имя целевого объекта>"
    },
    "Columns": [
      {
        "ColumnUId": "<UId колонки Id целевого объекта>",
        "IsForceUpdate": false,
        "IsKey": true,
        "ColumnName": "Id",
        "DataTypeValueUId": "<GUID типа данных GUID>"
      },
      {
        "ColumnUId": "<UId колонки Name целевого объекта>",
        "IsForceUpdate": true,
        "IsKey": false,
        "ColumnName": "Name",
        "DataTypeValueUId": "<GUID типа данных Text>"
      }
    ]
  }
}
```

### Шаг 3: Выбрать `InstallType`

В поле `Descriptor.InstallType` выбери значение согласно таблице:

| InstallType | Значение | Поведение | Частота | Примечание |
|---|---|---|---|---|
| Install | `0` | Устанавливается при КАЖДОЙ установке пакета (также при переустановке) | Самый частый (почти все наборы) | Используй этот вариант по умолчанию для обычных данных справочников |
| FirstInstall | `1` | Устанавливается ТОЛЬКО при первой установке пакета, не переустанавливается при повторной установке/обновлении | Редкий (2 файла) | Используй для seed-данных, которые пользователь может изменить, и которые не должны перезаписываться при обновлении пакета |
| Update | `2` | Обновляет существующие записи (колонки с `IsForceUpdate: true`); новые строки при «Обновить из файловой системы» не добавляет (✅ 21.10.2026) | Редкий (13 файлов) | Используй, чтобы обновлять значения уже существующих записей, не создавая новых |

**По умолчанию используй `InstallType: 0` (Install)** — это охватывает большинство случаев (справочники, лукапы и т.д.).

✅ Проверено 05.10.2026: при «Обновить из файловой системы» строки загружает только набор с `0`; наборы с `1` и `2` отмечаются «Добавлено», но строк не добавляют.

### Шаг 4: Создать `data.json`

```json
{
  "PackageData": [
    {
      "Row": [
        { "SchemaColumnUId": "<UId колонки Id>", "Value": "04992e36-958e-476a-8824-06c7192c6eed" },
        { "SchemaColumnUId": "<UId колонки Name>", "Value": "Первая запись" }
      ]
    },
    {
      "Row": [
        { "SchemaColumnUId": "<UId колонки Id>", "Value": "a1234567-890b-4d2f-1234-5678901234cd" },
        { "SchemaColumnUId": "<UId колонки Name>", "Value": "Вторая запись" }
      ]
    }
  ]
}
```

**Правила**:
- Каждая запись в `PackageData` — одна строка таблицы данных
- В каждой `Row` перечисли все колонки из `Columns` (из `descriptor.json`) в любом порядке
- Для каждой колонки укажи:
  - `SchemaColumnUId` — соответствующий `ColumnUId` из `descriptor.json`
  - `Value` — значение:
    - Для GUID — строка с GUID (например `"04992e36-958e-476a-8824-06c7192c6eed"`)
    - Для текста — строка (например `"Первая запись"`)
    - Для чисел — число (например `42`)
    - Для булевых — JSON-булево `true`/`false` (не строка)
    - Для пустого lookup — строка `"null"` (буквально)
- **Для lookup-колонок `DisplayValue` обязателен** (см. `data.md`): отображаемое значение записи или `"null"`. Если клонируешь строку с реального набора и меняешь `Value` lookup-ячейки — не удаляй `DisplayValue`, а замени его на отображаемое значение новой записи (или `"null"`)
- Для даты/времени — строка `"\/Date(<миллисекунды>+0300)\/"` (смещение пояса указывай всегда; в БД значение ляжет в UTC).
- `DisplayValue` нужен только для формата файла: в БД пишется ссылка из `Value` (✅ проверено строкой с неверной подписью).

```json
}
```

**Правила**:
- **Локализуемые текстовые колонки** (например `Name`, `Description`) — размещаются ТОЛЬКО в файлах `Localization/data.<culture>.json`, НЕ в основном `data.json`
- **Нелокализуемые колонки** (например `Country`, числовые поля, булевы) — размещаются ТОЛЬКО в основном `data.json`, НЕ в локализацион файлах
- `Id` (ключ) — размещается И в основном `data.json` И во всех файлах `Localization/data.<culture>.json` (для сопоставления строк)
- Каждая строка в файлах `Localization/` должна содержать поле `"ColumnName"` рядом с `SchemaColumnUId` (это помогает системе идентифицировать, какое поле переводится)

### Шаг 6: Создать пустой `filter.json`

```
Pkg/<Пакет>/Data/<Имя>/filter.json
```

Содержимое: пустой файл или файл с одним переносом строки. Назначение/структура при заполнении не установлены; на реальных примерах этот файл всегда пустой, но его присутствие обязательно.

### Шаг 7: Обновить в BPMSoft

Открыть BPMSoft-CRM и нажать "Обновить из файловой системы" (Update from file system). Данные будут загружены в целевой объект согласно `InstallType`.

**Типичные ошибки при первом создании**:
- Забыли `IsKey: true` для колонки `Id` — без этого система не сможет правильно сопоставлять записи при повторной установке
- `InstallType` установлен неправильно — выбрал `1` (FirstInstall) для данных, которые должны обновляться при каждой установке (обычно нужен `0`)
- Не совпадают `ColumnUId` в `descriptor.json` с `SchemaColumnUId` в `data.json` — проверь, что используешь правильные UId из целевого объекта
- Локализованные текстовые колонки размещены в основном `data.json` вместо `Localization/data.<culture>.json` — разделяй локализуемые и нелокализуемые колонки
- `ModifiedOnUtc` захардкодирован и не совпадает с реальным временем — потом это затрудняет отладку истории изменений
- Забыли создать файл `filter.json` — хотя он пустой, его присутствие может быть требуется системой

## ✅ Удалить набор данных целиком

✅ Подтверждено 05.10.2026: удаление набора (папки или строк) не удаляет записи в БД — их стирай SQL, см. «Удалить записи данных — только SQL».

Процедура проще, чем у других типов схем, так как у Data нет отдельной папки `Resources/` с ресурсами:

1. Удалить рекурсивно ТОЛЬКО одну папку:
   - `Pkg/<Пакет>/Data/<Имя>/` (сама папка с данными, включая её собственную подпапку `Localization/` если была)

2. **НЕ требуется удалять папку в `Resources/`** — она не существует для Data-схем (в отличие от Entity/Process/ClientUnitSchema)

3. Открыть BPMSoft-CRM и нажать "Обновить из файловой системы"

4. Данные пропадают из runtime (строки в целевой таблице НЕ удаляются автоматически; если нужно их удалить, сделай это отдельно в БД или через UI CRM)

**ПЕРЕД удалением проверить зависимости** — убедиться, что никакие другие пакеты/конфигурация не ссылаются на этот набор данных или не полагаются на его строки как на критичные исходные данные.
