# API платформы для C#: где искать и проверенные факты

Для серверного кода: схемы исходного кода, слушатели событий, свои действия процесса. Здесь — какой `using` нужен, где посмотреть сигнатуру метода и значения перечислений. Рецепты целиком — в `source-code-edit.md` и `user-task-edit.md`.

## Порядок поиска API
1. ✅-факты этого файла — используй сразу, без поиска.
2. XML-документация платформы `[app]/BPMSoft.*.xml` — официальная поставка, лежит рядом с DLL в любой установке; основной файл — `BPMSoft.Core.xml`, общие типы — `BPMSoft.Common.xml`.
3. Примеры вызова в `[app]/BPMSoft.Configuration/Autogenerated/Src` и в `Pkg` — как метод реально вызывают и какие `using` стоят рядом.
5. Подтверждения нет нигде — не угадывай: укажи в плане риск ошибки компиляции.

## Как читать XML-документацию
- Каждый элемент — `<member name="<префикс>:<полное имя>">` с описанием в `<summary>`, `<param>`, `<returns>`.
- Префикс: `T:` — тип (класс, интерфейс, перечисление), `M:` — метод или конструктор (`#ctor`), `P:` — свойство, `F:` — поле или значение перечисления, `E:` — событие.
- Пространство имён для `using` — всё, что стоит перед именем класса: `T:BPMSoft.Core.Entities.Entity` → `using BPMSoft.Core.Entities;`.
- Параметры метода — полными именами типов в скобках: `M:BPMSoft.Core.Entities.Events.BaseEntityEventListener.OnSaving(System.Object,BPMSoft.Core.Entities.EntityBeforeEventArgs)`.
- Описаны не все типы. Если строки `T:` нет, пространство имён видно по именам методов типа (`M:...`) или по ссылкам `cref="T:..."`.
- Порядок тегов `<param>` может не совпадать с порядком аргументов (пример — `Entity.Save`: в XML сначала `setColumnDefValue`, в сборке первым идёт `validateRequired`). Позиционный порядок по XML не определяй: ищи вызовы с именованными аргументами в `Autogenerated/Src` или передавай аргументы по имени.

Команды (вместо `[app]` — корень приложения; файлы большие — ищи точечно, целиком не читай):
```bash
# пространство имён типа
grep -ho 'name="T:[A-Za-z.]*\.EntitySchemaQuery"' [app]/BPMSoft.*.xml
# тип не описан — пространство имён по ссылкам на него
grep -ho 'cref="T:[A-Za-z.]*\.UserConnection"' [app]/BPMSoft.Core.xml | sort -u
# методы класса с параметрами
grep -o 'name="M:BPMSoft.Core.Entities.EntitySchemaManager\.[^"]*"' [app]/BPMSoft.Core.xml
# описание конкретного метода
grep -n -A6 'name="M:BPMSoft.Core.Configuration.SysUserInfo.GetCurrentDateTime"' [app]/BPMSoft.Core.xml
# значения перечисления
grep -o 'name="F:BPMSoft.Common.OrderDirectionStrict\.[^"]*"' [app]/BPMSoft.Common.xml
```

## Частые операции
- ✅ Создать запись: `userConnection.EntitySchemaManager.GetInstanceByName("<Объект>")` → `schema.CreateEntity(userConnection)` → `SetDefColumnValues()` → `SetColumnValue(...)` → `Save(false)`. Рецепт — `source-code-edit.md`, «Создать связанную запись после вставки».
- ✅ по метаданным `BPMSoft.Core.dll` (21.10.2026): сигнатура `Entity.Save(bool validateRequired = true, bool setColumnDefValue = true)`; есть ещё `Save(EntitySaveConfig)` (свойства `ValidateRequired`, `SetColumnDefValue`, `SetForceBackgroundMode`). `Save(false)` в рецептах — сохранить без проверки обязательных колонок; значения справочных колонок по умолчанию при этом подставляются. С проверкой обязательных — `Save()`. В коде платформы встречаются именованные вызовы `Save(validateRequired: false)` и `Save(setColumnDefValue: false)` — так понятнее, пиши так же. Опровергнуто: прежняя запись «первый параметр — `setColumnDefValue`» — её вывели из порядка тегов `<param>` в XML-документации, а он обратный порядку аргументов.
- ✅ Прочитать одно значение из БД: `new Select(userConnection).Column("<Колонка>").From("<Объект>").Where("Id").IsEqual(Column.Parameter(id)) as Select`, затем `ExecuteScalar<T>()`.
- ✅ Изменить запись без событий объекта: `new Update(userConnection, "<Объект>").Set("<Колонка>", Column.Parameter(value)).Where("Id").IsEqual(Column.Parameter(id)) as Update`, затем `Execute()` (`entity-edit.md`, скрипт «После сохранения»).

## ✅ Системные настройки, функциональности, соединения (проверено записью в CRM, 22.10.2026)
- `SysSettings.SetValue(UserConnection, "<Код>", <значение>)` пишет **персональное** значение текущего пользователя (строка `SysSettingsValue` на пользователя), даже у администратора и у настройки с `IsPersonal: false`. Общее значение («Все сотрудники») пишет только `SysSettings.SetDefValue(UserConnection, "<Код>", <значение>)`; персональные значения пользователей при этом остаются и перекрывают его. Класс — `global::BPMSoft.Core.Configuration.SysSettings` (см. CS0117 выше).
- `SysSettings.TryGetValue(UserConnection, "<Код>", out object value)` — параметр `out` (не `ref`: с `ref` ошибка компиляции «Argument 3 must be passed with the 'out' keyword»); для несуществующего кода — `false` и `null`.
- Сервер кеширует значения настроек: после правки `SysSettingsValue` SQL `GetValue` возвращает старое значение, пока не сбросить кеш — `POST /0/DataService/json/SyncReply/ClearSysSettingsCacheRequest` с телом `{}` (под администратором) или перезапуск приложения. Обновление CRM из файловой системы кеш тоже сбрасывает.
- Функциональности (`using BPMSoft.Configuration;`, методы-расширения `UserConnection` из `FeatureUtilities`): `SafeSetFeatureState("<Код>", 1)` создаёт функциональность, если её нет, и ставит состояние **только текущему пользователю**; создание требует операции `CanManageLookups` — у обычного пользователя `SecurityException`. `SetFeatureState("<Код>", <состояние>, forAllUsers: true)` меняет только уже существующие строки `AdminUnitFeatureState`, новых не создаёт. `GetIsFeatureEnabled` читает состояние через роли пользователя (`SysAdminUnitInRole`).
- ⚠️ Кеш функциональностей: `GetIsFeatureEnabled` после `SetFeatureState`/`SafeSetFeatureState` возвращает старое значение (в той же и в новых сессиях) — очистка кеша в платформенном коде не попадает в группу, из которой читается состояние. Новое состояние видно после перезапуска приложения. Не включай функциональность кодом с расчётом сразу на неё опереться.
- `UserConnection.AppConnection.SystemUserConnection` — соединение системного пользователя (системная настройка `SystemUser`; обычно `Supervisor`). Записи, созданные через него, получают `CreatedBy` = контакт системного пользователя; права на операции не проверяются (обычный пользователь через него создаёт запись справочника).
- ✅ Сохранение записи справочника (наследника `BaseLookup`) через `Entity.Save` под пользователем без операции `CanManageLookups` — `SecurityException` «Текущий пользователь не имеет прав на запуск администрируемой операции с кодом "CanManageLookups"». Справочники из кода от имени пользователя заполняй через `SystemUserConnection` или выдай роли операцию.
- `UserConnection.GetLocalizableString("<Схема>", "<Ключ>")` (расширение из `NotificationProviderHelper`, `BPMSoft.Configuration`) — то же, что `new LocalizableString(UserConnection.Workspace.ResourceStorage, "<Схема>", "LocalizableStrings.<Ключ>.Value")`; язык — культура пользователя.
- Регистр строк на PostgreSQL: фильтр ESQ `FilterComparisonType.Equal` по строке **не учитывает** регистр (`"консультация"` находит «Консультация»); `Select … .Where("<Колонка>").IsEqual(Column.Parameter("консультация"))` и SQL-скрипт — **учитывают**.
- Запросы `Insert`, `Update`, `Delete` из `BPMSoft.Core.DB` работают напрямую с таблицей: слушатели объекта, журнал изменений и права по записям не срабатывают (проверено 22.10.2026 для `Update`; для `Insert` — `rights.md`). Нужна бизнес-логика объекта — работай через `Entity` или `DataService`.

Наследник `GridDashboardItemData` (или другого `*DashboardItemData`) без своего `[DashboardItemData("<Тип>")]` получает атрибут родителя, и `types.Add` падает с `An item with the same key has already been added` — ломаются все виджеты стенда (`Logs/<дата>/Error.log`, стек `DashboardItemDataFactory.GetWidgetTypes`). Лечится своим атрибутом с уникальным типом на наследнике.
- ✅ Данные виджета с изменённой конфигурацией (подтверждено в CRM, 20.10.2026): подставь свой `filterData` в JSON конфигурации виджета (вложенный `EXISTS` тоже работает) и вызови `new DashboardItemDataFactory(UserConnection).CreateInstance(<тип виджета>, <имя итога>, <config JObject>, <timeZoneOffset>).GetJson()` — фильтр применяется штатно, результат совпал с SQL.
- ✅ `timeZoneOffset` у `CreateInstance` и классов `*DashboardItemData` — в минутах, UTC+3 → `180` (подтверждено в CRM, 20.10.2026): на сервере — `(int)UserConnection.CurrentUser.GetTimeZoneOffset().TotalMinutes`; клиент передаёт `-BPMSoft.util.getCurrentTimezoneOffsetInMinutes()` (`[app]/conf/content/MobileDashboardDataManager.js`).
- ✅ `SysDashboard.Caption` локализуемая (подтверждено в CRM, 20.10.2026; переводы — в таблице `SysDashboardLcz`): ESQ из серверного кода сравнивает название на языке текущего пользователя, поэтому поиск итога по английскому названию у пользователя с русским языком ничего не находит. Ищи итог по `Id`, а не по `Caption`.

## Чего нет в XML-документации
- `StoringObjectState` — не описан совсем (значения — выше).
- Типы `UserConnection`, `EntitySchemaManager`, `SysUserInfo`, `EntityBeforeEventArgs` не имеют строки `T:`, но их методы (`M:`) и ссылки (`cref`) есть — пространство имён находится по ним.
- `EntityAfterEventArgs.ModifiedColumnValues`, `Entity.GetTypedOldColumnValue` / `GetColumnOldValue` — только в примерах `Pkg` и `Autogenerated/Src` (свойство `EntityColumnValue.OldValue` в XML есть).
