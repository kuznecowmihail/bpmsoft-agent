# Кейсы (DcmSchemaManager) — рецепты

Факты, коды и поведение — `dcm.md`. Общая механика записи — `metadata-editing.md`, наборы данных — `data-edit.md`. ✅ — проверено записью в CRM, 🧪 — не проверено, ❌ — опровергнуто.

## ✅ Что нужно до кейса
1. Объект со справочной колонкой стадии и справочник стадий с записями (по записи на стадию). UId колонки — в `Autogenerated/Src/<Объект>Schema.<Пакет>.cs` (`Create<Колонка>Column`, `UId`), `Id` записей — запросом к справочнику.
2. Раздел объекта: `select "Id" from "SysModuleEntity" where "SysEntitySchemaUId" = '<UId объекта>'`. Есть ли уже настройка кейсов: `select * from "SysDcmSettings" where "SysModuleEntityId" = '<Id>'`. Если есть (у платформенных разделов — лиды, продажи, обращения), новую не создавай, добавь только связь (шаг 6).
3. Для шага «Выполнить задачу», связанного с записью, — справочная колонка `Activity` на объект, зарегистрированная в `EntityConnection` (`select * from "EntityConnection" where "ColumnUId" = '<UId колонки>'`), см. `process-activity-edit.md`, «Связь задачи с записью».

## ✅ Шаг «Выполнить задачу» на стадии
Подтверждено: шаг, добавленный в дизайнере, с поправкой связи файлом — при входе в стадию создалась задача, связанная с записью (`Activity.<Колонка связи>Id` = запись), карточка показала её в «Следующих шагах» с кнопкой «Завершить».
- Шаблон — `templates/dcm/case-activity-task.json` (`about` — что заменить): `element` — в `Elements` стадии, `mappings` — в `BK15` кейса, `resources` — в оба файла ресурсов. Если в проекте есть кейс с таким шагом, бери его как образец.
- Шаг — `DcmSchemaElement`, внутри `ProcessFlowElement` — обычный `ProcessSchemaUserTask` (параметры как у элемента процесса, `process-tasks-edit.md`), но маппинги лежат в `BK15` кейса, и их `A2` = `DcmProcessElement<N>`.
- ⚠️ Связь задачи с записью. Параметр связи шага: имя = колонка `Activity` на объект кейса, UId = UId этой колонки `Activity`, `L17` `ActivityConnection`. Значение `[#ColumnValue.{<UId объекта кейса>}.{ae0e45ca-c495-4fe7-a39d-3ab7278e1617}#]` с `GS1` 3 нужно и в `L8` параметра (с `GS5` = UId кейса, `IL2` параметра = UId `ProcessFlowElement`), и в маппинге `BK15`. Дизайнер ставит это значение сам только для колонок связи, известных клиенту при добавлении шага; для своей колонки связи он сохранил параметр без значения и без маппинга — задача создавалась с пустой ссылкой. ❌ Опровергнуто: одного маппинга `BK15` мало — ссылка осталась пустой; заработало после значения в `L8` и `IL2` параметра.
- Обязательный шаг — `"RequiredType": 1`; автопереход после него — `"TransitionType": 1` у стадии.
- ✅ Шаг без связи с записью (подтверждено записью в CRM 25.10.2026): если у `Activity` нет колонки на объект кейса, убери из шаблона параметр связи и его маппинг. Задача создаётся при входе в стадию, после её выполнения автопереход срабатывает, но в «Следующих шагах» карточки задачи нет — она видна в разделе «Активности».
- Подписи — `Stages.<Стадия>.Elements.<Шаг>.Caption` и подписи параметров в обеих локалях (дизайнер кладёт подпись шага и значения только в ru-RU).

## ✅ Автопереход на следующую стадию
`"TransitionType": 1` в объекте стадии (последним полем) и `"RequiredType": 1` у шага. Поведение (переход на следующую стадию из `StageConnections`, не на альтернативную) и проверка — `dcm.md`, «Как работает экземпляр кейса».

## ✅ Условие запуска кейса
Поле `Filters` схемы — фильтр строкой (формат фильтров процесса, `rootSchemaName` = объект кейса). Пример «<Колонка> = запись справочника»:
```json
"Filters": "{\"className\":\"BPMSoft.FilterGroup\",\"items\":{\"<GUID>\":{\"className\":\"BPMSoft.InFilter\",\"filterType\":4,\"comparisonType\":3,\"isEnabled\":true,\"trimDateTimeParameterToDate\":false,\"leftExpression\":{\"className\":\"BPMSoft.ColumnExpression\",\"expressionType\":0,\"columnPath\":\"<Колонка>\"},\"isAggregative\":false,\"key\":\"<GUID>\",\"dataValueType\":10,\"leftExpressionCaption\":\"<Подпись колонки>\",\"referenceSchemaName\":\"<Справочник>\",\"rightExpressions\":[{\"className\":\"BPMSoft.ParameterExpression\",\"expressionType\":2,\"parameter\":{\"className\":\"BPMSoft.Parameter\",\"dataValueType\":10,\"value\":{\"Name\":\"<Название>\",\"Id\":\"<Id записи>\",\"value\":\"<Id записи>\",\"displayValue\":\"<Название>\"}}}]}},\"logicalOperation\":0,\"isEnabled\":true,\"filterType\":6,\"rootSchemaName\":\"<Объект>\",\"key\":\"\"}"
```
- Проверено: запись с этим значением получила экземпляр, с другим — нет; дизайнер показал условие «<Колонка> = <Название>».
- Чтобы дизайнер редактировал условие, укажи эту колонку в `Filters` настройки раздела: `[{"columnUId":"<UId колонки>"}]`. Правка набора применяется при «Обновить из файловой системы» только со свежим `ModifiedOnUtc` в `descriptor.json` набора (`data-edit.md`).
- Несколько кейсов на объект — каждый со своим `Filters`; кейс без `Filters` подходит любой записи. Какой выбирается при нескольких подходящих — 🧪.

## ✅ Перевести запись на стадию из кода или запросом
Меняй колонку стадии: `UpdateQuery` DataService (`integration-api.md`) или `Entity.SetColumnValue("<Колонка>Id", <Id записи стадии>)` и `Save()`. Проверено запросом: экземпляр перешёл на стадию и запустил её шаги. Прямой SQL `update` события не вызывает 🧪 (как у процессов, `process-flow-edit.md`).

## Изменить кейс
- ✅ Свой кейс — правь его файлы (тот же `UId`), свежий `ModifiedOnUtc` в `descriptor.json`, «Обновить из файловой системы»; новые экземпляры идут по новой схеме. Запущенные при правке на месте 🧪 (при новой версии остаются на старой, `dcm.md`).
- 🧪 Новая версия файлами (формат снят с версии, сохранённой дизайнером): скопируй папки схемы и ресурсов под новым именем с новым `UId`; в `descriptor.json` — `"Parent": {"UId": "<UId прежней>", "Name": "<Имя прежней>"}`; в metadata — `A2`, `UId`, а также `A3`/`A4` стадий, шагов, `BK37` и маппингов `BK15` = новый UId, `BK8` = UId прежней, `"IJ9": <N>`; в `properties.json` — `"Version": "<N>"`; у прежней — `"IJ7": false` и `"IsActiveVersion": "False"`; строка новой версии в набор `SysDcmSchemaInSettings`.
- 🧪 Платформенный кейс замещением не меняют (замещений кейсов нет ни в платформе, ни в проекте) — новая версия в своём пакете.

## 🧪 Выключить кейс
Чекбокс «Активен» в дизайнере (свойство `Enabled` корневой версии). ❌ Правка `"Enabled": "False"` в `properties.json` не сработала (`dcm.md`).

## ✅ Удалить кейс
Подтверждено на двух версиях кейса и его наборах.
1. Поиск ссылок по `Pkg`: UId и имя кейса (другие версии через `Parent`, наборы `SysDcmSchemaInSettings`, код с `DcmSchemaManager`).
2. Удали папки `Schemas/<Имя>/` и `Resources/<Имя>.Dcm/` всех версий и наборы `Data/` настройки и связи (настройку раздела — только если она своя и нужна лишь этому кейсу).
3. «Обновить из файловой системы»: схемы «Удалено»; экземпляры кейса пропадают из `SysProcessData` и `SysEntityCommonPrcEl`.
4. Строки данных набор не удаляет — SQL: `delete from "SysDcmSchemaInSettings" where "SysDcmSchemaUId" = '<UId>'`, `delete from "SysDcmSettings" where "Id" = '<Id настройки>'` (если настройка своя). Журнал по желанию: `SysProcessElementLog` по `SysProcessId` и `SysProcessLog` с именем = заголовок кейса (остаются со статусом Running).
- ⚠️ Удаление только последней версии: новые записи кейс перестали получать. У оставшейся версии были `"IsActiveVersion": "False"` и выключенный `Enabled`, причина 🧪. Чтобы вернуть прежнюю версию, поставь ей `"IsActiveVersion": "True"` и убери `IJ7` 🧪.
