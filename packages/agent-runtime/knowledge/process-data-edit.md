### ✅ Режим «Агрегирующая функция»
✅ Подтверждено записью в CRM.
- Count: `ResultType` = `"1"`, `FunctionType` = `"0"`, `AggregationColumnName` не задан. Выход — `ResultCount`.
- Sum/Avg/Min/Max: `ResultType` = `"1"`, `FunctionType` = `"1"`…`"4"`, `AggregationColumnName` = **имя** колонки (`"Amount"`, не UId). Выход — `ResultIntegerFunction` (целые), `ResultFloatFunction` (дробные и деньги), `ResultDateTimeFunction` (даты).
- В этом режиме `ReadSomeTopRecords` = `"false"`, `OrderInfo` и `EntityColumnMetaPathes` без значения (`L8` = `{"GS5": "<UId процесса>"}`, в маппинге `GT1` = `{}`), `ResultCompositeObjectList` без `L18`.
- `comparisonType` — список см. в «Что настраивать» элемента «Читать данные» (`DataSourceFilters`).
- ✅ **Найдена ли запись** (подтверждено в CRM): в режиме «первая запись» (`ResultType` = `"0"`) `ResultCount` не заполняется и остаётся `0`, поэтому условие `== 0` срабатывает и для найденной записи. Для проверки «есть ли запись» ставь элемент в режим Count (`ResultType` = `"1"`, `FunctionType` = `"0"`) и проверяй `ResultCount`. Если нужны и колонки записи — второй элемент «Читать данные» в режиме «первая запись».
- Два элемента одного типа в процессе — каждый со своими новыми UId элемента, 20 параметров и 20 маппингов; ресурсы — под своим именем элемента.

- `RecordAddMode` — `"0"` = добавить одну запись, `"1"` = «Добавить результат выборки» (✅ подтверждено записью в CRM: выборка из двух записей создала две записи). В режиме `"1"` ещё два параметра: `FilterEntitySchemaId` — `GS2` = UId объекта выборки; `DataSourceFilters` — `GS2` = JSON фильтра в том же виде, что у «Читать данные» (`className`, `serializedFilterEditData`, `dataSourceFilters`; например `comparisonType` 9 — «начинается на»). Значение колонки из выборки — элемент `RecordDefValues` с `Source` `6`, `MetaPath` = UId колонки объекта выборки, `Value`/`DisplayValue` пустые, `value`/`displayValue` = `{"isLczValue": true}`, `DataValueTypeUId` — тип колонки; в Designer — «Колонка из выборки», показ `[#Результат выборки.<Колонка>#]`.
- `RecordId` — выход, Id созданной записи: `[#[IsOwnerSchema:false].[IsSchema:false].[Element:{<UId элемента>}].[Parameter:{<UId параметра RecordId>}]#]`.
- `RecordDefValues` — `GS2` = JSON-строка `{"$type": "BPMSoft.Core.Process.LocalizableParameterValuesList, BPMSoft.Core", "$values": [...]}`, по элементу на колонку: `ItemUId` (новый GUID), `columnMetaPath.value` = UId колонки, `schemaUId.value` = UId объекта, `value` / `displayValue`, `parameterValue.value` = JSON-строка `ProcessSchemaParameterValue` (`Source`, `DataValueTypeUId` = тип колонки, `ReferenceSchemaUId` = объект справочника или нули).

### Общий приём клонирования элемента-действия

Проверен на пяти видах. Порядок: загрузить процесс-образец, взять элемент и его маппинги (`BK15`, где `GT2` содержит UId элемента), заменить в их JSON-тексте UId процесса-источника, элемента, дорожки, всех параметров `BP2` и маппингов на новые, переименовать элемент (`A2` элемента и маппингов), затем задать свои значения ключевых параметров одновременно в `L8` параметра и в `GT1` маппинга. Ресурсы `BaseElements.<Образец>.Parameters.*` скопировать с заменой имени элемента. Не меняются: `BL7` и `J6` элемента, `A3`/`A4` параметров `BP2` (равные UId схемы действия), `GT4`, `GT5`, `L1`, `L9`, `GS5` у параметров, значения которых не менялись.
