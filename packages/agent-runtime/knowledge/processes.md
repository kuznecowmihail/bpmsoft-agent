# Процессы (ProcessSchemaManager) — модель metadata

Поля `metadata.json` процессов. Метки: ✅ подтверждено записью в CRM или Designer, 🧪 не проверено, ❌ опровергнуто. Всегда перепроверяй на текущем проекте — набор мог не покрыть все случаи.

## Структура файла
- Все элементы процесса (события, задачи, шлюзы, связи) лежат в одном массиве `MetaData.Schema.BK4`.
- Тип элемента — по полю `BL1` (полное имя .NET-класса, например `BPMSoft.Core.Process.ProcessSchemaSequenceFlow`, `ProcessSchemaConditionalFlow`, `ProcessSchemaExclusiveGateway`, `ProcessSchemaParallelGateway`, `ProcessSchemaUserTask`, `ProcessSchemaScriptTask`, `ProcessSchemaStartEvent`, `ProcessSchemaTerminateEvent`, `ProcessSchemaIntermediateCatchTimerEvent`).
- `A3`/`A4` — CreatedInSchemaUId / ModifiedInSchemaUId: UId схемы, где элемент создан и изменён последний раз (у своих элементов = UId процесса).
- `A5` — CreatedInPackageId: UId пакета, где создан элемент (у элементов процесса = `B6`).
- `BL7` — для элементов БЕЗ собственной страницы — **фиксированная константа**, одинаковая у ВСЕХ экземпляров этого типа элемента во всех просканированных процессах: `ScriptTask`, `IntermediateCatchTimerEvent`, шлюзы, остальные события, формула, подпроцесс, веб-сервис, дорожки (✅ подтверждено на реальных схемах проекта, 30.10.2026). Исключения: `ProcessSchemaSequenceFlow` (два значения) и `UserTask`, у которого `BL7` зависит от вида страницы или собственного действия (например, `J6`, см. `process-user-pages.md`). Похоже на ссылку на шаблон фигуры/типа элемента.

## Связи (`SequenceFlow`/`ConditionalFlow`)
- `CI1`/`CI2` — UId источника/цели связи (**подтверждено** через Designer Service API и через самопроверку целостности на нескольких файлах).
- `CI3` — текст условия перехода. **Подтверждено скриншотом**: правая панель `ConditionalSequenceFlow1` в Designer показывает «Условие перехода» с текстом того же смысла — только там имя параметра резолвлено из GUID в читаемое, в файле — сырой биндинг `[#[IsOwnerSchema:false].[IsSchema:false].[Parameter:{guid}]#] > 0` (или обычный C#-код вроде `UserConnection.DBSecurityEngine.GetCanExecuteOperation(...)`). Литеральная строка `"null"` — если условия нет.
- `CI4` — тип связи. **Подтверждено скриншотом**: заголовок правой панели `DefaultSequenceFlow1` — «Поток по умолчанию», `ConditionalSequenceFlow1` — «Условный поток». `1` = безусловная/запасная ветка на развилке (заголовок «Поток по умолчанию», имя схемы не обязано быть `Default*`), `2` = условная ветка (заголовок «Условный поток», есть `CI3`). У `ParallelGateway` (все ветки выполняются одновременно) поле `CI4` отсутствует у всех исходящих связей.
- Подпись стрелки на холсте (например «Период хранения > 0») — это **имя/caption связи**, хранится отдельно от `CI3` — не путать одно с другим.
- `CI5` — **подтверждено экспериментом (реальный до/после диф на одноразовом тестовом процессе)**: константа `"FF939598"` — цвет линии, но НЕ настраивается через обычный интерфейс Designer вообще (проверили — опции смены цвета линии в UI нет). Фиксированный внутренний дефолт, не бизнес-параметр.
- `CI6` — VisualType связи; платформа всегда пишет `1` (AutoPolyline), не менялась при изгибе линии.
- `CI11`/`CI12` — **подтверждено экспериментом**: это координаты точек привязки линии к двум фигурам (начало/конец), а НЕ «только для прямых линий», как предполагалось раньше — они присутствуют ВСЕГДА (и для прямых, и для изогнутых линий) и подстраиваются под новую геометрию при изменении маршрута линии (проверено: значения изменились после изгиба той же линии, но поля не исчезли).
- `CI7`/`CI8` — **подтверждено экспериментом**: появляются именно тогда, когда маршрут линии становится не прямым (у прямой линии их не было, после изгиба — появились `"0;1"`/`"0;1"`). Похоже на векторы направления выхода/входа стрелки из/в фигуру.
- `CI10` (`{Item0, Item1}`) — **подтверждено экспериментом**: координаты промежуточных точек излома линии — появляется только когда линия не прямая (после изгиба той же линии появилось `{"Item0": "317;81", "Item1": "616;81"}`, обе точки на одной высоте — верхняя часть прямоугольного обхода).
- `CI9` — CurveCenterPosition (центр кривой, для связи-кривой); в эксперименте не воспроизведено, изгиб дал `CI10`.
- **Эксперимент с перемещением фигуры (линия не правилась)**: при переносе фигуры в Designer пересчитались `CI7`/`CI8`/`CI10`/`CI11`/`CI12`. При переносе `TerminateEvent1` (без прикосновения к линии) `CI7` (направление выхода из источника) не изменилось — источник не двигали; `CI8` (направление входа в цель) сменило знак (`"0;1"` → `"0;-1"`) — цель оказалась по другую сторону точки излома; `CI10.Item1` (точка излома со стороны цели) сдвинулась по X вслед за новой позицией цели; `CI12` (точка привязки к цели) изменилась полностью, проследовав за фигурой. `CI1`/`CI2`/`CI5`/`CI6` при этом не изменились. ❌ Опровергнуто: «Designer сам пересчитает `CI11`/`CI12` при загрузке процесса из файлов». После переподключения `CI2` без правки `CI12` линия ушла в пустоту, хотя процесс выполнялся по `CI1`/`CI2` (шаг 20, 03.10.2026). При записи файлами Designer геометрию не пересчитывает — задавай `CI11`/`CI12` сам (`process-edit.md`, «Создать процесс с нуля», таблица «Что заменить»).

## Параметры (`FJ1` — параметры процесса; `BP2` — локальные параметры элемента, например `UserTask`; `FC1` — локальные параметры `IntermediateCatchTimerEvent`)
- `BL1: "BPMSoft.Core.Process.ProcessSchemaParameter"`, `A2` — имя параметра.
- `L1` — тип данных параметра. **Подтверждено самопроверкой**: использует ТОТ ЖЕ каталог DataValueType GUID, что и `S2` у колонок объекта (см. `entity.md`, «`D2`») — например `8b3f29bb-...`=TEXT, `23018567-...`=GUID, `90b65bf8-...`=BOOLEAN, `b295071f-...`=LOOKUP, `6b6b74e2-...`=INTEGER.
- `L8` — значение по умолчанию: `{GS1: <источник значения>, GS2: <значение или выражение>, GS5: UId процесса}`. `GS1`: `1` константа, `3` формула/макрос (полный enum — в «Расшифровано по словарю»). Структурно похоже на `defValue` колонок объекта (🧪).
- `L9` — для lookup-параметра: UId целевой Entity-схемы (та же роль, что `S4` у колонок объекта) — **подтверждено самопроверкой** на нескольких примерах.
- `L14` — IsPerformer, `L16` — ReferenceSchemaName (см. «Расшифровано по словарю»).
- `BK37` — специальный параметр процесса «Заголовок экземпляра процесса» (**подтверждено скриншотом буквально**: содержимое `[#[PropertyValue:Caption]#]` совпадает с полем «Заголовок экземпляра процесса» в настройках процесса). Хранится не в `FJ1`, а отдельным полем верхнего уровня (одиночный dict, не список).

## ScriptTask
- `CH1` — **само тело C#-кода задачи, прямо строкой внутри `metadata.json`** (**подтверждено**: папка схемы содержит только `metadata.json`/`properties.json`/`descriptor.json`, отдельного `.cs`-файла с этим кодом НЕТ — компилируется в `Autogenerated` при сборке, но в `Pkg` хранится только как строка `CH1`).- `CH2` — UseFlowEngineScriptVersion (по умолчанию false; у 99% заданий-сценариев `true`, см. «Расшифровано по словарю»). ❌ Опровергнуто: «выполнять асинхронно». Без `CH2` задач всего два процесса, вероятно старый формат схемы.
- `BL6` — **прояснено широким сканированием**: встречается лишь у единичных элементов проекта, значения — просто названия категорий («Event»/«Task»/«Gateway»/«SequenceFlow»). Похоже на пережиток старого формата схем, не настоящая настройка Designer.

## IntermediateCatchTimerEvent (таймер ожидания)
- Собственные параметры лежат в `FC1` (аналог `BP2` у `UserTask`), обычно один параметр `StartOffset`.
- `StartOffset` — **подтверждено**: `L1 = INTEGER` (тип INTEGER, см. `entity.md`, «`D2`»), `L8.GS2` — арифметическое выражение в СЕКУНДАХ (например `"10 * 60"` = 10 минут, `"7 * 24 * 60 * 60"` = 7 дней) — это задержка перед срабатыванием таймера.
- `IL3: true`, `BY3: 0` — **подтверждено широким сканированием**: константы без единого исключения на всех 39 таймерах проекта. Похоже на фиксированный внутренний маркер типа элемента (аналогично `BL7` у нестраничных элементов), не пользовательская настройка — не ожидается соответствующий видимый чекбокс.

## Ресурсы процесса (`Pkg/<Пакет>/Resources/<ИмяПроцесса>.Process/resource.<culture>.xml`)
**Подтверждено на реальном процессе проекта**: реальный человекочитаемый текст (заголовки элементов, подписи параметров, тексты условий и т.д.) хранится НЕ в `metadata.json` схемы, а в ОТДЕЛЬНОЙ структуре — папке `Resources/<ИмяПроцесса>.Process/` (родная сестра папки `Schemas/<ИмяПроцесса>/`, лежит в том же пакете), внутри которой по одному XML-файлу на каждую локаль: `resource.ru-RU.xml`, `resource.en-US.xml` и т.д. Формат: `<Resources Culture="ru-RU"><Group Type="String"><Items><Item Name="<Путь>" Value="<Текст>" /></Items></Group></Resources>`.
- Ключ (`Name`) — это ПУТЬ ПО ИМЕНАМ элементов процесса (не по UId!): `Caption` — заголовок самого процесса; `BaseElements.<ИмяЭлемента>.Caption` — подпись элемента (задачи/события/шлюза) на диаграмме; `BaseElements.<ИмяЭлемента>.Parameters.<ИмяПараметра>.Caption` — подпись параметра элемента; `BaseElements.<ИмяЭлемента>.Parameters.<ИмяПараметра>.DisplayValue` — читаемое представление значения/биндинга параметра (см. ниже); `LaneSets.<ИмяLaneSet>.Caption` и `LaneSets.<ИмяLaneSet>.Lanes.<ИмяLane>.Caption` — подписи дорожек; `NotificationCaption.Caption`/`NotificationCaption.DisplayValue` — **подтверждает ранее найденное**: это ровно поле `BK37` («Заголовок экземпляра процесса»); `Parameters.<ИмяПараметра>.Caption` — подписи параметров процесса верхнего уровня (`FJ1`).
- `DisplayValue` — показывает, как «сырой» биндинг вида `[#[IsOwnerSchema:false].[Parameter:{guid}]#]` (хранящийся в `metadata.json`) превращается в читаемый текст вида `[#<Элемент>.<Параметр>:<Колонка>#]` — то есть каждый GUID в биндинге заменяется на цепочку человекочитаемых подписей (имя элемента → имя параметра → имя вложенного поля). Это ключ к тому, как реально расшифровывать/составлять такие выражения без доступа к живому Designer.
- ✅ Значения параметров элементов тоже в ресурсах (подтверждено на реальных схемах проекта): ключ `BaseElements.<ИмяЭлемента>.Parameters.<ИмяПараметра>.DisplayValue` — читаемое значение параметра элемента, в том числе строковой константы (в `metadata.json` у такого параметра `GS1: 1` без `GS2`, само значение — только в ресурсе). Описывая процесс, бери значения параметров элементов отсюда.
- Эта же логика (папка `Resources/<Имя>.<Категория>/resource.<culture>.xml` рядом со `Schemas/<Имя>/`) — ОБЩИЙ механизм BPMSoft, не специфичный для процессов: подтверждено, что для объектов используется суффикс `.Entity`, для клиентских схем — `.ClientUnit`, для исходного кода — `.SourceCode` (видно по содержимому папки `Resources` реального пакета) — при разборе объектов/исходного кода/действий процессов ожидай точно такую же структуру ресурсов, только со своим набором путей-ключей.

## Расшифровано по словарю `metadata-codes.md` (бывшие открытые вопросы)
Коды взяты из методов `WriteMetaData` платформы (см. `metadata-codes.md`), часть уже подтверждена записью в CRM.
- `A3`/`A4` — CreatedInSchemaUId / ModifiedInSchemaUId: UId схемы, где элемент создан и где изменён последний раз (у своих элементов = UId процесса).
- `A5` — CreatedInPackageId: UId пакета, где создан элемент (у элементов процесса = `B6`). У самой схемы в файлах встречаются и другие GUID; для нового процесса подошёл новый GUID (✅).
- `L8.GS1` — источник значения (enum `ProcessSchemaParameterValueSource`): 0 None, 1 ConstValue, 2 Mapping, 3 Script (формула/макрос), 4 SystemValue, 5 SystemSetting, 6 EntityMapping, 7 SamplingEntityMapping. В проекте встречаются только 1 и 3; системные переменные и настройки пишутся макросом через 3 (✅ записью).
- `GS5` — ModifiedInSchemaUId = UId процесса.
- `L12` — Direction: 0 In, 1 Out, по умолчанию (поля нет) Variable (✅ записью). `L6` — IsRequired (✅). `L13` — IsResult. `L14` — IsPerformer. `L16` — ReferenceSchemaName. `L11` — IsValueSerializable (по умолчанию true).
- `CH2` — UseFlowEngineScriptVersion (по умолчанию false; у 99% заданий-сценариев true — ставь true).

## ✅ Диагностика выполнения: журнал процессов в БД

**Подтверждено записью в CRM (21.10.2026).** Где и почему упал или завис процесс, видно запросом к БД, без интерфейса:
- `SysProcessLog` — экземпляры процессов: `Id` — UId экземпляра (это `ProcessDescriptor.UId` и `OwnerUId` в действии процесса), `Name` — заголовок процесса, `StatusId` → `SysProcessStatus`, `StartDate`, `CompleteDate`. Есть представление `VwSysProcessLog`.
- `SysProcessElementLog` — выполненные элементы: `Id` — UId элемента (свойство `UId` в действии процесса; его передают в `ProcessEngine.CompleteExecuting`), `SysProcessId` → экземпляр, `Caption`, `Type` (класс элемента, например `BPMSoft.Core.Process.ProcessSchemaUserTask`), `StatusId`, `ErrorDescription` (полный текст исключения со стеком), `SchemaElementUId`, `StartDate`, `CompleteDate`. Есть представление `VwSysProcessElementLog`.
- `SysProcessStatus` (колонка `Name`): `Running` `ed2ae277-b6e2-df11-971b-001d60e938c6`, `Completed` `815c9586-b6e2-df11-971b-001d60e938c6`, `Error` `f942c08d-b6e2-df11-971b-001d60e938c6`, `Inactive` `67700d9c-28ac-46ef-9037-b81a53b7b330`, `Canceled` `1be78f3e-234d-4d6a-869a-dc07253fd2f3`, `Cancelling` `006f6d7a-6d9a-4e8c-bf5f-2ddac8b3df9a`.
- Последние запуски процесса и шаги экземпляра:
  ```sql
  SELECT l."Id", s."Name" AS "Status", l."StartDate"
  FROM "SysProcessLog" l JOIN "SysProcessStatus" s ON s."Id" = l."StatusId"
  WHERE l."Name" = '<Заголовок процесса>' ORDER BY l."StartDate" DESC LIMIT 5;

  SELECT e."Caption", s."Name" AS "Status", e."ErrorDescription"
  FROM "SysProcessElementLog" e JOIN "SysProcessStatus" s ON s."Id" = e."StatusId"
  WHERE e."SysProcessId" = '<Id экземпляра>' ORDER BY e."StartDate";
  ```
- Исключение в задании-сценарии не пробрасывается в `Execute`: элемент и процесс получают статус `Error`, текст и стек — в `SysProcessElementLog.ErrorDescription` (✅ 24.10.2026). Статус проверяй в коде запуска, см. `process-run-edit.md`, «Запуск процесса с клиента и из C#».
- Процесс, который ждёт элемент, — `Running` и у экземпляра, и у элемента. После отмены — `Canceled` у обоих.
