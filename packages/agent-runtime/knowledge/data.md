# Данные пакета (Data) — модель metadata

Статусы: ✅ подтверждено записью или запросом, 🧪 не проверено, ❌ опровергнуто. Рецепты создания и правки — `data-edit.md`.

## Общее

- **Назначение**: данные (обычно строки справочников и системных таблиц), которые переносятся вместе с пакетом. Это конкретные значения строк таблиц БД, зафиксированные в файлах пакета, а не структура схемы.
- **Структура папки**: `Pkg/<Пакет>/Data/<Имя>/`
  - `descriptor.json` — метаданные набора и список колонок;
  - `data.json` — сами строки;
  - `filter.json` — пустой во всех проверенных примерах; не обязателен: наборы без него загружаются (✅ подтверждено записью в CRM (29.10.2026));
  - `Localization/` — опциональная подпапка, есть только если в наборе есть локализуемые колонки (`Name`, `Description`); содержит `data.<culture>.json`.
- Папки `Resources/` у Data нет: локализация идёт через `Localization/` внутри Data-схемы, а не через `resource.xml` (как у Entity/Process/ClientUnitSchema).
- ✅ Пример с локализацией: набор справочника с колонками `Name`/`Description` (локализуемы), в `Localization/` три файла культур.
- ✅ подтверждено на реальных схемах проекта (30.10.2026): набор `Lookup_<Объект>` может содержать только `Id`, `SysEntitySchemaUId`, `SysPageSchemaUId` — без локализуемых колонок и без `Localization/`; такой набор загружается. У большинства наборов `Lookup_*` есть `Name`/`Description` и `Localization/`.

## Data или SQL-скрипт

- **Data** — записи и переводы, которые должны появиться или обновиться при установке (см. `IsForceUpdate` ниже).
- **SQL-скрипт пакета** — удаление строк (Data строки не удаляет, ✅ 05.10.2026), массовые правки и всё, что Data не умеет (`sql-script.md`).
- Порядок в одном обновлении: Data, затем SQL-скрипт с `InstallType: 2` (`AfterSchemaData`). ✅ подтверждено записью в CRM (29.10.2026): набор (значение системной настройки) установлен первым, скрипт увидел его и перезаписал значение.

## descriptor.json

```json
{
  "Descriptor": {
    "UId": "<UId набора>",
    "Name": "<Набор>",
    "ModifiedOnUtc": "\/Date(1790154047000)\/",
    "InstallType": 0,
    "Schema": {
      "UId": "<UId объекта>",
      "Name": "<Объект>"
    },
    "Columns": [
      {
        "ColumnUId": "9e53fd7c-dde4-4502-a64c-b9e34148108b",
        "IsForceUpdate": true,
        "IsKey": false,
        "ColumnName": "Description",
        "DataTypeValueUId": "ddb3a1ee-07e8-4d62-b7a9-d0e618b00fbd"
      },
      {
        "ColumnUId": "ae0e45ca-c495-4fe7-a39d-3ab7278e1617",
        "IsForceUpdate": false,
        "IsKey": true,
        "ColumnName": "Id",
        "DataTypeValueUId": "23018567-a13c-4320-8687-fd6f9e3699bd"
      }
    ]
  }
}
```

### Поля

- **`Schema.UId` / `Schema.Name`** — ЦЕЛЕВОЙ объект (Entity-схема), в который загружаются данные: реальный справочник (`<Объект>`) или `BaseLookup` — универсальный справочник BPMSoft.
- **`Columns`** — ШАБЛОН данных (какие колонки участвуют):
  - `ColumnUId` — UId колонки целевого объекта (поле `D2` в metadata.json, `entity-schema.md`);
  - `ColumnName` — имя колонки (`Id`, `Name`, `Description`…);
  - `DataTypeValueUId` — GUID типа данных; таблица типов — `crm-db.md`, «Типы данных»;
  - **`IsKey`** — ✅ `true` только у `Id` (подтверждено на обоих примерах). Ключ сопоставления строки при повторной установке и обновлении;
  - **`IsForceUpdate`** — см. раздел «IsForceUpdate» ниже.
- **`InstallType`** — ✅ enum платформы `BPMSoft.Common.SysPackageSchemaDataInstallType`, три значения (не путать с 4-значным enum SQL-скриптов, `sql-script.md`):
  - `0` — **Install**. ✅ Строки загружаются при «Обновить из файловой системы» (05.10.2026). Почти все наборы.
  - `1` — **FirstInstall**. ✅ При «Обновить из файловой системы» строки не добавляет (05.10.2026). 🧪 Поведение «только при первой установке пакета» по названию; не проверено.
  - `2` — **Update**. ✅ Новые строки не добавляет; существующие записи обновляет колонками с `IsForceUpdate: true`, включая переводы в `Sys<Объект>Lcz` (21.10.2026).
- ✅ Ключи `descriptor.json` одинаковы у всех наборов данных стенда: `Columns`, `InstallType`, `ModifiedOnUtc`, `Name`, `Schema`, `UId`; корень `data.json` — `PackageData` (подтверждено на реальных схемах проекта, 30.10.2026).
- **`ModifiedOnUtc`** — время последнего изменения в формате `"\/Date(<миллисекунды_с_эпохи_Unix>)\/"` (см. `metadata-editing.md`). ОБЯЗАТЕЛЬНО обновлять на текущий момент при создании или изменении набора.

## IsForceUpdate

✅ Подтверждено 05.10.2026 на `Lookup_TestSrcEntity`:
- `true` — значение из файла перезаписывает БД у существующей записи (в основной таблице и в `Sys<Объект>Lcz`);
- `false` — значение пишется только при вставке новой записи; у существующей не меняется. Удобно для данных, которые пользователь меняет в CRM (счётчики).
- Ключ `Id` — всегда `IsKey: true`, `IsForceUpdate: false`.
- Новая запись (новый `Id` в `data.json` и в `Localization`) добавляется со всеми колонками, включая колонку с `IsForceUpdate: false`.
- ✅ 08.10.2026: правка только `Localization/data.en-US.json` у колонки с `IsForceUpdate: true` обновила перевод у установленной записи; русский файл не трогали.

## data.json

```json
{
  "PackageData": [
    {
      "Row": [
        { "SchemaColumnUId": "ae0e45ca-c495-4fe7-a39d-3ab7278e1617", "Value": "04992e36-958e-476a-8824-06c7192c6eed" },
        { "SchemaColumnUId": "bd9ec46e-6371-466e-87ec-1adf995e47c7", "Value": "null", "DisplayValue": "" },
        { "SchemaColumnUId": "e86949e7-1ee6-4277-8e20-982a9c673fdb", "Value": false }
      ]
    }
  ]
}
```

### Поля

- **`PackageData`** — массив; одна запись `Row` на каждую строку таблицы данных, которая должна быть установлена.
- **`Row`** — массив пар `{SchemaColumnUId, Value}`:
  - `SchemaColumnUId` — соответствует `ColumnUId` из `Columns` в `descriptor.json`;
  - `Value` — значение колонки:
    - GUID, числа, строки — литерал;
    - пустой lookup — строка `"null"` (буквально, не JSON `null`);
    - логические — JSON-булево `true`/`false`, не строка.
  - **`DisplayValue`** — ✅ обязательно у каждой lookup-колонки и колонок-изображений: отображаемое значение выбранной записи (например `"Россия"`), для пустой ссылки — `"null"` или `""`. Подтверждено ошибкой установки (28.09.2026): без `DisplayValue` «Обновить из файловой системы» пишет «При попытке чтения свойства "DisplayValue" получено значение ""». ❌ Ранее считалось опциональным — опровергнуто.
- ✅ Справочная колонка: в БД пишется `Value` (= `Id` записи); `DisplayValue` на запись не влияет (строка с неверной подписью получила тот же контакт, 05.10.2026).

## Localization/data.<culture>.json

Подпапка `Localization/` появляется ТОЛЬКО если среди колонок есть локализуемые текстовые колонки (`Name`, `Description`). Без них папку не создают.

```json
{
  "PackageData": [
    {
      "Row": [
        { "SchemaColumnUId": "ae0e45ca-c495-4fe7-a39d-3ab7278e1617", "ColumnName": "Id", "Value": "04992e36-958e-476a-8824-06c7192c6eed" },
        { "SchemaColumnUId": "736c30a7-c0ec-4fa9-b034-2552b319b633", "ColumnName": "Name", "Value": "ЮЛ" },
        { "SchemaColumnUId": "9e53fd7c-dde4-4502-a64c-b9e34148108b", "ColumnName": "Description", "Value": "" }
      ]
    }
  ]
}
```

Отличия от `data.json`:
1. Содержит только `Id` (ключ сопоставления) и ЛОКАЛИЗУЕМЫЕ колонки. Нелокализуемые (`Country`, `RecordInactive`) остаются только в `data.json`.
2. В каждой ячейке есть `ColumnName` рядом с `SchemaColumnUId` (в `data.json` его нет).
3. Один файл на каждую культуру: `data.ru-RU.json`, `data.en-US.json`, `data.es-ES.json`.
4. `Name` наследника `BaseLookup` — только в `Localization/`, в `data.json` его нет.

## Форматы значений

- ✅ Целое — JSON-число (`42`); логическое — `true` / `false`.
- ✅ Дата и время — строка `"\/Date(<мс с эпохи>+0300)\/"`, в БД хранится в UTC (`12:00 +0300` → `09:00`). Смещение указывай всегда.
