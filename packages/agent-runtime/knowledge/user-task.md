# Кастомные действия процесса (ProcessUserTaskSchemaManager) — подтверждённая модель metadata

## ⚠️ Отличие от преднастроенной страницы (UserTask с J5/J6)

**КРИТИЧЕСКИ ВАЖНОЕ УТОЧНЕНИЕ**: в `processes.md` существует раздел "## UserTask — страницы и «преднастроенные страницы»", описывающий механизм преднастроенной страницы (`ProcessSchemaUserTask` с полями `J5: "ProcessUserTaskSchemaManager"` И `BL7`/`J6`, указывающими на виртуальный UId).

**ТО, ЧТО ОПИСАНО ДАЛЕЕ — СОВЕРШЕННО ДРУГОЙ, ОТДЕЛЬНЫЙ МЕХАНИЗМ**: это НЕ преднастроенная страница, а **кастомное C#-действие** (кубик, вставляемый в диаграмму процесса как элемент) со своей собственной физической схемой-файлом.

**Оба используют**:
- один и тот же `ManagerName: "ProcessUserTaskSchemaManager"` для описания СВОЕЙ схемы
- один и тот же `ProcessSchemaUserTask` элемент в процессе

**НО подключаются к процессу РАЗНЫМИ способами**:
- **Преднастроенная страница** (старый механизм из `processes.md`): элемент процесса указывает на виртуальный UId через `J5`/`J6`, реальная страница берётся из `BP2.ClientUnitSchemaUId` параметра элемента
- **Кастомное действие** (новый механизм, описываемый здесь): элемент процесса содержит BL7-константу и параметры в `BP2`, привязанные напрямую к UId СХЕМЫ-ДЕЙСТВИЯ через `A3`/`A4`

Если при работе с `UserTask` ты видишь `BL7: "1418e61a-82c3-403e-8221-01088f52c125"` (ФИКСИРОВАННАЯ константа) — это **именно кастомное действие**, а НЕ преднастроенная страница.

Уточнено 02.10.2026 (шаг 19): у преднастроенной страницы `BL7` = `J6` = `ac2ef13c-30dd-4023-9c04-58f580743b48`, а `J5` обычно нет (1 из 19 элементов проекта). Рецепт — `process-tasks-edit.md`, «Преднастроенная страница».

## Общее

- `descriptor.json` → `ManagerName: "ProcessUserTaskSchemaManager"`. **Ключевое отличие**: НЕТ поля `Parent` (как и у SourceCode — нет наследования). Это просто ДЕЙСТВИЕ, регистрируемое в системе и вставляемое как кубик в диаграмму процесса.
- Папка схемы: `descriptor.json`, `properties.json`, `metadata.json`, `<Name>.cs` — та же структура из 4 файлов как у обычной Process-схемы или Entity.
- `properties.json` → содержит `CreatedInVersion` + **`IsInteractive`** (булево строкой, `"True"`/`"False"`) — **подтверждено на примере** (`"True"`) — вероятно означает, требует ли действие интерактивного участия пользователя (показывает страницу) или выполняется полностью автоматически.
- `metadata.json` — **плоский JSON-снимок (Формат B, аналог SourceCode)**, НЕ diff-журнал. Весь файл — один JSON-объект, без построчных операций `=`/`+`/`~`/`-`.
- `descriptor.json` → **`Caption`** — человекочитаемое название действия, видимое в панели инструментов Designer при выборе действия для вставки в процесс (например `"Вызвать веб-сервис \"Billing Contract Create\""`).

## Схема действия — структура верхнего уровня

Содержимое `metadata.json`: `{"MetaData": {"Schema": {...}}}`. Поля верхнего уровня `MetaData.Schema`:

- `ManagerName` — `"ProcessUserTaskSchemaManager"` постоянно
- `UId` — UId самой схемы-действия (используется везде как идентификатор этого кубика)
- `A2` — имя схемы, совпадает с `Name` в `descriptor.json` и с именем `.cs`-файла
- `A5` — UId ревизии/группы изменений (та же роль, что у Entity/Process/SourceCode)
- `B6` — UId пакета
- `B8` — версия BPMSoft создания/правки
- `B1`/`B2`/`B3` — пустые в примерах (вероятно служебные, как у Process)

## `FJ1` — параметры действия (входные и выходные)

**Подтверждено на примере**: `FJ1` — это массив СОБСТВЕННЫХ ПАРАМЕТРОВ действия, той же структуры `ProcessSchemaParameter`, что и `FJ1` параметров процесса верхнего уровня (см. `processes.md`). Это И входные, И выходные параметры вперемешку.

**Направление параметра — поле `L12`** (подтверждено 02.10.2026 записью, шаг 17): `0` — вход (в Designer процесса стрелка →), `1` — выход (стрелка ←). Если `L12` нет — параметр и вход, и выход; так у всех параметров старого реального действия проекта, поэтому там направление видно только по подписи «(Входящий)»/«(Исходящий)» и по коду C#.
- Опровергнуто: прежний вывод «направление не хранится отдельным полем» был сделан по образцу без `L12`.

**Структура каждого параметра в `FJ1`**:
- `UId` — идентификатор параметра (использует внутри действия)
- `A2` — имя параметра (совпадает с имением свойства-геттера/сеттера в C#)
- `A3`/`A4`/`A5` — UId владельца (схемы-действия) и ревизии
- `L1` — DataValueType (GUID типа данных, как у параметров процесса)
- **`L6: true`** — обязательный параметр (✅ шаг 17: в Designer процесса у параметра красная звёздочка)
- **`L13: true`** — встретилось на параметре со специальным назначением (например `ResponseBody`, явно выходной, хранит текст ответа) — гипотеза «многострочный текст»/«может быть длинным», не подтверждено
- `L8` — значение по умолчанию/биндинг (для входных параметров — обычно пусто или стандартный дефолт)

## `FK12` и `FK16`

- **`FK12`** — строка формата `"#839DC3"` (HEX-цвет) — **подтверждено сопоставлением**: точно совпадает с цветом заливки (`fill:#839DC3`) в SVG-иконках действия (см. раздел "Ресурсы" ниже) — это акцентный цвет иконки кубика на диаграмме процесса
- **`FK16`** — булево (`true` в примере), назначение не установлено — гипотеза «опубликовано»/«видно в панели инструментов Designer», не подтверждено

## Реальный код (`.cs`-файл)

**Подтверждено на реальном действии проекта**:
- `namespace BPMSoft.Core.Process.Configuration` — фиксированное пространство имён для всех действий процесса
- Класс **`partial`** с ИМЕНЕМ, СОВПАДАЮЩИМ с `Name` схемы
- Базовый класс `ProcessUserTask` задаёт сгенерированная платформой часть класса; от него доступны `UId` (элемент), `Owner` (экземпляр процесса), `OwnerUId` (строка, `Guid.Parse(OwnerUId)`), `CompleteExecuting` и `CancelExecuting` (✅ подтверждено записью в CRM, 21.10.2026: `OwnerUId` совпал с `ProcessDescriptor.UId`, `UId` — с `SysProcessElementLog.Id`).
- Переопределяет метод `protected override bool InternalExecute(ProcessExecutingContext context)` — главный метод выполнения кубика
- Обращается к СВОЙСТВАМ С ИМЕНАМИ, СОВПАДАЮЩИМИ с `A2` каждого параметра из `FJ1` (например `ResponseStatusCode`) — эти свойства-геттеры/сеттеры **генерируются автоматически платформой** на основе `FJ1` при компиляции (сам класс `partial`, видимая часть — только `InternalExecute`)
- **Входные параметры ЧИТАЮТСЯ** в начале метода (например `var clientId = ClientId;`)
- **Выходные параметры ЗАПИСЫВАЮТСЯ** перед `return true;` (например `ResponseStatusCode = 200;`)
- Метод возвращает `true` — элемент выполнен, процесс идёт дальше. `false` — элемент остаётся в статусе «Выполняется», процесс ждёт, пока элемент завершат: `UserConnection.ProcessEngine.CompleteExecuting(UId)` или переопределённый `public override bool CompleteExecuting(params object[] parameters)` с вызовом `base.CompleteExecuting(parameters)`. Ошибку сообщай исключением, а не `false`: процесс перейдёт в статус «Ошибка». ✅ подтверждено записью в CRM (21.10.2026): процесс в статусе `Running` ждёт, `CompleteExecuting` завершает элемент и процесс идёт дальше; рецепт — `user-task-edit.md`, «Асинхронное действие».
- Опровергнуто: прежняя запись «`false` при ошибке» — по коду платформы `false` означает ожидание завершения, а не ошибку.

## Ресурсы действия (`Pkg/<Пакет>/Resources/<ИмяДействия>.ProcessUserTask/resource.<culture>.xml`)

**Подтверждено на 3 культурах** (`ru-RU`/`en-US`/`es-ES`) реального примера:
- **`Caption`** — название действия (то же, что в `descriptor.json`), видимое в панели инструментов Designer
- **`Parameters.<ИмяПараметра>.Caption`** — подпись каждого параметра в интерфейсе Designer (с соглашением "(Входящий)"/"(Исходящий)" в тексте, см. выше)
- **`LargeSvgImage`** — большая SVG-иконка кубика (размер для отображения в библиотеке элементов)
- **`SmallSvgImage`** — маленькая SVG-иконка (размер для быстрого показа на диаграмме)
- **`TitleSvgImage`** — SVG-иконка для заголовка/название

Каждое изображение кодируется как `<Item Name="..." Type="Image" ContentType="Data" FileExtension=".svg" Value="<base64>" />` — это ИМЕННО те иконки, которые показываются в панели инструментов Designer при выборе действия для вставки в процесс.

**ПОДТВЕРЖДЁННОЕ совпадение**: цвет заливки в SVG-иконках (`fill:#...`) совпадает с `FK12` из metadata.json — это единый акцентный цвет действия.

## ✅ Как действие вставляется в процесс — ПОДТВЕРЖДЕНО

Реальный пример — процесс проекта с элементом, вызывающим своё действие:

### Элемент типа ProcessSchemaUserTask в диаграмме процесса (BK4)

```json
{
  "BL1": "BPMSoft.Core.Process.ProcessSchemaUserTask",
  "UId": "<свой UId элемента в диаграмме>",
  "A2": "<имя элемента на диаграмме, обычно совпадает с ИменемДействия>",
  "A3": "<UId процесса>",
  "A4": "<UId процесса>",
  "A5": "<UId пакета>",
  "IL2": "<UId дорожки>",
  "BL7": "1418e61a-82c3-403e-8221-01088f52c125",
  "BL8": "<UId процесса>",
  "BP2": [/* см. ниже */],
  ...другие поля...
}
```

**КЛЮЧЕВАЯ НАХОДКА**: `BL7 = "1418e61a-82c3-403e-8221-01088f52c125"` — **фиксированная УНИВЕРСАЛЬНАЯ КОНСТАНТА для элемента типа «вызов кастомного C#-действия»** (ProcessUserTaskSchemaManager).

**Подтверждено широким сканированием процессов проекта**: эта константа ОДНА И ТА ЖЕ для ЛЮБОГО такого действия, независимо от того, КАКОЕ именно действие вызывается. 

**Это резко отличается от механизма преднастроенной страницы** (из `processes.md`), где `BL7`/`J6` указывают на виртуальный UId, СОВПАДАЮЩИЙ с конкретной страницей — здесь наоборот, `BL7` ВСЕГДА один и тот же, а конкретное действие определяется через `BP2` (см. ниже).

**`J6` = UId схемы-действия** (по нему Designer выбирает действие), **`J5` нет**. Опровергнуто: прежнее «нет полей J5/J6» — у всех элементов реального процесса и в шаге 17 `J6` есть.

### BP2 — параметры действия, привязанные к конкретной схеме

**Подтверждено на примере и записью (шаг 17)**: `BP2` содержит по параметру на каждый параметр `FJ1` вызываемой схемы-действия (те же `A2`/`L1`/`L6`/`L12`), но **с новыми `UId`** — связь с параметром `FJ1` идёт через `GT5` маппинга (см. ниже). Отличия от `FJ1`:

- **`A3`/`A4` каждого параметра в `BP2` = UId СХЕМЫ-ДЕЙСТВИЯ** (а не UId процесса!)
  - Именно ЭТО и есть привязка к конкретному действию
  - **Подтверждено на примере**: все параметры `BP2` элемента имеют `"A3": "<UId схемы-действия>"` — реальный UId вызываемой схемы-действия
  - Если в процесс вставить ДРУГОЕ действие, `A3`/`A4` будут указывать на UId ТОГ ДРУГОЙ схемы-действия

- **`IL2` каждого параметра в `BP2` = UId элемента-владельца** (то есть UId самого этого `ProcessSchemaUserTask`-элемента, не путать с `IL2` дорожки на самом элементе)

### Биндинги входных параметров (L8)

Для ВХОДНЫХ параметров действия:
- `L8.GS2` содержит биндинг-выражение (например `"[#[IsOwnerSchema:false].[IsSchema:false].[Parameter:{<UId параметра-источника>}]#]"`)
  - Значение параметра берётся из другого элемента/параметра процесса
  - Формат биндинга — тот же, что у параметров процесса (см. `processes.md`)
- `L8.GS5` = UId процесса (владелец выражения)

### Выходные параметры без явного значения

Для ВЫХОДНЫХ параметров без явного значения:
- `L8` может быть пустой (`{}`)
- или содержать константу (например `"GS2": "false"` без GS1/GS5 — просто значение по умолчанию)

## ✅ Чтение выходных параметров действия дальше по процессу (маппинги BK15)

После того как действие выполнилось и установило свои выходные параметры, они могут быть прочитаны и переданы дальше по процессу через стандартные `BK15`-маппинги процесса (см. `processes.md`).

**ПОДТВЕРЖДЕНО И РАСКРЫТО ПОЛНОСТЬЮ: смысл полей `GT4`/`GT5` в маппингах** (это было открытым вопросом в `processes.md`):

- **`GT5` = UId КОНКРЕТНОГО ПАРАМЕТРА в схеме-действия**
  - Например UId выходного параметра В СХЕМЕ САМОГО ДЕЙСТВИЯ
  - Это НЕ UId параметра элемента процесса, а UId параметра ИЗ САМОЙ СХЕМЫ-ДЕЙСТВИЯ
  
- **`GT4` = UId СХЕМЫ-ДЕЙСТВИЯ, КОТОРОЙ ПРИНАДЛЕЖИТ параметр из `GT5`**
  - В данном случае — UId вызываемой схемы-действия
  - Это нужно, потому что UId параметра (`GT5`) уникален только В ПРЕДЕЛАХ своей схемы
  - `GT4` разрешает неоднозначность, указывая, В КАКОЙ ИМЕННО схеме искать этот параметр

**Подтверждено прямым сопоставлением реальных UId**:
- `GT5` мэппингов ТОЧНО совпадает с UId параметров из `FJ1` схемы-действия
- `GT4` ТОЧНО совпадает с `UId` САМОЙ ЭТОЙ СХЕМЫ

**Важное уточнение**: это работает, потому что `GT2` маппинга указывает на ЭЛЕМЕНТ ПРОЦЕССА (через `[Element:{elementUid}]`), а параметры в маппинге ищутся через `GT4`/`GT5`, которые вместе однозначно идентифицируют нужный параметр в `BP2` элемента — система "знает", что это элемент типа кастомного действия, и ищет параметр в его `BP2`, используя `GT4`/`GT5` как ключ для поиска.
