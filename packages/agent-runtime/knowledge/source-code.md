# Исходный код (SourceCodeSchemaManager) — подтверждённая модель metadata

## ⚠️ ПОДТВЕРЖДЕНО: структура и формат metadata.json для SourceCode-схем

Собрано на реальных схемах исходного кода проекта (веб-сервис и слушатель событий) — структура одинакова.

## Общее
- `descriptor.json` → `ManagerName: "SourceCodeSchemaManager"`. **Ключевое отличие от Entity/Process**: НЕ содержит поля `Parent` вообще — у SourceCode-схем нет наследования/родителя, это просто именованный кусок кода, зарегистрированный в системе. `Caption` обычно совпадает с `Name` (человекочитаемое имя не отличается от технического кода).
- Папка схемы: `descriptor.json`, `properties.json`, `metadata.json`, `<Name>.cs`. **Ключевое отличие от Entity**: `.cs`-файл СОДЕРЖИТ РЕАЛЬНЫЙ C#-КОД ЦЕЛИКОМ (полный класс с namespace/using/атрибутами), а НЕ пустой (как у Entity). SourceCode-схема ближе по этому признаку к ClientUnitSchema, где реальный код тоже лежит отдельно в файле (`.js` для клиента, `.cs` для исходного кода).
- `properties.json` — `{"Properties": {"CreatedInVersion": "<версия>"}}` (обёртка `Properties` есть у всех схем проекта).
- `metadata.json` использует **ПЛОСКИЙ JSON-СНИМОК (Формат B), а НЕ построчный diff-журнал** (`=`/`+`/`~`/`-`). Весь файл — один JSON-объект `{"MetaData": {"Schema": {...}}}` без построчных операций сохранения. Это отличает SourceCode от большинства Entity-схем и много Process-схем, но совпадает с форматом, встречающимся у некоторых Process-примеров (см. примечание в `metadata-editing.md`) и у ClientUnitSchema (Формат B).

## `metadata.json` — структура верхнего уровня

Содержимое: `{"MetaData": {"Schema": {...}}}`. Поля верхнего уровня `MetaData.Schema`:

- `ManagerName`: `"SourceCodeSchemaManager"` — постоянно.
- `UId` — UId самой схемы (используется везде в проекте как идентификатор этого кода).
- `A2` — имя схемы, совпадает с `Name` в `descriptor.json` и с именем `.cs`-файла.
- `A5` — UId «ревизии/группы ревизии» (та же роль, что и у Entity/Process, см. `metadata-editing.md`) — группирует записи, изменённые в одном движении; одна общая ревизия может охватывать разные типы схем.
- `B6` — UId пакета (та же семантика, что у Entity/Process).
- `B8` — версия BPMSoft создания/правки — совпадает с `properties.json.CreatedInVersion`.
- `B2` — ✅ локализуемые строки схемы (`{UId, A2: <ключ>, A3, A4: <UId схемы>, A5}`), значения — в ресурсах `LocalizableStrings.<Ключ>.Value`; непусто у 32 схем проекта, подтверждено записью 05.10.2026. `B1`, `B3` — пустые у всех 473 схем проекта.
- `HD1` — UId родителя схемы (`ParentSchemaUId` в `metadata-codes.md`). Почти у всех схем исходного кода реального проекта — `50e3acc0-26fc-4237-a095-849a1d534bd3`, у единичных — другие значения или поля нет. Опровергнуто: прежний вывод «фиксированная константа» был сделан по двум примерам.

## Реальный код (`.cs`-файл)

В отличие от Entity, где `.cs`-файл пустой, SourceCode-схема содержит реальный полноценный C#-класс:
- `namespace BPMSoft.Configuration.<ИмяПространства>` — обычное пространство имён.
- Стандартные `using`-директивы (например `using BPMSoft.Core;`, `using BPMSoft.Web;` для веб-сервисов).
- Атрибуты класса (например `[ServiceContract]`, `[WebInvoke]` и т.п. для веб-сервисов).
- Класс наследует нужный базовый класс платформы (например `BaseService` для веб-сервисов, или другие типы обработчиков).
- Методы класса с реальной реализацией логики.
- Код компилируется в `Autogenerated` при сборке пакета — то есть SourceCode-схема — это, по сути, просто **именованный, зарегистрированный в системе C#-файл**, доступный из других мест проекта (например из `ScriptTask`/`UserTask` через `using`-директиву с этим пространством имён).

## Ресурсы (`Pkg/<Пакет>/Resources/<ИмяСхемы>.SourceCode/resource.<culture>.xml`)

Тот же общий механизм, что и у процессов/объектов/клиентских схем (см. `processes.md`/`entity.md`/`client-schemas.md`):
- `Caption` — заголовок/подпись SourceCode-схемы (только один элемент, самой схемы, не под-элементов — в отличие от сложных типов типа Entity/Process, где может быть иерархия подписей).
- Формат: `<Item Name="Caption" Value="<Подпись>" />` внутри `<Items>`.
- **ВАЖНО**: как для любого типа схемы (см. `metadata-editing.md`), агент ОБЯЗАТЕЛЬНО должен создавать/обновлять оба культурных файла минимум `resource.ru-RU.xml` И `resource.en-US.xml`, даже если технически система может обойтись без одного из них.
