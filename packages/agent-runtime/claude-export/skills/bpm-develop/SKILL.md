# Разработка задачи в пакете BPMSoft

Скилл ведёт задачу на реализацию от пакета до проверки. Правила стенда — в `CLAUDE.md` (карта папок, главное правило для metadata, правило для C#, замены инструментов, наблюдения). Здесь — порядок работы.

Вопросы об устройстве без правок — скилл `bpm-explain`. Ошибка или сбой стенда — `bpm-troubleshoot`.

## Порядок работы

1. **Пакет.** Составь список пакетов: папки в `BPMSoft.Configuration/Pkg` с `descriptor.json`. Базовые пакеты платформы в список не входят. Если пакет не назван — спроси вопросом с вариантами (если пакетов много — покажи самые вероятные с пометкой, почему). Не угадывай пакет по задаче. Если пакет один — возьми его и назови. Названный пакет не найден — покажи список и попроси выбрать. Вопрос о пакете задавай отдельно; вопросы по требованиям — после ответа, потому что варианты зависят от объектов выбранного пакета. Если без правки другого пакета задачу не сделать (например, нужное замещение лежит в другом пакете) — спроси до плана.

2. **Требования.** Выясни всё, без чего придётся гадать: что делает функционал; где работает (раздел, карточка, деталь, объект, процесс, сервис); что меняется и что остаётся как было; что происходит с уже существующими записями; краевые случаи и что при этом видит пользователь; права; условия запуска (кнопка, сохранение, сигнал, расписание); названия объектов, колонок и полей, подписи на русском и английском; типы, обязательность, значения по умолчанию; связи и справочники; интеграции и формат данных. Существенный вопрос — спроси, не предполагай. Вопросы задавай встроенным инструментом вопросов (AskUserQuestion): один вызов на все вопросы, у каждого 2–5 коротких вариантов, рекомендуемый вариант ставь первым с пометкой «(рекомендуется)». Не спрашивай то, что однозначно следует из задачи, из кода проекта или из правил (префикс и стиль соседних схем, ресурсы на двух языках). Такие решения прими сам и перечисли в плане. Чтобы подготовить варианты, можно заглянуть в код пакета.

3. **Исследование.** Прочитай файлы знаний по теме — список по типам ниже. Найди затрагиваемые схемы и аналоги в выбранном и соседних пакетах. Переиспользуй паттерны проекта, не придумывай свою архитектуру. Для каждого затрагиваемого типа схемы вызови соответствующий подскилл (`bpm-entity`, `bpm-client-schemas`, `bpm-process`, `bpm-user-task`, `bpm-source-code`, `bpm-data`, `bpm-sql-script`, `bpm-registration`, `bpm-web-service`) и следуй его обязательным шагам. Для клиентских схем собери полную иерархию родителя (`bpm-client-schemas`), найди все карточки объекта: замещения с тем же именем, отдельные карточки-наследники (по `Parent.Name` в `descriptor.json`) и привязки в `SysModuleEdit`. Колонки объектов проверяй по `Autogenerated`.

4. **План и стоп.** Покажи план и дождись явного подтверждения. В плане:
   - критерии приёмки: AC-n — поведение, которое пользователь увидит или проверит; CC-n — краевые случаи, каждый закрыт хотя бы одним AC; DoD-n — готовность реализации. AC и DoD — в форме «Дано … Когда … То …», языком интерфейса (роль, карточка, поле, кнопка), без путей файлов и имён методов;
   - «Не делаем» — только то, что пользователь сказал или подтвердил; если границ нет — спроси;
   - схемы и файлы: что создаётся, что меняется (отдельно отметь чужие боевые схемы и замещения), что удаляется; пакет; порядок;
   - что сделать пользователю после записи (см. шаг 6), как проверить каждый AC: где смотреть, SQL-запрос, ожидаемый результат;
   - решения, принятые без вопроса, и риски (🧪-рецепты, неподтверждённые места).
   Заверши ход одним вопросом «Подтверждаете план?» с вариантами «Делай» и «Нужны правки» (через AskUserQuestion). Один ответ не совмещает открытый вопрос и план. Если пользователь меняет план — обнови его и снова остановись. Ответы на вопросы — не подтверждение плана: после них покажи план и остановись. Фразы «ок», «делай», «продолжай» не отменяют открытый вопрос по пакету или поведению. План и остановка нужны для любой правки файлов, даже маленькой и даже в продолжении того же чата.

5. **Реализация и проверка записи** — только после подтверждения плана. Пиши только в выбранный пакет; в другие — только если согласовано в плане. Правила записи — в знаниях: `.claude/skills/bpm-knowledge/metadata-editing.md` читай первым. Затем:
   - перечитай каждый изменённый файл;
   - запусти проверку по папкам изменённых схем: `node .claude/skills/bpm-knowledge/scripts/pkg-lint.js BPMSoft.Configuration/Pkg/<Пакет>/Schemas/<Имя> ...` (для наборов данных — `Data/<Набор>`, для SQL-скриптов — `SqlScripts/<Скрипт>`). Скрипт проверяет JSON, ресурсы в двух языках, SQL-скрипты, скобки в C#; для объектов и процессов запускает свои проверки. Исправь все строки «ОШИБКА» и повтори запуск. Строки «ВНИМАНИЕ» оцени; если считаешь «ОШИБКА» ложной — не обходи проверку, напиши об этом пользователю;
   - если `BPMSoft.Configuration/Pkg` — git-репозиторий, проверь `git status` (только чтение) и убедись, что изменилось только задуманное;
   - каталоги внутри `Pkg` копируй по одному источнику на команду с явным целевым путём;
   - если `node` недоступен, скажи пользователю, что автоматическая проверка не прошла по причине отсутствия `node`, и перечитай файлы сам по чек-листам из знаний.

6. **Проверка и итог.** Кратко перечисли, что создано и изменено. Затем напиши пользователю, что сделать:
   - в CRM нажать «Обновить из файловой системы»;
   - компиляция нужна, если менялись C# (исходный код, слушатели, сервисы), процессы или объекты; для клиентских схем, данных и SQL-скриптов достаточно обновления. Компиляцию запускает пользователь;
   - после компиляции обновить страницу (Ctrl+F5);
   - проверить каждый AC: где смотреть, SQL-запрос готовым текстом (для проверки записей в БД), ожидаемый результат. Для проверки в браузере — рецепты в `.claude/skills/bpm-knowledge/browser-check.md`;
   - если есть записи для проверки или очистки — SQL тоже готовым текстом, не выполняй сам.
   В конце — блок «Наблюдения для базы знаний» по правилам из `CLAUDE.md`, если было что отметить.

## Исключение: исправление только что сделанного

Пользователь прислал ошибку или пишет, что правка не работает, — а правка сделана по подтверждённому плану в этом же чате. Найди причину и исправь сразу, без нового плана, если объём задачи не меняется. Повтори шаг 5 (проверка) и шаг 6 (что сделать пользователю). Если для исправления нужно менять поведение, затрагивать другие схемы или удалять что-то — сначала план и подтверждение.

Ошибку из журналов или скриншот разбирай через `bpm-troubleshoot`.

## Какие знания читать по типу задачи

| Тип схемы | Подскилл | Файлы знаний |
|---|---|---|
| объект, колонки, события объекта | `bpm-entity` | `entity.md`, `entity-edit.md` |
| клиентские схемы (раздел, карточка, деталь, модуль, миксин) | `bpm-client-schemas` | `client-schemas.md`, `client-schemas-edit.md` |
| бизнес-процесс | `bpm-process` | `processes.md`, `process-edit.md` |
| своё действие процесса с C# | `bpm-user-task` | `user-task.md`, `user-task-edit.md` |
| исходный код C# | `bpm-source-code` | `source-code.md`, `source-code-edit.md`, `platform-api.md` |
| данные пакета | `bpm-data` | `data.md`, `data-edit.md` |
| SQL-скрипт | `bpm-sql-script` | `sql-script.md`, `sql-script-edit.md` |
| регистрация в интерфейсе | `bpm-registration` | `registration.md`, `registration-edit.md` |
| веб-сервис и его вызов из процесса | `bpm-web-service` | `web-service.md`, `web-service-edit.md` |

Всегда до записи: `metadata-editing.md`. Для незнакомого кода поля — `metadata-codes.md`. Шаблоны — `templates/README.md`, если в проекте нет своего образца.
Пути знаний — `.claude/skills/bpm-knowledge/<файл>`.
