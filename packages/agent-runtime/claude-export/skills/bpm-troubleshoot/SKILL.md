# Разбор ошибки на стенде

Скилл находит причину по журналам, файлам и тексту ошибки, затем исправляет по правилам `bpm-develop`. Правила стенда — в `CLAUDE.md`. Журналы — в папке `Logs/<ГГГГ-ММ-ДД>/` корня стенда. Время в журналах — UTC.

Сначала определи вход. Если непонятно — спроси вопросом с вариантами: стенд не стартует или обновление/компиляция упали; ошибка в браузере; ошибка в процессе или серверной логике.

## Вход A. Стенд не стартует, ошибка обновления или компиляции

1. Найди самую позднюю папку `Logs/<ГГГГ-ММ-ДД>/`.
2. Читай журналы с конца, а не с начала: `Error.log`, `PackagesSynchronization.log` (обновление из файловой системы), `Common.log`. По ситуации — `BusinessProcess.log` и `Scheduler.log`. Ищи последние строки с ошибкой и сопоставляй их по времени UTC с моментом, который назвал пользователь. Журналы большие — читай хвост, не всё целиком.
3. Из строки ошибки выдели имя схемы, путь или класс исключения. Найди схему-виновника в `BPMSoft.Configuration/Pkg` (grep по имени). Если ошибка уходит в код платформы, смотри `ResourcesCore` (если он есть на стенде) — только чтение.
4. Если журналы не дают ответа — попроси пользователя прислать нужные строки журнала, а не угадывай.

## Вход B. Ошибка в консоли браузера

1. Возьми текст ошибки и стек из сообщения пользователя или со скриншота. Скриншот смотри, только если текст не дал ответа.
2. По стеку найди клиентскую схему: имя в пути или в функции. Ищи сначала в `BPMSoft.Configuration/Pkg`, затем в `conf/content` и `Resources`.
3. Собери полную иерархию схемы скриптом из знаний:
   `APP=. node .claude/skills/bpm-knowledge/scripts/hierarchy.js <ИмяСхемы>`.
   Запускай из корня стенда (папки, где открыт Claude Code; в ней `BPMSoft.Configuration` и `conf`): `APP=.` работает и в Git Bash на Windows. Порядок и вывод скрипта — в `.claude/skills/bpm-knowledge/client-schemas-edit.md`.
4. Шум консоли и типичные ложные сообщения — в `.claude/skills/bpm-knowledge/browser-check.md`.

## Вход C. Ошибка в работе процесса или серверной логики

1. Читай `BusinessProcess.log` и `Error.log` с учётом времени, когда процесс запускался.
2. Найди схему процесса или класса, который упал. Для процессов есть известные причины в `.claude/skills/bpm-knowledge/process-edit.md` (раздел «Проверка перед сдачей процесса»), например дробные координаты в `BL3`, `CI11`, `CI12`.
3. Для процесса запусти `node .claude/skills/bpm-knowledge/scripts/pkg-lint.js BPMSoft.Configuration/Pkg/<Пакет>/Schemas/<Процесс>` — он проверит структуру процесса.

## Дальше — причина и исправление

- Назови причину одним-двумя предложениями: что было не так, в какой схеме, по какой строке журнала.
- Исправление — по правилам `bpm-develop`:
  - если ошибка в твоей только что сделанной правке по подтверждённому плану — исправь сразу, без нового плана, если объём задачи не меняется; повтори проверку `pkg-lint.js`;
  - если ошибка в чужой схеме, в другой части проекта или исправление меняет поведение, затрагивает другие схемы или что-то удаляет — сначала план и остановка, вопрос «Подтверждаете план?» через AskUserQuestion.
- Блок «Наблюдения для базы знаний» — по правилам `CLAUDE.md`, если узнал новое.

## Шаги проверки для пользователя

Скажи пользователю, что сделать после исправления:
- в CRM нажать «Обновить из файловой системы» и посмотреть строки журнала `PackagesSynchronization.log` за это время;
- компиляция — если менялись C#, процессы или объекты;
- после компиляции обновить страницу (Ctrl+F5);
- повторить действие, которое привело к ошибке, и сообщить результат;
- если нужна проверка данных — SQL-запрос готовым текстом.
